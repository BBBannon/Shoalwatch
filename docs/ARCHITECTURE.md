### Build and supply-chain security (S10, S12)

- **Dependency verification** is on: `gradle/verification-metadata.xml`. After adding or bumping a dependency, regenerate with
  `./gradlew.bat --write-verification-metadata sha256 help testDebugUnitTest assembleDebug assembleDebugAndroidTest assembleRelease` and review the diff.
- **Verification is checksum-only (sha256), by decision.** Signature verification (`verify-signatures`) is off because many artefacts (much of Google Maven) are not signed or have no published keys, so it would mostly add trust-on-first-use key entries. A sha256 pins the exact bytes that were reviewed, which is the stronger guarantee for a fixed dependency set. Revisit at the Milestone 8 security-team review.
- **Repositories:** `FAIL_ON_PROJECT_REPOS`; `google()` is limited to `androidx.*`, `com.android.*` and `com.google.*` in both `pluginManagement` and `dependencyResolutionManagement`.
- **Gradle wrapper:** `distributionSha256Sum` pins the official checksum of `gradle-8.11.1-bin.zip`; change both lines together.
- **Merged release manifest check:** the `verifyReleaseManifest` task (part of `check`, and a dependency of `assembleRelease` and `bundleRelease`) parses the MERGED release manifest and fails the build unless: `allowBackup="false"`; not debuggable; the launcher `MainActivity` is the only exported component; the permissions are exactly `INTERNET`, `ACCESS_NETWORK_STATE` and androidx.core's signature-level `app.shoalwatch.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`; the only provider is androidx.startup's (not exported); no EmojiCompat or ProfileInstaller initialiser remains. The source manifest removes the profile installer's exported receiver and initialiser and the EmojiCompat initialiser (it can ask Google Play services for a font; S7) with `tools:node="remove"`. `ManifestSecurityTest` still checks the source manifest. It also fails if the application sets any `android:networkSecurityConfig` (S4: user CAs must never be trusted). The rules are one plain object, `ManifestRules`, in `app/build.gradle.kts`; the `verifyManifestRuleFixtures` task (part of `check`) runs it over fixture manifests in `app/src/test/manifest-fixtures/` and fails unless `ok.xml` passes and each `bad-*.xml` (extra exported component, extra permission, `allowBackup` true, `networkSecurityConfig`, debuggable, banned initialiser, foreign provider, no launcher) fails with its expected message. So each rule is shown to fail without touching the real manifest.

## Layer rules (read before changing anything that sends a credential)

- **Callers pass ids; settings come from the store.** Anything that acts on a server's security settings (address selection, sign-in, sign-out, removal) takes a `serverId` and reads the current `Server` from `ServerStore` at the moment of use. There is no API that accepts a caller's `Server` copy for these.
- **Two senders of credentials, each with one rule for the address.** `AuthRepository` is the only sender of passwords, Quick Connect secrets and token revocation, and it alone picks that address (verified, https preferred). `ServerApi` is the only sender of the access token on ordinary requests, and it takes its address only from `AddressSelector.awaitOnline(serverId)`. See "Credentials" and "Authenticated requests" below.
- **The UI cannot reach tokens.** The seams (`data/servers/Seams.kt`) carry none; screens read `ServerSummary` and `AccountSummary`.
- **Ids from the server are validated** at the gateway (`JellyfinId`) and stored normalised; display strings from the server are sanitised there too (`displayText`).

## Network security model

- **Who is trusted:** the platform's own certificate authorities only. User-installed CAs are not trusted (no `network_security_config`).
- **Self-signed servers:** accepted only if the leaf certificate's public key (SPKI SHA-256, base64) equals the pin the user approved. A pin is checked only when system trust fails; a mismatch raises `PinMismatchException`, which `AppError.from` maps to `TLS_PIN_CHANGED`. Pin comparison is constant-time.
- **Hostnames:** normal hostname verification always runs first, so a system-trusted certificate for a different host is refused even on a pinned client. Only if that fails does a pinned client accept, and only when the peer's leaf key is exactly the pinned key (LAN certificates often lack a matching name).
- **TLS versions:** 1.2 and 1.3 only. Plain `http` is allowed by the connection spec but policed per server by `CleartextGuard`.
- **Redirects:** no client from `HttpClientFactory` follows one (`followRedirects(false)`, `followSslRedirects(false)` on the shared base; there is no option to turn them on). A 3xx reaches the caller as a response and the gateway treats it as an error (`SERVER_NOT_FOUND`). Defence in depth, as both application and network interceptors: `CleartextGuard`; `AuthInterceptor` (sets `Authorization` only for the server's own authorities, removes it and the legacy token headers and `api_key`-style query parameters everywhere else); `CustomHeaderInterceptor` (adds the configured headers only for the server's own authorities and removes every configured header name for any other). So even a caller that re-enables redirects cannot carry the token or a header to another host (`RedirectPolicyTest`). A later milestone that genuinely needs a media redirect followed must do it by hand and re-check the target authority before sending anything.
- **First contact:** `probeCertificate` handshakes with a capture-only trust manager that always fails after recording the leaf, so no request, token or header is sent on the unverified connection. It uses no `clientFor` client. The whole probe has a hard 10 s deadline: on expiry or cancellation its socket is closed (an uninterruptible DNS lookup may leave one daemon thread behind until it returns, but the caller is released). Certificate names are sanitised for display.
- **Client certificates (S5):** every client gets a recording key manager from `ClientCertWatch`, wrapping `KeyChainKeyManager` (which offers only the stored alias) or nothing. The TLS layer asks it for a client alias only when the server sent a CertificateRequest, so "the server asked" is known structurally, never from exception text. With no alias configured, only two things become `CLIENT_CERT_REQUIRED`: (a) a failure DURING the TLS handshake of a call on which the server asked (a TLS 1.2 alert; the handshaking call is marked by an `EventListener`, and `connectFailed` records it), and (b) the FIRST response, or first read, on a freshly handshaken connection that was asked and sent no certificate (a 400/403 such as nginx's "No required SSL certificate was sent", or for TLS 1.3 an IOException on that first read; marked by socket). A connection that has returned any response is proven: a later 403 (a genuine `FORBIDDEN`), a timeout or any other failure on it is never remapped. Known limit: a genuine 403, and also a timeout or reset, on the first exchange of a fresh connection to a proxy with optional client authentication is still reported as "needs a certificate". The result is `CLIENT_CERT_REQUIRED`, which the add-server checker turns into the "Choose certificate" step. A server that only asks optionally and then serves the request is unaffected. The certificate probe refuses the server certificate before any CertificateRequest is acted on, so a self-signed server that also needs a client certificate is always "trust this certificate" first, then "choose a certificate" (`ClientCertificateTest`, `ClientCertFlowTest`). `KeyChain` calls block and refuse the main thread; every network call in this app runs off the main thread. Any KeyChain failure presents no certificate.
- **Clients:** all share one connection pool and dispatcher; no cache, no cookies; connect 10 s, read/write 30 s, no call timeout (it would cut long downloads). Callers hold one client per server configuration (`ServerClients`; each `clientFor` builds a new SSLContext); a token revocation uses a one-off client instead (see "Token rules").

## Credentials: where they go

`AuthRepository` is the only code that sends a password, a Quick Connect secret or a revocation, and it alone picks the address for those (ordinary requests that carry the access token are `ServerApi`'s, see "Authenticated requests"):

1. The server is read from the store now (a removed server is `SERVER_NOT_FOUND`, and nothing is sent).
2. The address must be verified on the current network: `AddressSelector.awaitOnline(serverId)`. If nothing is verified, nothing is sent.
3. **HTTPS preferred:** if the verified address is plain http and the server also has an https address, that https address is checked (`/System/Info/Public` must report this server's id); if it answers, it is used. Plain http is used only when it is the server's only address or its https address cannot be reached.
4. The identity check is repeated on the chosen address immediately before the credential is sent; after sign-in the result's `ServerId` must match too (`SERVER_MISMATCH` otherwise; nothing stored).

The UI gets an opaque `SignInRoute` from `Authenticator.signInRoute(serverId)` before every attempt and hands it back; `AuthRepository` refuses any route it did not issue, so a screen cannot choose an address. `SignInRoute.encrypted` drives the Sign in screen's persistent "This connection isn't encrypted" notice.

- **Quick Connect** re-sends its secret on every poll (up to 5 minutes), so each issued route remembers the selector connection (`Connection.Online`) it was derived from, and a watcher on `connection(serverId)` ends the flow with `Failed(CONNECTION_CHANGED)` the moment that connection is anything else: `Checking` after a network change, `Offline`, or `Online` on another address. The check is also repeated just before the final `authenticateWithQuickConnect`, so no secret is sent after the change (`QuickConnectConnectionChangeTest`). The screen says "Your connection changed. Start Quick Connect again."
- **Sign-out** revokes the token only through that verified address (never by trying the saved addresses in turn), within 12 s, then removes the account here regardless (`NonCancellable`). If no address is verified the token is sent nowhere. A saved token that cannot be read (lost Keystore key) is not "nothing to revoke": `ServerStore.token` answers `StoredToken.Unreadable`, distinct from `Missing`, and `signOut` reports it exactly as an unreachable server. Either way the Servers screen says "Signed out on this phone. Shoalwatch couldn't sign you out on the server, so that sign-in may still be active there — you can remove it from the server's dashboard."
- **Remove server** first revokes every account on it in parallel by the same rules (6 s overall), then deletes the server here regardless, with the same notice when any revocation did not reach the server or any saved token could not be read (`ServerStore.tokens` counts the unreadable ones; the readable ones are still revoked).
- **Residual risk (plain http):** with an http address, nothing can authenticate the server: the id it reports is public, so on another network a device holding the same address can pass the identity check and capture what is sent. The https preference and the warnings shrink this; recommending HTTPS is the mitigation. Recorded in `docs/security/milestone-1-check.md`.

## Authenticated requests (`ServerApi`)

Every signed-in request in the app goes through `data/api/ServerApi`: `get` (decoded JSON), `post`, `delete`, `getBytes` (bounded stream, for artwork). Callers pass a `Session(serverId, userId)` (token-free; the UI observes it as `ServerCatalog.activeSession()`, which waits for the token warm gate like the other account reads), a `path` starting with `/` and a `query` list.

1. `store.awaitWarmed()`.
2. `AddressSelector.awaitOnline(serverId)`: nothing verified is `OFFLINE` ("You're offline. Showing what's saved on this phone where possible.") and **nothing is sent**. Only then is the server read from the store (so its addresses and security settings are current; a removed server is `SERVER_NOT_FOUND`), and the verified address must still be one of its saved addresses, or the attempt is treated like a lost connection.
3. The account's client comes from `ServerClients` via `ServerNet.authenticated(..., store::cachedToken)`: the token is read live on every request and never captured, so a signed-out account fails as `NOT_SIGNED_IN` with zero requests sent.
4. The URL is the verified `ServerAddress` (base path kept, e.g. `https://example.org/jellyfin`) plus `path` plus `query`, built only with `HttpUrl.Builder` so everything is encoded. A `path` containing `..`, a `.` segment, `//`, `?`, `#`, a backslash or a control character, or not starting with `/`, is an `IllegalArgumentException` (programmer error, fixed message, nothing sent). Ids are passed already normalised by `JellyfinId` and are not re-validated here.
5. Everything runs on the injected IO dispatcher (main-safe); cancelling the caller cancels the OkHttp call, including during the body read.

- **Unlike sign-in, ordinary requests do not upgrade to https.** If the verified address is the (consented) plain-http home address, that is where the token goes: using the fast home address at home is the feature. The residual risk is the one already recorded under "Residual risk (plain http)".
- **Status mapping** (a response is an answer, never retried): one function, `AppError.fromHttpStatus`, shared with the sign-in gateway: 401 `UNAUTHORISED`, 403 `FORBIDDEN`, 404 `SERVER_NOT_FOUND`, any other 3xx `SERVER_NOT_FOUND` (no client follows redirects, so that address is not serving the API), 304 `SERVER_ERROR` (we never send a conditional request, so a 304 is the server misbehaving), every other 4xx and 5xx `SERVER_ERROR`.
- **Network failure before a response:** the selector is asked to re-probe THIS server only (`refreshIfCurrent(serverId, used)`), and only if the `Connection.Online` the failed attempt used is still its current state (compared by identity: every verification publishes a new instance). So a burst of parallel failures after a network change causes one probe cycle, and a failure from before a newer verification cannot flip it back to `Checking`. The global `refresh()` stays for the UI's manual retry. If the call's `retry` flag is set (default true for GET and `getBytes`, false for POST and DELETE; callers opt in only for idempotent operations), `awaitOnline` is asked again and the call repeated exactly once, to whatever address is verified now (nothing verified: `OFFLINE`); a second failure is `AppError.from`. A guard refusal (`BlockedRequestException`: cleartext, signed out, client certificate, pin) is never retried. A failure while reading the body is mapped (and re-checks) without a retry. **Callers must not wrap `ServerApi` calls in their own retry loops**: retries would multiply (10 s connect and 30 s read timeouts each).
- **Bodies** (`JsonBodies`, shared with `JellyfinGatewayImpl`): bounded read on the decoded bytes (one byte past the limit decides; default 4 MiB for `get`), one Json configuration: `ignoreUnknownKeys` only. `coerceInputValues` is deliberately off, so an explicit JSON null for a non-nullable field is a decode failure (fixed `SERVER_ERROR`), never a silent default; DTOs for untrusted responses declare every field nullable with a default. Nothing from a body is ever in a message. `getBytes` hands the caller a source that fails with `SERVER_ERROR` past `maxBytes` (a larger declared length fails before the reader runs); the response is closed when the reader returns or throws and the source must not be kept. The reader's own exceptions, including an IOException such as a failed file write, propagate unchanged and are never treated as a network failure.
- **Rejected sign-in (401):** a 401 from the verified address of a signed-in call means the server no longer accepts this token. `ServerApi` calls `ServerStore.invalidateToken(serverId, userId)`: the in-memory token is removed (later calls fail at once as `NOT_SIGNED_IN` with zero requests, so the app cannot loop on a dead token), the account leaves `usable` (so `accounts`, `activeAccount`, `active()` and `activeSession()` all drop it, and the UI shows the server as needing sign-in), the server's cached clients are evicted, and `warmTokens` will not load it back. The database row is kept; signing in again (`upsertAccount`) overwrites it and restores normal operation. The call then fails with `UNAUTHORISED` "Your sign-in has expired. Sign in again." It is skipped when the sign-in was replaced after the request began (`tokenGeneration`), so a late 401 for the old token cannot sign out the new one. A 403 does none of this, and anonymous calls (sign-in, probing) never do. **Known limit:** on a plain-http address an impostor that passed the (public) identity check can answer 401 and so sign the user out locally. That is a denial of service only: no credential is exposed beyond what the plain-http residual risk already covers.
- **Network moved after verification:** `awaitOnline` proves the address answered as this server since the last network change the OS reported, not that the phone has not just moved. Ordinary requests have the same window as sign-in has (see "What `awaitOnline(serverId)` proves"); the ordinary-request token goes to the verified address in that window, and the plain-http residual risk applies.
- **Deferred (M9):** every request reads the full `Server` (a Keystore decrypt of custom headers) to build its client configuration. A correct cache needs a settings-version signal from the store; not small, so left for the artwork task, which is where parallel loads make it matter.

## Library endpoints (`LibraryGateway`)

`data/library/api/LibraryGateway` is the typed face of the server's library endpoints, built on `ServerApi`. It returns the app's own models (`data/library/Models.kt`), never DTOs or JSON; the DTOs (`Dtos.kt`) and mappers (`Mappers.kt`) are `internal`. Every request names the user (`userId`), asks for user data (`enableUserData=true`) and images (`enableImages=true`, `enableImageTypes=Primary,Backdrop,Thumb`, `imageTypeLimit=1`) where the endpoint offers them. Names and enum values below were checked against `docs/reference/jellyfin-openapi-12.4.0.json`.

| Gateway call | Method and path | Parameters used (besides `userId` and the image set) | Response |
|---|---|---|---|

List views do not request `Overview` (large); detail and episodes do. The three mutations are idempotent, so they opt in to `ServerApi`'s one retry. Array parameters are sent comma-delimited, as the reference describes.

**Untrusted-input rules at this boundary (SPEC S11):**
- **Ids** go through `JellyfinId` (normalised: lower case, no dashes). An item whose own id is not a GUID is dropped from a list; a single `item()` fails as `SERVER_ERROR`. Invalid optional ids (`parentId`, `seriesId`, `seasonId`) become null. Ids the caller passes in that are not GUIDs fail as `SERVER_NOT_FOUND` before any request.
- **Display strings** go through `displayText` (`displayParagraphs` for the overview) (control and format characters, including bidi and zero-width, removed): name, series name and sort name 200 characters, official rating 20. The overview (4,000) keeps line breaks (`displayParagraphs` in `core/`: at most one blank line in a row) but loses everything else unusual; HTML is not stripped here, the UI shows it as plain text. A name with nothing visible left is the empty string (the model holds no English text; the UI supplies the placeholder).
- **Numbers** are range-checked: index numbers 0..100,000 else null; year 1800..2200 else null; rating 0..10 else null; runtime, position, counts and percentages must be in range else null (position and play count 0). Ticks become milliseconds with `Ticks`.
- **Dates** (`premiereDate`, `lastPlayed`) parse leniently; an unparseable date is null.
- **Image tags** must match `[A-Za-z0-9]{1,64}` else null (they become cache keys and query values).
- **Element-level tolerance:** list containers keep each element (and an item's `UserData`, and the total) as a raw `JsonElement` and decode them one at a time, so one element of the wrong JSON type (a number for a name, a fractional index, an id that is not a string, an integer beyond Long, a bare string or null in the array) is skipped and never costs the page; an unreadable `UserData` leaves the item with `userData = null`. A numeric string such as `"2020"` is accepted by the decoder and still range-checked. A single `item()` that cannot be read is `SERVER_ERROR`.
- **De-duplication:** in every list (items and views) the first occurrence of an id wins (ids compared after normalisation), because ids become Room keys and `LazyColumn` keys; a duplicate does not use up the limit.
- **Self-links and watched state:** an item that is its own `parentId`, `seriesId` or `seasonId` has that link nulled; a watched item has `positionMs = 0` and no `playedPercentage`.
- **Ordering:** `children` sort keys are sent as above. `episodes` (season, episode number with missing last, sort name, id) and `seasons` are sorted in the gateway, so the app never depends on the server's order. Both use one season rule (`Ordering.kt`): numbered seasons first, then anything with no season number, then season 0 (Specials) genuinely last. The reference's `sortBy` on the episodes endpoint accepts a single value only, so none is sent.
- **Long series:** `episodes` pages with `startIndex`/`limit=500` until the server's own usable count is reached (an empty page ends it; with no usable count, a short page does), at most 10,000 items and 50 requests. `/Shows/{id}/Seasons` has no paging parameters, so seasons are one request (capped at 1,000).
- **Sizes:** lists are capped at the requested limit (views at 100) even if the server sends more; `Page.total` is at most 1,000,000. **A nonsense total is no total:** a `TotalRecordCount` that is negative, zero while elements came back, or smaller than the elements already seen (`startIndex` plus what this response held) is ignored, so `Page.total` is `null` (unknown) and the episodes loop does not stop early on it. **Paging by what the server consumed:** `Page.items` holds only the kept elements (malformed ones are skipped, repeats removed), so a caller must not advance by `items.size`. `Page.nextStartIndex` is `startIndex` plus every element the server sent, and `Page.endReached` is true when the server sent nothing, or the usable total is reached, or (no usable total) it sent fewer than the limit. An all-skipped page is therefore not the end.
- **Unproven until a real server:** the mutations send no `datePlayed`, so a retried mark-as-watched should not count a second play; and comma-delimited `sortBy`/`sortOrder` pairing per key. Both to be confirmed against a real Jellyfin 12.x server.
- Libraries whose collection type is not films, TV, collections or mixed (music, books, photos, live TV, playlists, home videos...) are skipped.

## Data model (servers and accounts)

- **Tables:** `servers` (id, name, version, home/away address strings, allowCleartext, pinnedSpkiSha256, clientCertAlias, customHeaders BLOB), `accounts` (PK serverId+userId, userName, accessToken BLOB), `active_account` (single row, `slot = 0`).
- **Ids:** server and user ids are GUIDs from the server, validated and normalised at the gateway (`JellyfinId`: 32 hex digits, dashes optional, stored lower-case without dashes); anything else is `SERVER_UNSUPPORTED` (public info) or `SERVER_ERROR` (sign-in). So the same server cannot become two rows, comparisons are plain equality, and an id is safe as a route segment or (Milestone 4) part of a file name. Server name and user name are capped at 80 characters, the version at 40, with control characters and every Unicode format character (category Cf: bidi, zero-width, soft hyphen, tags, ...) removed; a name left empty becomes a fixed default ("Jellyfin" for a server, "Unnamed user" for a user). The Quick Connect code is shown on screen, so the gateway accepts only 4 to 12 ASCII letters or digits and treats anything else as `SERVER_ERROR`.
- **Secrets at rest:** access tokens and custom headers are stored only as `SecretBox` ciphertext in BLOB columns (tests assert the raw bytes contain neither). The account lists, the active-account flow and `active()` wait for the first `warmTokens()` (the cold-start gate) and show only accounts whose token is loaded (`ServerStore.usable` mirrors the token map's keys), so what is listed always agrees with what could send a request. An account whose token cannot be decrypted (lost Keystore key), or that a failed warm never loaded, is hidden everywhere, consistently, until the user signs in again or a retry succeeds (`WarmGateTest`); unreadable headers load as none.
- **Keystore off the main thread, and only when needed (I7):** what screens read (`ServerSummary` lists, `AccountSummary` lists, the active account, "is anyone signed in") selects only non-secret columns (`ServerRow`, `AccountRow`) and never calls `SecretBox`. Every seal and open (warm, saving an account or server, the revocation reads `token`/`tokens`, full server reads for the selector and the settings screen) runs on the store's injected IO dispatcher (`TokenFreeReadsTest`). Opened custom headers are memoised in a small bounded in-memory map keyed by a SHA-256 of the sealed bytes (never the plaintext): the row is still read on every `server()` call, a changed header is a different ciphertext so the memo cannot go stale, an unreadable blob is never remembered, and the map is emptied when a server is saved or removed (`HeaderMemoTest`).
- **Integrity:** accounts cascade-delete with their server; `active_account` cascades from the account, so removing the active account (or its server) leaves nobody active, and the single-row key means there can never be two. Writes use `@Upsert`, never `REPLACE` (REPLACE deletes first and would cascade away accounts). No destructive-migration fallback; the schema is exported to `app/schemas/`.
- **Id guard:** `upsertServer` and `upsertAccount` `require` every id they are given to equal its `JellyfinId`-normalised form (fixed message, never echoing the id), so nothing but the gateway's normalised GUIDs can become a key. Tests make valid ids with `testId(label)` (`TestIds.kt`).
- **Pins:** `upsertServer` rejects a malformed pin (`IllegalArgumentException`, fixed message). A damaged pin already in the database loads as `pinnedSpkiSha256 = null` with `Server.pinInvalid = true`; `ServerNet` then throws `TLS_UNTRUSTED`, so the next connection prompts for re-trust rather than silently falling back to system trust. Saving other edits to such a server keeps the damaged column untouched. Re-trusting a changed certificate pins it only after the address answers, with the new pin, as the same server.
- **One place for security settings:** `ServerNet.anonymous(addresses, draft-or-Server, device)` and `ServerNet.authenticated(addresses, server, userId, device, tokens)` are the only code that turns a server's settings into a `ServerNetConfig`.
- **Device identity:** random UUID generated once, kept in private SharedPreferences (excluded from backup); client name `Shoalwatch`, version from `BuildConfig.VERSION_NAME`, device name from `Build.MODEL` sanitised.

## Library cache (Room v2)

The on-phone copy of what the server told us, and the only thing browsing screens read (SPEC section 4, rule 1: the network writes, screens observe Room, so offline browsing is just "what is in these tables"). Package `data/db/library`.

**Scoping: why items are per server and user data per user.** Two profiles signed in to the same server share the same `items` rows (and, in Milestone 4, the same downloaded file: SPEC 3.3), while each keeps its own watched state, resume position, favourites, libraries and home rows. So item metadata is keyed by `(serverId, itemId)` and everything a user does or sees is keyed by `(serverId, userId, ...)`. The same item id on two servers is two rows.

| Table | Primary key | Foreign key (ON DELETE CASCADE) | Extra indices | Holds |
|---|---|---|---|---|
| `items` | `serverId, itemId` | `serverId` to `servers.id` | `(serverId, parentId)`; `(serverId, seriesId, seasonId, parentIndexNumber, indexNumber)` | everything the `Item` model carries, plus `nameKey` (the folded name, for offline search), `fetchedAt`, `pinned` (default 0, reserved for downloads) |
| `user_data` | `serverId, userId, itemId` | `(serverId, userId)` to `accounts` | `(serverId, itemId)` | played, positionMs, playedPercentage, playCount, favourite, lastPlayed, unplayedItemCount, `updatedAt` (last local write), `pendingSyncAt` (non-null: a local change the server has not confirmed) |
| `views` | `serverId, userId, viewId` | `(serverId, userId)` to `accounts` | none | a user's libraries, in server order (`position`) |
| `list_entries` | `serverId, userId, listKey, position` | `(serverId, userId)` to `accounts` | `(serverId, itemId)` | ordered membership only: `itemId` at `position` |
| `visible_items` | `serverId, userId, itemId` | `(serverId, userId)` to `accounts` | `(serverId, itemId)` | `seenAt`: "the server showed this user this item" (see "Visibility") |
| `list_state` | `serverId, userId, listKey` | `(serverId, userId)` to `accounts` | none | `total` (server's count; null when it gave no usable one), `loadedCount`, `nextStartIndex`, `pagesLoaded`, `endReached`, `refreshedAt` |

- **Visibility (safeguarding, a design rule).** Item rows are shared per server, but the app shows a user only items THE SERVER HAS SHOWN THAT USER: a restricted profile (a child) must never see a title another profile on the same server cached. `visible_items` records it, written inside the same `LibraryStore` transaction as every server-sourced item write for the session (list pages, a single-item fetch, search results; views are not items), and recording only what was returned (the series of a returned episode is not inferred); `seenAt` is refreshed by every such write. A user is shown only items the server has returned to that user on this device, re-confirmed within the last 30 days (or downloaded, or in one of their current lists). An item the server later refuses for that user is hidden from them at once. Every read that returns an item for a user joins to it: list reads, `observeItem`/`getItem`, `observeEpisodes`/`getEpisodes`, and `searchByName`; an item the user was not shown is treated exactly as absent. The only unfiltered reads are `ItemDao.getItemEntity` and `countItems`, which are `internal` and exist for the store and tests. **Revocation:** when a single-item refresh for a session fails with `SERVER_NOT_FOUND` or `FORBIDDEN`, `LibraryStore.revokeVisibility` deletes THAT user's record and removes the item from each of that user's lists (`removeEntry`, so no gap), in one transaction through the write gate; the shared row and other users' records stay, and a later server return makes it visible again. **Expiry:** maintenance deletes records whose `seenAt` is older than 30 days unless the item is pinned or is in one of that same user's current lists. Eviction also deletes the record of items it deletes and keeps it for pinned items: Milestone 4's shared downloads rely on this record as the "allowed to see" check. Account removal cascades it; signing in again keeps the account and so the record. `LibraryVisibilityTest`, `LibraryRepositoryRevocationTest` and `LibraryRepositoryItemSearchTest` cover it.
- **No foreign key from `user_data` or `list_entries` to `items`**, on purpose: user data and lists can arrive before their item row or outlive it, and watched state must survive eviction of metadata (it is needed by sync in a later milestone). Maintenance removes orphans instead.
- **Cascades:** removing an account deletes that user's `user_data`, `views`, `list_entries`, `list_state` and `visible_items` and leaves `items`; removing a server deletes everything for it. Both are tested through the real `ServerStore.removeAccount` and `removeServer`. Room keeps `PRAGMA foreign_keys` on; writes are `@Upsert` or explicit upserts, never `REPLACE` (it deletes first and would cascade).
- **Times** are epoch milliseconds (`INTEGER`); `kind` is the `ItemKind` name (`TEXT`, via `ItemKindConverter`; a name this version does not know reads as `OTHER`); view kinds are `LibraryKind` names (unknown reads as `MIXED`).
- **Ids** are the gateway's normalised `JellyfinId` strings; the cache stores what it is given and never builds a request from it.

**The list model.** A list is `list_entries` (membership and order, no item data) plus `list_state`. `ListDao.entryIds` returns a list's ids in order without the join (for de-duplicating the next page). `ListDao.observeList/getList(serverId, userId, listKey, limit)` is `list_entries` JOIN `items` LEFT JOIN `user_data` (that user's), `ORDER BY position LIMIT n`; an entry whose item row is missing, or that the server never showed this user (see "Visibility"), is simply not returned. A list key is an opaque caller-supplied string of 1 to 200 characters (`resume`, `nextUp`, `latest:<viewId>`, `children:<parentId>:<kinds>:<sort>:<filter>`, `seasons:<seriesId>`, `episodes:<seriesId>:<seasonId|all>`; search results are not cached). Positions are contiguous from 0. `ItemDao.observeEpisodes/getEpisodes(serverId, userId, seriesId, seasonId?)` reads episodes straight from `items` (season number, episode number, missing numbers last, then sort name and id), so a series shows whatever is stored even if no list names it. `ItemDao.searchByName` is case-insensitive in every script (SQLite's `LIKE` and `lower()` only fold ASCII, so the lower-cased `nameKey` column is compared instead) and treats `%`, `_` and `\` in the query literally.

**Writing a page** (`LibraryStore.writePage(session, listKey, start, page, total, now)`) is one transaction: upsert the items; upsert the user data of the items that came with some (an item with none leaves stored user data untouched); delete the list's entries from `start` on (`start == 0` replaces the whole list) and insert the page at `start`; write `list_state` (`total`, if known, raised to at least `loadedCount`; plus the paging state `nextStartIndex`, `pagesLoaded`, `endReached`, which default to "read in one go"). `nextStartIndex` is the server index to continue from and is NOT `loadedCount`: the gateway drops unusable elements, so fewer rows are stored than the server sent. A `start` past the end of what is stored (or a state that is no longer the one the caller read) is reported as `PageResult.Stale` and nothing is written; an empty or over-long key is refused. Any failure rolls everything back. `LibraryStore.writeItems` is the same without a list (detail fetches); `replaceViews` makes a user's views exactly the given list in one transaction.

**Upsert rules for items** (`ItemDao.upsertItems`, read and write in one transaction): `pinned` is never touched; **`overview` keeps the stored value when the incoming one is null**, because the list endpoints do not ask for it (`fields=Overview` only on episodes; the detail call returns it); **`childCount` is always taken as sent, null included (null means unknown and the UI shows no badge)**, because Jellyfin's count is per user while the row is shared, so a kept value could be another user's number; every other column takes the incoming value, null included (an image that was removed stays removed). `fetchedAt` is the time of the write. `user_data.updatedAt` is when that row was last written on this device. The targeted updates `setPlayed`, `setFavourite` and `setPosition` create the row if missing (`INSERT OR IGNORE`, then `UPDATE`, in one transaction).

**Maintenance** (`LibraryStore.evict(now, EvictionPolicy)`, one transaction per server, defaults 30 days and 20,000 unpinned items): (1) delete `list_entries` and `list_state` of lists not refreshed since the cutoff; (2) delete unprotected items fetched before the item cutoff; (3) if the server still has more unpinned items than the cap, delete the oldest-fetched unprotected ones; (1b) delete `visible_items` records not re-confirmed within the item cutoff unless pinned or in that user's current lists; (4) delete `user_data` whose item no longer exists, except rows that are `played`, `favourite`, have a resume position or hold an unsynced change; (5) delete the `visible_items` record of items that no longer exist (a pinned item still exists, so its record stays). **Protected** (never deleted): pinned items, items named by any list entry on that server (any user), and the `seriesId`, `seasonId` and `parentId` of such items, so a pinned or listed episode keeps its season and series. The cap can only be exceeded by protected rows.

**Migration 1 to 2** (`Migration1To2`, explicit; there is no destructive fallback). Version 2 has not shipped, so the paging columns of `list_state` were added to the v2 schema and to this migration in place (and `2.json` regenerated), not as a version 3: `MigrationTest` compares a migrated database with a fresh one, so the hand-copied SQL cannot drift from the entity. Creates the six tables (`items`, `user_data`, `views`, `list_entries`, `list_state`, `visible_items`) and five indices with Room's own generated SQL, copied from `app/schemas/app.shoalwatch.data.db.AppDatabase/2.json` (Room validates the migrated database against that file when it opens, and a difference crashes the app). Servers, accounts and sealed tokens are not touched. `MigrationTest` builds a real v1 database from `1.json`, opens it through Room with the migration, checks the sealed token bytes are identical, the new tables work and cascades fire, and that a migrated and a fresh database have identical `sqlite_master` SQL. **Changing an entity means a new schema version and a new migration, with the same test.**

**No SQL newer than SQLite 3.22.** `minSdk` is 29 and Android 10 ships SQLite 3.22, while Robolectric and Room's own query verifier use a newer one, so a statement that needs a later SQLite passes every unit test and fails on an Android 10 phone. So: no SQL UPSERT (`INSERT ... ON CONFLICT ... DO UPDATE/NOTHING`, 3.24), no `RETURNING`, window functions, `UPDATE ... FROM`, `RENAME/DROP COLUMN`, generated columns, `STRICT`, `->`/`->>`, `IIF`, `MATERIALIZED` and the like. Create-or-update is `INSERT OR IGNORE` plus `UPDATE` in one `@Transaction` (Room's `@Upsert` is fine: it is an insert then an update, not SQL UPSERT). `SqlCompatibilityTest` scans every SQL string in the Kotlin sources and the exported schema for these and names the file and line; `LibraryCacheOnDeviceTest` (androidTest) runs every statement shape on a real device's SQLite.

**Pending local changes (`user_data.pendingSyncAt`).** SPEC 3.2: a watched mark is never undone by a sync. A non-null `pendingSyncAt` means "this row holds a local change the server has not confirmed". The ONE function that stores server-provided user data, `ItemDao.writeServerUserData` (reached only through `LibraryStore.writePage`/`writeItems`; the raw upserts are not callable from outside), ignores a server row for any (server, user, item) whose stored row is pending; every other row is replaced as before and is never itself pending. `ItemDao.setPlayed/setFavourite/setPosition(..., pending)` set the local value and the marker in one transaction (without `pending` an existing marker is left alone); `LibraryStore.markPending`, `clearPending` (keeps the local value) and `deleteUserData` (rolls back an optimistic action on a row that did not exist) are the rest. Eviction never deletes a pending row. The Milestone 5 playstate outbox builds on this marker; `ListCache` has no reconcile hook any more.

**Changing one list entry.** `LibraryStore.removeEntry(session, listKey, itemId)` deletes every occurrence of the item, moves later entries down (the tail is rewritten after the removed position, so the key is never violated), lowers `loadedCount` and a known `total` (never below `loadedCount`) and leaves `nextStartIndex`, which is a position on the server. `insertEntryAt(session, listKey, position, itemId)` is its undo (later entries move up; the list must exist and `position` be within its length). Each is one transaction. `writePage` checks that the stored positions really are contiguous (`MAX(position) + 1 == COUNT`, re-packing if not) instead of trusting the count, and returns `PageResult.Written` or `PageResult.Stale`: **Stale** (nothing written at all) when the page starts beyond the stored entries, or when the caller passed `basedOn`, the list state it read before fetching, and the stored state has since changed (a refresh replaced the list while the page was on its way). The repository drops a stale page. A negative start or a bad list key is still an `IllegalArgumentException` (a programming error).

**Authoritative item writes.** List endpoints do not request `Overview` (and only some request `ChildCount`), so a list write keeps a stored `overview` when the incoming one is null (`childCount` is always as sent, see the upsert rules). A detail fetch does request it, so `writeItems(..., authoritative = true)` (the repository's single-item refresh) writes nulls as nulls and an overview the server has removed is cleared. `pinned` is never touched by either.

**Search folding.** `nameKey` is the name with accents and other combining marks removed (NFD, then `\p{M}` stripped), Turkish dotted and dotless I both read as `i`, then lower-cased with `Locale.ROOT`; the same function is applied to the query, and `nameKey` is rewritten on every upsert (so changing the function needs no migration). "elite" finds "Élite", "istanbul" finds "İstanbul", "angstrom" finds "Ångström". A search with no kinds covers every row, including one whose stored kind this version does not know.

**Maintenance protects one level of links:** the `seriesId`, `seasonId` and `parentId` of a pinned or listed item, not the parents of those parents (an episode carries both its season and its series, so that is enough for the item kinds in use). **`pinned` will have a single writer**, the downloads feature in Milestone 4; nothing in the cache writes it, and every item write preserves it.

**Episode order** in `ItemDao.getEpisodes/observeEpisodes` is the gateway's (`Ordering.kt`): numbered seasons, then no season number, then season 0 (Specials) last of all; then episode number (missing last), sort name (or name), id. `LibraryOrderAndJoinTest` compares the two on the same shuffled data. User data is `LEFT JOIN`ed with the user condition in the `ON` clause, so another user's data can never decide whether a row is returned (mutation-checked).

**Query plans** are asserted in `LibraryPerformanceTest` (5,000 items and entries, a 200-row page): the list query is four index searches (`list_entries`, `items`, `visible_items`, `user_data`) with no sort and no scan of `items`; the episodes query searches `items` by the `(serverId, seriesId, ...)` index. Offline name search is the one query that scans a server's items (a leading wildcard cannot use an index); the cap on stored items bounds it.

## Library repository (`LibraryRepository`)

`data/library/Library` is the only thing browsing screens use (home, listings, series, item detail, search, pull-to-refresh); `LibraryRepository` implements it on `LibraryGateway` and Room. It exposes only models from `data/library` (no DTOs, entities, `ServerApi` or HTTP types) and no flow throws because of the network: a failed refresh is `Freshness.Stale(kind)`. `AppGraph.library` is the lazy instance. Every read and write is for a `Session(serverId, userId)`: item rows are shared per server, user data and lists per user, so switching user shows that user's lists and watched state at once and never the other's.

**Cache first, refresh behind.** Collecting a flow emits what Room holds at once (even if empty), then starts a refresh in the background if the list was never loaded or is older than its window. Collecting never waits for the network. Screens only observe Room; the network only writes to it (`ListCache`). Refreshes run in the repository's own scope (the app scope), so one that has begun is written to Room even if its collector leaves.

| List | Window | Saved as |
|---|---|---|
| home rows: libraries (`views`), `resume`, `nextUp`, `latest:<viewId>` | 2 min | limits 24, 24, 16 per library |
| `children:<parentId>:<kinds>:<sort>:<filter>` (a library or folder) | 15 min | pages of 100 |
| `seasons:<seriesId>`, `episodes:<seriesId>:<seasonId or all>`, the series item | 10 min | whole lists |
| `item:<itemId>` (detail) | 5 min | one item, no entries |

**List keys** (`ListKey`, the only place they are built): opaque strings of at most 200 characters in `list_entries.listKey` and `list_state.listKey`. Ids are normalised 32-digit ids, so `:` is a safe separator; `kinds` is `ListShape.key` (`movie_r`, `series_r`, `box_set_r`, `any_d`...). `views` and `item:<id>` hold state only (a `list_state` row with no entries) because that row's `refreshedAt` is how current they are. `ListKeyTest` checks distinct inputs give distinct keys, within the limit.

**Freshness** (`Fresh`, `Refreshing`, `Stale(kind)`) is the in-memory outcome of the last attempt per (session, list key) combined with the Room flows. Idle with a saved state is `Fresh`; a running refresh or load is `Refreshing`; a failure is `Stale(kind)` (`OFFLINE`, `NETWORK`, `TIMEOUT`, `SERVER_ERROR`, `SERVER_NOT_FOUND`, TLS kinds, and `UNAUTHORISED` / `NOT_SIGNED_IN` so the screen can offer sign-in; nothing is deleted). A never-loaded list that fails is empty and `Stale`; nothing saved with nothing running (the work vanished) is `Stale(UNKNOWN)`, never a spinner that no one will stop (the cold start is `Refreshing` because the first refresh is started before the first emission). `Home.viewsFreshness` reports the libraries list the same way, so a failed libraries refresh is visible while the saved libraries stay. After a restart nothing is in memory, so staleness is recomputed from `list_state.refreshedAt`. A brief `Fresh` with the old rows can show between a write committing and Room re-emitting; a state that says "loaded" beside no rows is treated as still arriving.

**One refresh per list.** `Refresher` keeps at most one piece of work per (session, list key): concurrent collectors and an explicit `refresh()` join the one in flight; `loadMore` is declined while anything is running for the list; a refresh asked during a `loadMore` waits for it, then runs (a refresh replaces the list, so they must not overlap). At most 4 requests run at once across all lists, so home rows load in parallel without flooding the server, and a failing row does not blank the others. No retries here: `ServerApi` already retries a lost connection once, and callers must not add their own.

**Paging.** Page size 100; `loadMore` continues from the stored `nextStartIndex` (the server index the last page ended at, so skipped or repeated elements cannot cause a re-fetch), never stops because a page kept nothing, and stops only on `endReached`. An id already in the list keeps its first position. The hard ceiling is 200 pages per list; `canLoadMore` is "not end reached and under the ceiling". A failed `loadMore` leaves the list as it was and sets `Stale(kind)`. **A refresh replaces the list with page 0 in one transaction** (so items removed on the server disappear) and resets the paging state: anything beyond the first page is dropped and loaded again by scrolling. `Listing.items` can be empty while `canLoadMore` is true (a page whose elements were all unusable).

**What a listing asks for** (`ListShape.forLibrary`): films library `{MOVIE}` recursive, TV `{SERIES}` recursive, collections `{BOX_SET}` recursive, mixed and folders the direct children of any kind (`ListShape.DIRECT`).

**Series.** `series(session, seriesId, seasonId?)` gives the series, its seasons and the episodes of the selected season, each with its own list key and refresh; `freshness` is Refreshing if any part is, else the first failure, else Fresh. With no `seasonId` the season is the one holding the next unwatched episode when the saved episodes show it (Specials never decide), else the first numbered season, else Specials. The choice is sticky while the screen is open, so marking an episode watched does not jump seasons. No episodes are fetched until a season is known.

**Item detail** emits the saved row at once (it may lack the overview if it was only seen in a list), then refreshes the single item. `ItemDetail.item` is null until the item is saved for this user (see its `freshness`). When the server answers `SERVER_NOT_FOUND` or `FORBIDDEN` for the item, it is revoked for this user: the flow emits `ItemDetail(item = null, freshness = Stale(SERVER_NOT_FOUND))`, i.e. THE ITEM DISAPPEARS for this user (it is also taken out of their lists); the screen should say it is no longer available. Other users are unaffected. **Search** online asks the server and saves the results as items (not as a list) so detail screens open instantly; if that fails as `OFFLINE`, `NETWORK` or `TIMEOUT` it searches the saved names (case-insensitively) and returns `SearchResult(offline = true)`. Any other failure is thrown as an `AppError`. A blank term sends nothing. A local failure (a raw database exception) in `loadMore`, `search` or `refresh` is thrown as `AppError(UNKNOWN)`, never as a raw exception.

**User data precedence.** Everything the server sends is saved through one function, `ItemDao.writeServerUserData` (via `LibraryStore`): the server's copy overwrites the cached one unless the stored row has `pendingSyncAt` set, in which case the local change wins (see "Library cache"). Milestone 5's playstate outbox sets and clears that marker. (There is no precedence hook in the repository any more: this one function in the store transaction is the place.)

**Eviction** (`LibraryMaintenance`): `LibraryStore.evict` with the default policy (lists not refreshed for 30 days, unreferenced unpinned items older than 30 days, at most 20,000 unpinned items per server), at most once every 24 hours for all servers together (so no server more often; a recorded run in the future, from a clock that went back, counts as due). The last run is kept in memory and in a private preferences file (`PrefsMaintenanceLog`, one number). It starts the first time the library is used each day, off the main thread, and takes the same write lock as every list write, one server at a time, so it never overlaps a refresh write and never holds one back for long; a failure is not recorded and is tried again. After a clear-out the refresher forgets its "finished" records, so a live list whose saved state was just removed reads `Stale(UNKNOWN)` (the next collection refreshes it) rather than spinning.

**Failures, retries and malformed ids.** After a refresh fails, a new collection of the same list does not start another refresh for 30 seconds (injected clock), so a screen that is reopened again and again cannot become a request storm; pull-to-refresh (`refresh()`) always tries. The remembered failures are per (session, list), dropped when the account is removed, signed out or signed in again (`ServerStore` tells the repository: `onAccountGone`, `onAccountSignedIn`, so a list never keeps showing `Stale(UNAUTHORISED)` after a fresh sign-in) (`ServerStore` tells the repository) or the server is removed, cleared by the next success, and capped at 500 entries (oldest dropped). Anything a refresh throws, including a non-`AppError` from the store, ends as `Stale(UNKNOWN)`; a refresh never stays `Refreshing`. A malformed id (a navigation argument, saved state) never throws from the seam: a flow emits one empty result with `Stale(SERVER_NOT_FOUND)` and sends nothing, `loadMore` and `refresh` do nothing.

**Guidance for screens.** Pass a `Session` into every call and restart the flow when the account changes. Do not refresh on every resume: collecting already refreshes what is due. `Listing.items` can be empty while `canLoadMore` is true, so load more rather than show "empty"; call `loadMore` again when freshness returns to `Fresh` while the end of the list is still on screen. Never read the DAOs or `LibraryStore` from UI code.

**Threading.** All Room and network work runs on the injected IO dispatcher, including `refresh`, `loadMore` and `search` whatever the caller's dispatcher (`withContext(io)`); flows are safe to collect on the main thread; there is no `runBlocking`. Tests (`LibraryRepository*Test`) use a fake `LibraryGateway` (programmable answers, call log, a gate to hold calls, forced failures), a real in-memory Room under Robolectric, and an injected clock for time.

## Tidy-up actions (`Playstate`)

`data/library/Playstate` is what screens call to take an item off Continue Watching, mark it watched or unwatched, or favourite it; `PlaystateRepository` implements it (`AppGraph.playstate`, lazy). Screens observe Room, so an action is "change Room, then tell the server" and the screen updates at once. Each function returns normally only when the server accepted the change, and otherwise throws an `AppError` (the gateway's own, unchanged, whatever its kind) after putting everything back.

**The five steps** (the same for every action):
1. **Snapshot** what will change (`Touched`): the `user_data` row of every item set as a whole (or its absence), the amount each season/series badge is moved by, and the position of every `resume` entry about to go, each recorded as the list stood when that entry was taken out.
2. **Change Room** in ONE transaction under the library write gate (`LibraryRepository.writeGated`, the lock every list write and eviction takes, so an action never interleaves with a page write), setting `pendingSyncAt` on every row it writes. The item must be one this user was shown (the visibility join); otherwise, and for a malformed id, `AppError(SERVER_NOT_FOUND)` with nothing changed or sent.
3. **Call the server**, exactly once. No retry loop here (the three mutations already opt in to `ServerApi`'s single retry).
4. **On success:** under the gate, in one transaction: stamp every row and removed list entry the action touched as changed AGAIN (the confirmation is a change too: a request sent while the server call was in flight, after the optimistic write, but answered from the server's old state, is older than this moment and cannot overwrite the result), then clear the markers (if that fails the action still succeeds: rows are cleared one by one, and the user's queue clears any leftover when it goes idle, or the start-up sweep does at the next start). Then start a refresh of each list the server recomputes (`LibraryRepository.refreshInBackground`), without waiting for it. A refresh already running for that list is not joined, because it may have been asked for before the change: a new one is queued behind it, and queued ones are COALESCED (a queued one that has not yet read its request stamp is joined by later actions, since its stamp will be newer than every change so far; only one that has started gets another behind it). So twenty actions while a `resume` refresh is stuck cost at most two further `resume` requests. The refresh a later action starts is stamped after this confirmation and applies normally.
5. **On failure:** restore the snapshot EXACTLY under the gate (a row that did not exist is deleted with `deleteUserData`; the others are written back through `ItemDao.restoreUserData` as they were, WITHOUT a marker: a restore never writes one; a badge is moved back by what this action moved it by, on whatever the row holds now; removed entries go back with `insertEntryAt` in REVERSE order of removal, so each lands at its recorded position (a position past the end of the list now goes to the end), unless a refresh has already put the item back (then it is left) or the server has since stopped showing the item to this user), then throw. If the restore itself throws, every marker is cleared one row at a time and the lists are refreshed (plus the item), so the cache reconverges with the server; the original error is still the one thrown.

**The pending marker is what makes the sequence safe.** `ItemDao.writeServerUserData` ignores a server row for a pending row, so a list refresh that lands during step 3 cannot revert the optimistic state (SPEC 3.2: a watched mark is never undone by a sync). It is also the Milestone 5 hook: **Milestone 5 replaces step 3 with a durable outbox behind this same interface. On failure it will keep the local change and its marker and queue the call instead of rolling back.** Until then actions are online only: offline is a rolled-back failure whose `AppError` the screen shows.

**What each action changes locally, and what it refreshes afterwards**

| Action | Local change (all rows pending) | Refreshed after success |
|---|---|---|
| `removeFromContinueWatching` | `positionMs = 0`, `playedPercentage = null`, `played` untouched; entry removed from `resume` (not `nextUp`: the server's Next Up is unaffected) | `resume` |
| `setPlayed`, film or other kind | the store's `setPlayed`: watched is `played`, position 0, no percentage, `playCount = max(playCount, 1)`, `lastPlayed = now`; unwatched is `played = false`, position 0, `playCount = 0`, `lastPlayed` kept. Out of `resume` either way (position 0) | `resume`, `nextUp` |
| `setPlayed`, episode | as a film, and the cached `unplayedItemCount` of its season and series rows moves by one (down when marked watched, up when unwatched; never below 0; only where the row has a count; not at all if the episode was already in that state) | `resume`, `nextUp` |
| `setPlayed`, season | the season row as a film, with `unplayedItemCount = 0` (watched) or null (unwatched: the server's count is not guessed from a partly saved list); every saved episode of that season this user was shown the same way; those episodes out of `resume`. Episodes that are not saved get no row | `resume`, `nextUp`, `seasons:<series>`, `episodes:<series>:<season>`, the series item (its badge) |
| `setPlayed`, series | the series row, every season in the saved `seasons:<series>` list, and every saved episode, as above | `resume`, `nextUp`, the series item, `seasons:<series>`, `episodes:` of every season seen |
| `setFavourite` | `favourite` only; no list is edited | nothing. A list filtered by favourites (`children:...:fav...`) shows the change after its next refresh; the screen can ask for one with `Library.refresh` |

**One action at a time per user:** sibling episodes share the season and series badge rows, and a season or series action touches many items, so actions queue per `Session` in the order the calls were made (the queue slot is taken synchronously in the caller), and each starts from the previous one's finished state (markers cleared, or rolled back). A queued action waits for the first one's WHOLE sequence: its change, its server call, and its clear or rollback (not for any refresh). Another user's actions do not wait. When a user's queue goes idle (the last action has finished, nothing queued behind it), any marker still set on that user's rows is cleared: nothing else sets markers in this milestone, so none can be live. The price of the queue: a second tap's optimistic change shows only when the first action has finished, which is its server round trip (one request; offline, `ServerApi` fails at once without sending; at worst the 10 s connect and 30 s read timeouts) plus a few local writes. Milestone 5's outbox will make every tap instant (see the to-do).

**Not abandoned:** steps 2 to 5 run in the app scope and the caller awaits them (`CompletableDeferred`): a screen cancelled after the change stops waiting and the action still finishes, so a screen that went away leaves no marker behind. Rollback and clean-up run non-cancellable, so an app scope that shuts down mid-call still puts the rows back. **The true guarantee, and the residual cases:** every marker an action sets is cleared by that action on every path it controls. Two cases can leave one: the app scope itself being cancelled after the optimistic write committed and before the server answered (the rollback then runs, but the work is cut short around it), and a clear that fails (a database fault). Both are cleaned up when that user's queue next goes idle, or at the latest by the start-up sweep at the next start. An action started on a scope that is already dead ends with a cancellation and has changed nothing.

**The rule: a server answer never overwrites user data for an item that was changed locally after that answer was asked for. Ordering is by a sequence number, never by time.** `LocalChangeLog` (one instance, made in `AppGraph`, required by `LibraryStore` and `LibraryRepository`) holds a process-wide counter. Every local change (optimistic write, confirmation, rollback, badge change) takes the next number and is noted per (server, user, item), with the lists an action took the item out of. Every request reads the current number (`LibraryStore.requestStamp()`) immediately BEFORE its gateway call and passes it, as the REQUIRED `requestedAtSeq` (no default), with its answer to `LibraryStore.writePage` or `writeItems` (list pages, `loadNextPage`, the single-item refresh, search results). An answer is dropped for an item exactly when the item's change number is GREATER than the request's stamp: `writeItems` skips that user's `user_data` row (the shared item row and visibility are still written), and `writePage` leaves the item out of a list an action took it out of, including when it was not in the saved list (the intent is recorded either way). A request stamped at or after the change applies, with no time passing at all; one stamped before is dropped, however the wall clock moves. The wall clock plays no part: setting it back cannot hide fresh answers and setting it forward cannot let stale ones through. This holds for every kind of request, because it is applied where server user data is written; `PlaystateStalenessTest`, `PlaystateStampTest` (every recipe reads its stamp before its call) and `LocalChangeLogTest` cover it. **Expiry and cap:** an entry is forgotten after 10 minutes by a MONOTONIC clock (`SystemClock.elapsedRealtime`, injected as `MonotonicClock`; a request that old would have timed out long since), and at most 5,000 entries are kept, oldest evicted first, which ends protection for an evicted item early (it needs more than 5,000 distinct items changed within 10 minutes). The same monotonic clock spaces the sweep's retries. Freshness windows and the failure cooldown still use the wall clock, which is safe because they only decide when to ask again: a clock set back keeps a list fresh a little longer and the cooldown guard (`0 until` window) treats a negative age as expired. After a rollback the restored value stands against any stale page asked for during the pending window (the page is dropped for that item); the next refresh, asked for after the rollback, heals it. The pending marker still covers the window while the server call is in flight and is the Milestone 5 hook.

**Start-up sweep (`StartupSweep`, owned by `LibraryRepository`).** Nothing but a live action or the queue's idle clean-up clears `pendingSyncAt`, so a marker left by a process killed mid-action would hide the server's copy of that row for as long as it stands (and eviction keeps pending rows). Every entry point waits for the sweep before it reads freshness or writes anything: the list flows (`ListCache.ensure`: home, children, series, item), every refresh and "load more" (`Refresher` work), `search`, and every tidy-up action (`LibraryRepository.writeGated`). It clears exactly a SNAPSHOT of the rows that had a marker when it first managed to look (one query, its first step, taken before any entry point lets an action run), minus any row this process has touched since, and ages the lists only of users who really had a leftover cleared (by an hour: more than the longest window, far less than eviction's 30 days) so the server's copy arrives promptly and decides. If an attempt fails it is logged (the exception type only) and tried again on the next entry-point call at least 30 s later (monotonic clock), at most 5 times in all; the snapshot is kept across attempts, and a retry can therefore never clear the marker of an action that is waiting on the server right now (a failed first attempt does let actions run before the retry; their rows are excluded as touched). Until an attempt succeeds a stuck marker makes that row ignore the server. **In this milestone an unconfirmed change can be reverted by the server's state. Milestone 5 owns recovery.**

**Known limits**
- A refresh asked for before a change is ignored for the changed item's data and cannot put a removed item back into `resume` (tests: `PlaystateStalenessTest`, `PlaystateStampTest`); it still replaces the REST of the list with data from before the change, until the refresh that follows the action (queued behind it, coalesced, one request). Entries are forgotten after 10 minutes and capped at 5,000 (see the rule).
- Process death mid-action drops the unconfirmed change at the next start (the sweep), until Milestone 5. An action's own app scope being cancelled can also leave a marker until the queue next goes idle or the next start.
- Actions are one at a time per user; a queued tap shows after the first action's whole sequence (see above), until Milestone 5's outbox.
- Only the kinds a screen offers are modelled: a box set or folder marked played changes its own row only.

**For Milestone 5 (outbox).** Three marker-clearing paths exist today and all assume that a marker with no live action means DISCARD: the start-up sweep, its retries, and the queue's idle clean-up. With an outbox it will mean SEND, so each must be revisited (replay instead of clear). The local change log is process-local: after a restart nothing is remembered, and the outbox's own records must carry what the log carries now (which items changed, and which lists they left).

**What screens must do:** catch `AppError` from each call and show its `userMessage` (a rolled-back change reverts on screen by itself, because the screen observes Room); a list filtered by favourites needs `Library.refresh` to show a favourite change; an action completes even if the calling screen has gone, so a screen never needs to retry or clean up.

Tests: `PlaystateResumeTest`, `PlaystatePlayedTest`, `PlaystateSeriesTest`, `PlaystateConcurrencyTest`, `PlaystateRestoreTest` (order, shared badges, revoked mid-action), `PlaystateRefreshRaceTest`, `PlaystateStalenessTest` (the rule, ordering, acknowledgement), `PlaystateStampTest`, `PlaystateCoalesceTest`, `PlaystateSweepTest`, `LocalChangeLogTest`, `SourceShapeTest` (no main file over 400 lines or 45% blank) (fake gateway, real in-memory Room through the real `LibraryRepository`, injected clock).

## Artwork (`data/images`, `ui/components/Artwork`)

Posters, backdrops and thumbnails: loaded, bounded and cached so the screens never hold a URL. The UI passes an `ArtworkRef` to the `Artwork` composable and nothing else.

- **`ArtworkRef(session, itemId, type, tag)`** has a private constructor; `ArtworkRef.of` is the only way to make one and returns null unless `itemId` is a normalised `JellyfinId` and `tag` matches `[A-Za-z0-9]{1,64}`. It is a plain class (no `copy`), so an unchecked ref cannot be derived from a valid one, and its `toString` carries no id or tag. `Item.primaryArtwork` / `backdropArtwork` / `thumbArtwork` (extensions in `data/images`, since `data/library` is not edited here) build refs from the item's own tags; an episode with no primary image falls back to its series poster (`seriesId` + `seriesPrimaryTag`).
- **Guidance for screens:** use only `Artwork(ref, ...)` with refs from `Item.primaryArtwork(session)` and friends; never construct a Coil type, loader, request or URL in a screen (`ArtworkBoundaryTest` fails the build on a reference to `ImageLoader`, `AsyncImage`, `ImageRequest` or `coil3` outside the artwork code); do not retain refs across an account change (they carry the session; see "Session check"); a failed picture shows the placeholder and the UI never retries it.
- **Request** (checked against the 12.4.0 reference, `GET /Items/{itemId}/Images/{imageType}`): through `ServerApi.getBytes`, path `/Items/{itemId}/Images/{Primary|Backdrop|Thumb}`, query `tag`, `maxWidth` (the width bucket), `quality=90` and `format=Webp`. Everything else the endpoint offers (`maxHeight`, `width`, `height`, `fillWidth`, `fillHeight`, `blur`, `backgroundColor`, `foregroundLayer`, `imageIndex`, `percentPlayed`, `unplayedCount`) is unused. `format` is `ImageFormat.Webp` (the enum also has Bmp, Gif, Jpg, Png, Svg): WebP decodes on Android 10 and later with no extra library; AVIF is not requested. Real Jellyfin serves images without authentication, but every request goes through `ServerApi` (verified address, token in the header) so that no unauthenticated or unverified request path exists. No retry loop here: `ServerApi` makes its one retry after a lost connection, and a 401 signs the account out locally there; the composable just shows the placeholder.
- **Width buckets** 160, 320, 480, 720, 1280: the smallest bucket at least the width Coil resolved for the composable (clamped to 1280; 480 when the size is undefined).
- **Cache keys** (memory and disk): `art:<serverId>:<itemId>:<TYPE>:<tag>:<bucket>`, built from the validated ref only, so never from an address (switching between the home and away address reuses the cache) and a new `tag` (the server changes it when the picture changes) is a new entry. **The key deliberately has no userId:** the picture of an item is the same bytes for every user, and who may see an item is already decided by the per-user visibility rule: a screen can only build an `ArtworkRef` (which needs a `Session`) for an item the app showed that user, and nothing can build one from raw strings except `ArtworkRef.of`. Two profiles on one server therefore share cached pictures, which costs no privacy the visibility rule does not already give. The memory cache is Coil's default.
- **Session check:** the first interceptor also asks whether the ref's session is still a usable signed-in account (`ServerStore.cachedToken(serverId, userId) != null` after the warm gate: an in-memory, token-free check, no network) before ANY hit, memory or disk, so a signed-out session gets `NOT_SIGNED_IN` and the placeholder, never a saved picture. The saved entries themselves stay for other accounts of the server. Screens must still not keep refs across an account change.
- **Disk cache and clearing:** one Coil `DiskCache` per server (`ArtworkDiskCaches`: folder `cacheDir/artwork/<serverId>`, each capped at 250 MB, so the cap is per server), evictable (pinned artwork for downloads is Milestone 4). Coil's cache cannot list its keys, so a per-server cache is the simplest correct way to clear one server's pictures as a unit. `ArtworkEviction`, called from `AppGraph`'s store notifications, runs off the main thread: on **server removal** it removes the server's memory entries (keys starting `art:<serverId>:`), clears its cache and deletes its folder; on **sign-out** the pictures stay (another account of that server on this phone may still be signed in) unless no usable account remains for the server, which is then treated as removal. Failures are logged by kind only. Coil's own single disk cache is switched off.
- **Hostile-input bounds** (all tested in `ArtworkHostileInputTest`, `ArtworkPixelBudgetTest`; images are the largest volume of untrusted bytes the app handles):
  1. Body at most 8 MiB (`getBytes` enforces it on the declared length and while reading, chunked or not).
  2. `Content-Type` must be `image/jpeg`, `image/png` or `image/webp` (case-insensitive, parameters ignored; `image/jpg` is refused) before the body is read; SVG, GIF, HTML, anything else or missing is refused.
  3. The first bytes must show JPEG (`FF D8 FF`), PNG (signature) or WebP (`RIFF....WEBP`; another RIFF such as WAVE is refused), and the kind they show must EQUAL the kind the header named, else refused with nothing decoded or cached.
  4. The body must be complete **and exact** (JPEG end marker, PNG ends with `IEND`, WebP RIFF length equals the size). A genuine image with trailing bytes after its end is therefore refused and shows the placeholder (the price of reliable truncation detection).
  5. Animated images are refused, not shown as a still: an APNG (an `acTL` chunk before the image data) and an animated WebP (the `VP8X` animation flag). Detection is a few bytes. GIF is refused at steps 2 and 3.
  6. The declared dimensions are read from the header only (`inJustDecodeBounds`, no pixels) and refused above 8192 px a side or 40 megapixels.
  7. Only then is anything written to the disk cache (the editor is aborted on failure), so a refused or failed download leaves no entry. A saved entry gets the same checks, read once, before it is served; a bad one is deleted and fetched again. A snapshot or editor is always closed or ended, even when the caller is cancelled while it is being opened (`ArtworkResilienceTest`).
  8. Decoding (`ArtworkDecoder`, the only decoder) repeats the first-bytes and dimension checks before any pixel is allocated, then uses a power-of-two sample size (`ArtworkLimits.sampleSize`): the width stays under twice the bucket and the decoded bitmap never exceeds **4,000,000 pixels (16 MB at ARGB_8888)**; anything that cannot meet that is refused. At most 2 decodes run at once. A picture that fails to decode is evicted from the cache, so the next request downloads it again.
- **Worst-case transient memory for a full grid.** Decoding: at most 2 decodes x 16 MB = 32 MB (a normal 320-wide poster is about 0.6 MB, so a screenful of about 20 held by Coil's memory cache is roughly 12 MB, an LRU that Coil trims to its percentage of memory). Downloading: a body is held whole while it is checked (the buffered source and the byte array, up to about 16 MB for an 8 MiB body) and OkHttp runs at most 5 requests per host at once, so the pathological ceiling (five hostile 8 MiB bodies) is about 80 MB, plus the decodes; real posters are 20 to 100 KB.
- **Component allowlist.** `ArtworkLoader` builds the one `ImageLoader` (`AppGraph.imageLoader`). The composable takes it from `LocalArtworkLoader`, provided once in `MainActivity` with **no default**: without one, a screen showing a ref fails loudly in debug builds and tests, and shows the placeholder in release (logging a fixed line), so the app can never silently fall back to a default Coil loader. `ShoalwatchApp` also implements `SingletonImageLoader.Factory` with the same loader (belt and braces, proved with the real application class by `ShoalwatchAppImageLoaderTest`). Coil's service-loader discovery is off, and `coil-network-okhttp` (or any Coil network module) is not a dependency, so nothing in the app can fetch a URL. Final component list: interceptor `ArtworkOnlyInterceptor` (first), keyer `ArtworkKeyer`, fetcher `ArtworkFetcher.Factory`, decoder `ArtworkDecoder.Factory`. Coil 3.3.0 always adds its own built-in mappers, keyers and fetchers after those (string and path to Uri, file, content, resource, asset, data, byte array, bitmap, drawable) and its bitmap decoders: they cannot be removed. They are unreachable because `ArtworkOnlyInterceptor` runs first and fails any request whose model is not an `ArtworkRef` (`ModelNotAllowedException`): a `"https://..."` String, an `android.net.Uri`, an `HttpUrl`, a `File`, a path, `file:` / `content:` / `data:` strings and a byte array all fail with no request (`ArtworkLoaderTest`, `ShoalwatchAppImageLoaderTest`). Our decoder is consulted first and always decides.
- **Offline.** Reads go memory, then disk, then network. With a disk hit the picture shows with no request; with none, `ServerApi` fails `OFFLINE` (or a network error) and Coil's error state shows the placeholder: never a crash, never a loop. Cancelling (a list scrolling away) cancels the OkHttp call and leaves nothing cached.
- **Composable.** `Artwork(ref, contentDescription, modifier, aspect, title)` is stateless (no ViewModel). The box is `POSTER` (2:3), `WIDE` (16:9) or `SQUARE` from the first frame (`aspectRatio`, so nothing jumps); the caller sets the width. A rounded brand-tinted block (surface variant, leaning 8% to 29% towards the primary or tertiary container by a pure function of the item id; the letter is at least 3:1 against every tint in both themes, `PlaceholderContrastTest`) with the title's first letter in `headlineMedium` shows while loading, on every failure and when `ref` is null: no broken-image icon and no animation. Once the picture has loaded the block is removed and the picture sits on the theme surface, so a transparent PNG cannot show the letter through. The picture fades in over 150 ms, none when the system "remove animations" setting is on. The request sets `Precision.INEXACT` itself (a request built without it is `EXACT` and would never hit Coil's memory cache for a bitmap of a different size). The letter is not announced; `contentDescription` is exposed as given (null for a decorative picture inside a labelled card).
- **Logging:** a refusal logs its reason (a fixed word) through `AppLog` in debug builds; never a ref, tag, URL or response content. Exceptions carry fixed messages.
- **Deferred (M9)** from "Authenticated requests" still stands: every artwork request reads the full `Server` to build its client configuration, which is now a per-image cost when a grid loads; a settings-version signal from the store would remove it.

Tests: `ArtworkLimitsTest`, `ArtworkRefTest` (plain JVM), `ArtworkFetcherTest` (real `ServerApi`, OkHttp and disk cache against MockWebServer: path and every query parameter, bucket for several sizes, address-independent keys, new tag or bucket is a miss, another signed-in user reuses the entry, offline with and without a saved picture, cancellation, a lost connection), `ArtworkHostileInputTest` (every refusal above), `ArtworkPixelBudgetTest` (total decoded pixels for hostile shapes), `ArtworkResilienceTest` (session check, snapshot leaks, corrupt entries, memory keys), `ArtworkEvictionTest`, `ArtworkLoaderTest` (the allowlist, the component list, the decoder guard), `ShoalwatchAppImageLoaderTest` (the real application class), `ArtworkBoundaryTest` (source scan), `ArtworkPlaceholderTest`, `PlaceholderContrastTest`, `ArtworkRenderTest` (composes at each aspect with and without a ref, keeps its shape, exposes the description, fails loudly with no loader, hides the letter once loaded). ## Jellyfin client decision (SDK vs direct)

**Decision: `JellyfinGateway` is implemented directly on OkHttp + kotlinx.serialization; the Jellyfin Kotlin SDK is not used for any request.**

- AAFin's `JellyfinClients.kt` shows `OkHttpFactory(httpClient)` does accept an injected `OkHttpClient`, so injection is possible. But the SDK builds its own requests and applies its own authorisation and client options (its sources were not audited for this task), and proving that *every* byte of SDK traffic passes our guards and trust policy would need an audit of the SDK internals on each upgrade.
- The sign-in surface is seven small endpoints, so a direct implementation is cheaper than that audit and gives one auditable HTTP path: every call goes through `HttpClientFactory.clientFor(config)`, so the cleartext, header, token and client-certificate guards, the trust policy and the pin all apply.
- Endpoints: `GET /System/Info/Public`, `GET /QuickConnect/Enabled`, `POST /QuickConnect/Initiate`, `GET /QuickConnect/Connect?secret=`, `POST /Users/AuthenticateWithQuickConnect`, `POST /Users/AuthenticateByName`, `POST /Sessions/Logout`. Unauthenticated calls send `Authorization: MediaBrowser Client, Device, DeviceId, Version` without a token (the interceptor applies it from the config).
- **Untrusted responses (S11):** bodies over 1 MiB are refused, JSON is decoded with `ignoreUnknownKeys`, a missing token or user id is an error, ids must be GUIDs, display strings are sanitised. Error text never includes response content.
- **Documented exception to "no secrets in URLs":** the Quick Connect `secret` is sent as a query parameter for the `Connect` poll because the Jellyfin API requires it. It is short-lived, never logged, and the client logs no URLs.
- **No redirects on any call:** credentials sit in bodies and queries that OkHttp would resend on a 307/308, so no factory client follows redirects and any 3xx is an error (`SERVER_NOT_FOUND`).
- **Client holder and eviction:** `ServerClients` (data/servers) holds one client per configuration. `ServerNetConfig` equality is by value (authorities, cleartext flag, pin, client-cert alias, headers, `authKey`) and excludes the token-provider lambda; `authKey` is null for anonymous calls or `serverId:userId`. `ServerStore` reports every account upsert, account removal (in a `finally`), server removal and server upsert (old and new addresses) to `ServerClients.evict`, which drops matching clients and evicts their idle connections from the shared pool (other servers' idle connections may go too; harmless).

### Token rules

- `ServerStore` keeps an in-memory `(serverId, userId) -> token` map (`cachedToken`, suspend-free, no per-request decryption).
- It is **never filled as a side effect of reading rows** (a stale snapshot could resurrect a revoked token). It is written only by `upsertAccount` (new token) and `warmTokens()` (loads all saved accounts once; `AppGraph.tokensWarmed` starts it at app start; safe to repeat).
- **Cold-start gate:** `awaitWarmed()` completes when the first `warmTokens()` has finished, successfully or not; `awaitActive()` is `active()` after it. Anything that needs the active account for an authenticated request goes through them.
- `warmTokens` never throws (except cancellation): a Room or Keystore failure is logged by kind only and leaves the map empty, so requests fail closed as `NOT_SIGNED_IN` while start-up still proceeds.
- `removeAccount` and `removeServer` run in `NonCancellable`, so the token clear and client eviction happen even if the caller is cancelled. All writers share one `Mutex`, and `warmTokens` re-reads the rows inside the lock, so a removal that finished first is simply absent.
- `authenticated` is handed `store::cachedToken`, so a cached client (which keeps the first provider for its key) sends the current token after a re-sign-in.
- **A missing token fails loudly:** an authenticated request whose lookup finds no token is refused before it is sent (`BlockedRequestException` wrapping `NOT_SIGNED_IN`), never sent anonymously.
- **Revocation** reads the account's token explicitly (`ServerStore.token`, on IO) and sends it with `ServerNet.revocation`, the one place a captured token string is allowed. `JellyfinGateway.logout` always runs that configuration through `ServerClients.oneOff`: a client built for that single call by `HttpClientFactory`, never stored in the per-account cache (its key starts `revoke:`, so it could not equal a live `serverId:userId` key anyway, and `ServerClients.clientFor` refuses such a key with a `require`), after which the shared connection pool (one pool for all clients) is trimmed of idle connections in a `finally`. Nothing is put in the token map, a live authenticated client for the same account is neither reused nor touched, and no client holding the revoked token is left behind (`RevocationClientCacheTest`). Then the account is removed.

## Home / away address selection

- `AddressSelector` (data/servers) turns a server's home and away addresses into a live `StateFlow<Connection>` (`Checking` / `Online(address, isHome)` / `Offline`), one probe loop per server id (`connection(serverId)`; `refresh()`; `forget(serverId)`, called by `ServerStore.removeServer`).
- **Settings from the store:** each probe reads the server from its `ServerSettingsSource` (`ServerStore`) when it starts, and the selector watches the store: a change of addresses, pin, cleartext consent, client certificate or headers resets the state to `Checking` at once and re-probes; a server that is no longer saved is `Offline` and is never probed. A store failure on a probe's read publishes `Offline` and the loop carries on. If the store's `servers` flow itself fails, the watcher publishes `Offline` for every live server and drops in-flight results, then resubscribes after a backoff of 1 s doubling to 30 s (reset by a healthy emission); the first emission after a failure re-probes every live server. During the outage a probe started meanwhile (it reads the store directly) can still publish `Online`, and settings changes made during the outage are picked up within the backoff; `AuthRepository` re-reads the store before sending anything, so a stale `Online` cannot send a credential with old settings (`AddressSelectorStoreTest`).
- **Probing is anonymous** (`ServerNet.anonymous`, `publicInfo`): no token reaches an address before it has proved to be the server. An address counts only if its reported id equals `server.id`; a different server there is unreachable.
- **Timing:** home 1.5 s, away 5 s, probed concurrently with coroutine timeouts (a timed-out or no-longer-needed probe cancels its HTTP call). Home answering correctly wins at once; otherwise away is used when it answers; otherwise `Offline`. A missing address is skipped.
- **States:** `Checking(previous: Online?)`, `Online(address, isHome)`, `Offline(reason: AppError.Kind?)`. `reason` is set for security problems the user must act on (`TLS_PIN_CHANGED`, `TLS_UNTRUSTED`, `CLEARTEXT_BLOCKED`, `CLIENT_CERT_REQUIRED`, and a damaged saved pin as `TLS_UNTRUSTED`), preferring one if home and away fail differently; null for ordinary unreachability and identity mismatch. No address is ever in a state's text.
- **Re-probing and staleness:** on every `NetworkMonitor.changes` emission and on `refresh()` the state becomes `Checking(previous = the old Online)` **synchronously**, so a pre-change `Online` is never still published; a generation counter makes check-and-set atomic and discards any in-flight probe that started before the latest change. The probe then starts after a 500 ms debounce for network changes or at once for `refresh()`. Requests collapse through a conflated channel: one more probe after the running one, never overlapping. `forget(serverId)` publishes `Offline()` first, so a collector still holding the flow stops showing Online.
- **What `awaitOnline(serverId)` proves:** the address answered as this server, with the settings saved when the probe started, since the last network change the OS reported. It does not prove the answer came from the real server on plain http, or that the phone has not just moved network; that is why `AuthRepository` repeats the identity check on the chosen address immediately before sending (see "Credentials"). A caller whose request fails calls `refresh()`.
- `AndroidNetworkMonitor` registers `registerDefaultNetworkCallback` when the first collector arrives and unregisters after the last (`shareIn` with `WhileSubscribed`), with signal-strength-only capability updates ignored. `AppGraph` owns the process-wide `appScope` they run in.

## UI (Task 8)

Single activity (`ui/MainActivity`, edge to edge) hosting Compose with Navigation-Compose. Material 3 with one fixed brand colour scheme (see "Brand"; no dynamic colour); `ui/theme/Theme.kt` adds firmer headings and `CodeStyles` for Quick Connect codes and fingerprints.

```
ui/
├── MainActivity, ClientCertChooser (+ KeyChainCertChooser: the Activity-bound KeyChain picker), CertificateSummary, ConnectionView (Connection -> chip model)
├── nav/          AppNav (AppRoot, NavHost, Routes), Routes.kt (one wiring composable per route), GraphViewModel, StartupViewModel
├── components/   Artwork (+ LocalArtworkLoader, ArtworkPlaceholder), AppScreen (top bar, centred 560dp column, IME padding), Buttons, Messages (ErrorMessage live region, NoticeCard), SecurityPrompts
│                 (http / certificate / client-certificate steps shared by Add server and Connection settings), CertificateDetails, ConnectionChip, Dialogs,
│                 SecureWindow, ObscuredTouches (FilterObscuredTouches)
├── onboarding/   AddressChecker (state machine), AddServerViewModel + Screen + Steps, SignInViewModel + Screen + Panels
├── servers/      ServersViewModel + Screen, ServerEditViewModel + Screen + Sections + Panes
└── home/         HomeViewModel, HomePlaceholderScreen
```

- **Start-up routing:** a neutral splash shows until `StartupViewModel` has awaited `awaitWarmed()` (via `awaitActive()`); then nothing saved means `welcome`, otherwise `home` (which copes with nobody signed in). No flash of the wrong screen.
- **Navigation graph:** `welcome` (first run) or `home` start; `add_server`; `sign_in/{serverId}`; `servers`; `server/{serverId}` (connection settings). Home -> servers -> add server / sign in / settings. Adding a server goes to its sign-in (popping `add_server`; on first run `welcome` stays underneath so the stack is never empty); signing in clears the stack and lands on `home`. Transitions are short fades with a small slide.
- **ViewModel and state conventions:** plain `androidx.lifecycle.ViewModel`s made by `graphViewModel { ... }` from `AppGraph` (scoped to the nav entry, cleared on pop; no DI framework). Each exposes one immutable `UiState` data class as `StateFlow` plus event functions; all logic and every error string (`AppError.userMessage`) lives there and is unit-tested with fakes. Composables are stateless: state plus an `...Actions` class of lambdas. ViewModels depend on the small interfaces in `data/servers/Seams.kt` (`ServerCatalog`, `Authenticator`, `ServerConnections`, `CertificateProber`), each implemented by one production class (`StoreCatalog`, `AuthenticatorImpl`, `AddressSelector`, a lambda). `ServerCatalog.activeSession()` (distinct values only) gives the active account as a token-free `Session`. The seams carry **no access token** and take server ids; lists are `ServerSummary`/`AccountSummary`. What remains reachable from the UI layer: the typed password (in the sign-in `TextFieldState`, until submitted) and the Quick Connect code on screen; custom header values (deliberately, for the settings screen). UI states that hold addresses, headers or certificate details override `toString`.
- **Secrets in the UI:** the password lives in a `TextFieldState` owned by `SignInViewModel`, never in `UiState`; it is copied to a `CharArray`, the field is cleared at once, and `AuthRepository` wipes the copy. `FLAG_SECURE` (counted, `SecureWindow`) is set while Sign in and Connection settings are visible. Header values are masked until revealed and the data layer's validation message (`validateCustomHeader`) never repeats a value. Autofill hints are set for username and password.
- **Sign in:** before every attempt the ViewModel asks for a `SignInRoute` and passes it back. The first route obtained when the screen opens is the baseline: it sets `unencrypted` and blocks nothing (the user consented to plain http when adding the server, and the notice is on screen while they act), so an http-only server goes straight to Quick Connect, or to the password form when Quick Connect is off. Only a later downgrade, a route that is unencrypted after the baseline said encrypted (at password submit, or at Quick Connect start, restart or "Use Quick Connect instead"), is held once: nothing is sent, the notice appears, the password stays in the field with "The secure connection isn't available right now...", and the next press sends. `SignInUiState.unencrypted` shows a persistent, non-blocking "This connection isn't encrypted" notice when the route is plain http.
- **Servers:** sign-out and remove server always succeed on the phone; `ServersUiState.notice` says when the server could not be reached to revoke the sign-in there too. The remove dialog says sign-ins are signed out on the server as well.
- **Add server:** `AddressChecker` runs `findServer` and turns each problem into an explicit state: plain http (`NeedsHttpConsent`, shown after an explicit `http://` is blocked, or offered when a scheme-less address failed to connect over https), untrusted certificate (`probeCertificate`, fingerprint, trust pins it), client certificate (`KeyChain` alias). Nothing is saved until the optional second-address step ends; the second address passes the same checks and must be the same server. The first address is sorted home/away by `looksLikeHome()`. One pin and one cleartext flag exist per server, so a second address with its own different self-signed certificate cannot be pinned separately.
- **Consent to plain http is per address:** every new address check (second address, any edit) starts with `allowCleartext = false`, so the warning appears again and names the role (home or away); on save the server flag is the OR of the existing flag and the new consent. The warning also says that on another network a different device could pose as the server. A check merges only what it changed into the server read at save time (a certificate forgotten meanwhile stays forgotten). An already saved server found while adding is not modified: the user is told and goes to sign-in.
- **Tapjacking:** `FilterObscuredTouches` sets `filterTouchesWhenObscured` on the hosting window while "Use anyway" (`HttpWarningScreen`), "Trust this certificate" (`CertificateScreen`) or any `SecureDialog` (every confirmation, the header editor) is shown, so touches made through another app's overlay are dropped. That backstop is not the only layer: while it is on, the hosting window's `Window.Callback` is wrapped, and any touch flagged `FLAG_WINDOW_IS_OBSCURED` or `FLAG_WINDOW_IS_PARTIALLY_OBSCURED` is dropped there (a gesture already begun is cancelled, never left half-pressed) and `FilterObscuredTouches()` returns true, so the screen shows one line, "Another app is drawing over the screen, so this button is switched off. Close screen filters or bubbles and try again." (`ObscuredTouchHint`), cleared by the next clean touch. Covered for both full screens, `ConfirmDialog` and the header editor dialog (`ObscuredTouchTest`).
- **Start-up failure:** if reading the saved servers throws, `StartupState.Failed` shows a plain retry screen (never Welcome); Retry also retries a failed token warm once (`retryWarmIfFailed`).
- **Cleartext flag and Home retry:** the server's plain-http flag lapses by itself when an address edit leaves no http address, and cannot be switched on with none. Home retries a failed token warm once on opening and on every Retry; if it still fails it shows "Something went wrong opening your saved servers" with Retry instead of a silent signed-out state.
- **Accessibility and secrets:** the Compose secure field keeps the raw text in the semantics node as `EditableText` (found with a Robolectric probe), which accessibility services such as `uiautomator` read; while hidden, the sign-in password and header value set the Password flag and override `EditableText` with bullets in one semantics block (real text once the user presses Show) (`PasswordExposureTest`, `PasswordExposureOnDeviceTest`).
- **Layout rules:** `AppScreen` keeps its action bar pinned above the keyboard by default; only when space is genuinely short (font scale above 1.5, or under 360dp of visible height after bars and keyboard) do the actions sit at the end of the scrolling content. Every form submit hides the keyboard first (`rememberSubmit`). Body text is 18/16/14sp with generous line height; paragraphs are left-aligned. `CheckGate` maps an address check onto the shared warning screens for both Add server and Connection settings; destructive settings are behind `ConfirmDialog`. Dialog windows use `DialogProperties(securePolicy = SecureOn)`; `SecureWindow` is counted per window.
- **Brand:** one fixed teal and coral colour scheme (no dynamic colour), light and dark (`Theme.kt`, contrast pinned by `ThemeContrastTest`); a three-fish shoal vector (`ic_shoal_foreground`) is the adaptive launcher icon (with a monochrome layer) and the welcome mark. Previews of each screen are in `ui/Previews.kt`.
- **Tests:** ViewModel unit tests (`ui/**`), `ScreenRenderTest` and `ManagementRenderTest` (Robolectric + Compose test: every state composes, shows its key text, survives 200% font scale), and four on-device tests in `app/src/androidTest` (`TrustOnDeviceTest`, `KeystoreSecretBoxTest`, `PasswordExposureOnDeviceTest`, `WelcomeSmokeTest`), run by the controller.
