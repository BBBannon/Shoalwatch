### Build and supply-chain security (S10, S12)

- **Dependency verification** is on: `gradle/verification-metadata.xml`. After adding or bumping a dependency, regenerate with
  `./gradlew.bat --write-verification-metadata sha256 help testDebugUnitTest assembleDebug assembleDebugAndroidTest assembleRelease` and review the diff.
- **Verification is checksum-only (sha256), by decision.** Signature verification (`verify-signatures`) is off because many artefacts (much of Google Maven) are not signed or have no published keys, so it would mostly add trust-on-first-use key entries. A sha256 pins the exact bytes that were reviewed, which is the stronger guarantee for a fixed dependency set. Revisit at the Milestone 8 security-team review.
- **Repositories:** `FAIL_ON_PROJECT_REPOS`; `google()` is limited to `androidx.*`, `com.android.*` and `com.google.*` in both `pluginManagement` and `dependencyResolutionManagement`.
- **Gradle wrapper:** `distributionSha256Sum` pins the official checksum of `gradle-8.11.1-bin.zip`; change both lines together.

## Layer rules (read before changing anything that sends a credential)

- **Callers pass ids; settings come from the store.** Anything that acts on a server's security settings (address selection, sign-in, sign-out, removal) takes a `serverId` and reads the current `Server` from `ServerStore` at the moment of use. There is no API that accepts a caller's `Server` copy for these.
- **Two senders of credentials, each with one rule for the address.** `AuthRepository` is the only sender of passwords, Quick Connect secrets and token revocation, and it alone picks that address (verified, https preferred). `ServerApi` is the only sender of the access token on ordinary requests, and it takes its address only from `AddressSelector.awaitOnline(serverId)`. See "Credentials" and "Authenticated requests" below.
- **The UI cannot reach tokens.** The seams (`data/servers/Seams.kt`) carry none; screens read `ServerSummary` and `AccountSummary`.
- **Ids from the server are validated** at the gateway (`JellyfinId`) and stored normalised; display strings from the server are sanitised there too (`displayText`).
- Admin requests go only through `Admin`, gated on `AdminRights`; see Server admin.

## Network security model

- **Who is trusted:** the platform's own certificate authorities only. User-installed CAs are not trusted (no `network_security_config`).
- **Self-signed servers:** accepted only if the leaf certificate's public key (SPKI SHA-256, base64) equals the pin the user approved. A pin is checked only when system trust fails; a mismatch raises `PinMismatchException`, which `AppError.from` maps to `TLS_PIN_CHANGED`. Pin comparison is constant-time.
- **Hostnames:** normal hostname verification always runs first, so a system-trusted certificate for a different host is refused even on a pinned client. Only if that fails does a pinned client accept, and only when the peer's leaf key is exactly the pinned key (LAN certificates often lack a matching name).
- **TLS versions:** 1.2 and 1.3 only. Plain `http` is allowed by the connection spec but policed per server by `CleartextGuard`.
- **Redirects:** no client from `HttpClientFactory` follows one (`followRedirects(false)`, `followSslRedirects(false)` on the shared base; there is no option to turn them on). A 3xx reaches the caller as a response and the gateway treats it as an error (`SERVER_NOT_FOUND`). Defence in depth, as both application and network interceptors: `CleartextGuard`; `AuthInterceptor` (sets `Authorization` only for the server's own authorities, removes it and the legacy token headers and `api_key`-style query parameters everywhere else); `CustomHeaderInterceptor` (adds the configured headers only for the server's own authorities and removes every configured header name for any other). So even a caller that re-enables redirects cannot carry the token or a header to another host (`RedirectPolicyTest`). A later milestone that genuinely needs a media redirect followed must do it by hand and re-check the target authority before sending anything.
- **First contact:** `probeCertificate` handshakes with a capture-only trust manager that always fails after recording the leaf, so no request, token or header is sent on the unverified connection. It uses no `clientFor` client. The whole probe has a hard 10 s deadline: on expiry or cancellation its socket is closed (an uninterruptible DNS lookup may leave one daemon thread behind until it returns, but the caller is released). Certificate names are sanitised for display.
- **Client certificates (S5):** every client gets a recording key manager from `ClientCertWatch`, wrapping `KeyChainKeyManager` (which offers only the stored alias) or nothing. The TLS layer asks it for a client alias only when the server sent a CertificateRequest, so "the server asked" is known structurally, never from exception text. With no alias configured, only two things become `CLIENT_CERT_REQUIRED`: (a) a failure DURING the TLS handshake of a call on which the server asked (a TLS 1.2 alert; the handshaking call is marked by an `EventListener`, and `connectFailed` records it), and (b) the FIRST response, or first read, on a freshly handshaken connection that was asked and sent no certificate (a 400/403 such as nginx's "No required SSL certificate was sent", or for TLS 1.3 an IOException on that first read; marked by socket). A connection that has returned any response is proven: a later 403 (a genuine `FORBIDDEN`), a timeout or any other failure on it is never remapped. Known limit: a genuine 403, and also a timeout or reset, on the first exchange of a fresh connection to a proxy with optional client authentication is still reported as "needs a certificate". The result is `CLIENT_CERT_REQUIRED`, which the add-server checker turns into the "Choose certificate" step. A server that only asks optionally and then serves the request is unaffected. The certificate probe refuses the server certificate before any CertificateRequest is acted on, so a self-signed server that also needs a client certificate is always "trust this certificate" first, then "choose a certificate" (`ClientCertificateTest`, `ClientCertFlowTest`). `KeyChain` calls block and refuse the main thread; every network call in this app runs off the main thread. Any KeyChain failure presents no certificate.
- **Clients:** all share one connection pool and dispatcher; no cache, no cookies; connect 10 s, read/write 30 s, no call timeout (it would cut long downloads). Callers hold one client per server configuration (`ServerClients`; each `clientFor` builds a new SSLContext); a token revocation uses a one-off client instead (see "Token rules").

## Credentials: where they go

`AuthRepository` is the only code that sends a password, a Quick Connect secret or a revocation, and it alone picks the address for those (ordinary requests that carry the access token are `ServerApi`'s, see "Authenticated requests"):

1. The server is read from the store now (a removed server is `SERVER_NOT_FOUND`, and nothing is sent).
2. The address must be verified on the current network: `AddressSelector.awaitOnline(serverId)`. If nothing is verified, nothing is sent.
3. **HTTPS preferred:** if the verified address is plain http and the server also has an https address, that https address is checked (`/System/Info/Public` must report this server's id); if it answers, it is used. Plain http is used only when it is the server's only address or its https address cannot be reached.
4. The identity check is repeated on the chosen address immediately before the credential is sent; after sign-in the result's `ServerId` must match too (`SERVER_MISMATCH` otherwise; nothing stored).

The UI gets an opaque `SignInRoute` from `Authenticator.signInRoute(serverId)` before every attempt and hands it back; `AuthRepository` refuses any route it did not issue, so a screen cannot choose an address. `SignInRoute.encrypted` drives the Sign in screen's persistent "This connection isn't encrypted" notice.

- **Quick Connect** re-sends its secret on every poll (up to 5 minutes), so each issued route remembers the selector connection (`Connection.Online`) it was derived from, and a watcher on `connection(serverId)` ends the flow with `Failed(CONNECTION_CHANGED)` the moment that connection is anything else: `Checking` after a network change, `Offline`, or `Online` on another address. The check is also repeated just before the final `authenticateWithQuickConnect`, so no secret is sent after the change (`QuickConnectConnectionChangeTest`). The screen says "Your connection changed. Start Quick Connect again."
- **Sign-out** revokes the token only through that verified address (never by trying the saved addresses in turn), within 12 s, then removes the account here regardless (`NonCancellable`). If no address is verified the token is sent nowhere. A saved token that cannot be read (lost Keystore key) is not "nothing to revoke": `ServerStore.token` answers `StoredToken.Unreadable`, distinct from `Missing`, and `signOut` reports it exactly as an unreachable server. Either way the Servers screen says "Signed out on this phone. Shoalwatch couldn't sign you out on the server, so that sign-in may still be active there — you can remove it from the server's dashboard."
- **Remove server** first revokes every account on it in parallel by the same rules (6 s overall), then deletes the server here regardless, with the same notice when any revocation did not reach the server or any saved token could not be read (`ServerStore.tokens` counts the unreadable ones; the readable ones are still revoked).
- **Residual risk (plain http):** with an http address, nothing can authenticate the server: the id it reports is public, so on another network a device holding the same address can pass the identity check and capture what is sent. The https preference and the warnings shrink this; recommending HTTPS is the mitigation. Recorded in `docs/security/milestone-1-check.md`.
- **A profile's PIN (Milestone 7)** never leaves the phone and is never stored: only its verifier is, in `profile_locks`, sealed by the same Keystore `SecretBox` as the tokens (see "Profile PINs"). Below the field the PIN is only a `CharArray`, zeroed after the check. **"Forgot PIN"** is the one place outside the Sign in screen where a server password is typed: it goes through `AuthRepository.signInWithPassword` by exactly the rules above (an issued `SignInRoute`, the identity check, the result's `ServerId`), for the locked profile's own user name, and the panel offers no Quick Connect. **Known limit (final review M2, Ben to confirm):** on an address Ben allowed over plain http, someone impersonating the server on that Wi-Fi can answer Forgot PIN and clear a PIN; HTTPS (a CA or pinned certificate) blocks it. Recorded in `docs/security/milestone-7-check.md`.
- **The Keystore key has no user-authentication binding, by decision** (`KeystoreKeyProvider`; Milestone 1 check Q9). Binding it to the phone's screen lock (or the app lock) would stop background downloads and sync, which decrypt tokens while the phone is locked. The app lock is therefore a gate on the screens, not a key: what protects the tokens at rest is the Keystore itself (not exportable, StrongBox where the phone has it) and no backup. The SPEC S1 wording for this is left to Ben.

## Profile PINs (`PinHasher`, `ProfileLocks`, Milestone 7)

A protected profile has a row in `profile_locks` (see "Profile tables (Room v6)").

- **The PIN** is 4 to 12 ASCII digits (`PinRules`), held only as a `CharArray`. Every `ProfileLocks` entry point (`protect`, `check`, `changePin`, `unprotect`) fills the arrays it was given with zeros before it returns, on every path; `PinHasher` only reads them and clears its own copy (`PBEKeySpec.clearPassword`) and the derived bytes.
- **The verifier** is PBKDF2-HMAC-SHA256 (the platform's own `PBKDF2WithHmacSHA256`, no new dependency), 100,000 iterations, a 16-byte `SecureRandom` salt and a 32-byte result, written as `p1:<iterations>:<base64 salt>:<base64 hash>` and sealed by the existing Keystore `SecretBox`, so a copied database cannot be tried offline. The iteration count is read back from the blob, so it can be raised later without a migration. Comparison is constant-time (`MessageDigest.isEqual`). A blob that cannot be opened (the Keystore key is gone) or is not in that format is `PinCheck.Unreadable`, which counts nothing: only "Forgot PIN" helps.
- **Waits:** five free tries, then 30 s doubling for each further wrong PIN, at most 15 minutes (`PinThrottle`). The count of wrong PINs is in Room (`failures`, back to 0 on a right PIN or a new PIN), so it survives a restart. The wait is timed only by the monotonic clock, from an anchor in memory per profile: the time of the last wrong PIN in this process or, if there was none, of the first check in this process. Killing the app therefore restarts the wait (never shortens it), and changing the phone's clock does nothing. While waiting, `check` answers `Wait(seconds, rounded up)` without opening the verifier or counting. Every try is counted in Room before the verifier is opened and the count is put back on a right PIN (or an unreadable verifier); if the count cannot be saved (a full or damaged database) `check` throws `AppError` and checks nothing, so no guess is ever uncounted (review I1). One mutex serialises every check, so two checks at once cannot share a free try; `LockParts` builds the only `ProfileLocks` (`LockPartsShapeTest`). `PinCheck.Wrong(0)` means the free tries are used up and the wait has started. Hashing and Room run on the IO dispatcher.
- `changePin` refuses (`IllegalArgumentException`, nothing checked or counted) a new PIN that breaks `PinRules`: screens check it first. `clear` (internal) removes the protection after a password sign-in from "Forgot PIN", and takes only a `ClearProof`: made by `ClearProof.afterPasswordSignIn` from the account the server returned for the locked profile's own password, and only when it is exactly that profile (Tasks 1-2 review M1). `LockBoundaryTest` keeps the proof in `LockViewModel` (right after `signInWithPassword`) and `clear` in `LockParts`.
- No PIN, PIN length, verifier or profile id is logged; every new type has a redacting `toString()`.
- **Switching (`ProfileSwitch`):** the one way a screen changes the active profile. An unusable target (signed out, expired, removed) is `Gone`; a protected one is `NeedsPin` (nothing set) until `switchWithPin` checks its PIN, records the proof in `ProvedSwitches` (one slot, consumed once, 10 s monotonic) and only then calls `ServerStore.setActive`. No proof is left behind that no change will use (final review M4): if `setActive` throws, the proof is forgotten (`ProvedSwitches.forget`), and none is recorded when the target is already active. `StoreCatalog.setActive` itself throws `ProfileProtectedException` for a protected profile, so a screen that forgets to ask is refused. Every other path that makes a profile active (a password or Quick Connect sign-in, "Sign in again", a restart) goes through `ServerStore` and is caught by `LockGate` (see "App lock"): a protected profile becoming active without a fresh proof is locked. A sign-out never makes another profile active (`ServerStore.removeAccount` leaves nobody). `ProfileSwitchTest`, `SwitchPathsTest` (every path, real store and gate).
- **The household check (`HouseholdGuard`):** while a protected profile exists and the active one is not protected (or nobody is), household changes need a protected profile's PIN: "Share downloads between profiles" (`DownloadRepository.setSharing`), "Delete shared downloads" (`HousekeepingRepository.setSharedDelete`), editing a saved server (`StoreCatalog.upsertServer` of an id already saved; adding a new server is not one) and removing a server (`AuthenticatorImpl.removeServer` → `requireRemoveServer`). Removing a server signs out every profile on it, so it also needs what signing each protected profile on it out needs (final review M5): its own PIN unless it is the active, open profile. One pass is one grown-up, so with two or more such profiles the Servers screen refuses ("Sign each of them out first…", `ServersUiState.signOutFirst`) and with one it asks that profile's own PIN. Signing out a protected profile that is not active needs that profile's own PIN (`requireSignOut`); an unprotected profile, or the active one, can always be signed out. Each check runs in the data layer before anything is sent or changed, and throws `HouseholdLockedException`. `confirm` gives a pass held in memory only, bound to the profile active when the PIN was typed (read before the check; a switch during the check records no pass, final review M6), for 60 s of monotonic time, ended at once by any change of the active profile or a lock (`endPass`). "The active profile is protected" counts only while `LockGate.isOpenFor` that very session: a protected profile that is active but locked (a Quick Connect sign-in approved on another device, or "Lock after" passed) is no grown-up (review I2). `HouseholdGuardTest`, `HouseholdEnforcementTest`.
- **Becoming a grown-up needs a grown-up (review I1):** `protect`, `changePin` and `unprotect` ask the household check (`ProfileLocks`'s `grownUp` hook, wired to `HouseholdGuard.require` in `LockParts`) whenever a protected profile OTHER than the one being changed exists, so a child cannot protect their own profile and then pass every household check. **Residual risk (Ben to confirm):** the very first protection on a phone needs no check (there is no grown-up yet), so whoever protects a profile first on a new or reset phone becomes the grown-up.

## App lock (`LockGate`, `LockPrefs`, `DeviceAuth`, `RecentsPrivacy`, Milestone 7)

One lock state for the app: `Checking` (start-up, until the settings, the active profile and the protected profiles are known), `Open`, `App` (the phone's own screen lock is asked for) or `Profile(session, userName)` (that profile's PIN). The rules:

- **Start**, and a **return** after "Lock after" (`LockPrefs`: immediately, 1, 5 or 15 minutes; default 1 minute): the app lock first (when on and the phone has a secure screen lock), then the active profile's PIN when it is protected, else open. A cold start always asks. `MainActivity.onStop` (not a configuration change) calls `onLeft`, `onStart` calls `onReturned` except while still in the picture-in-picture window (the screen off and on there, or a recreation there, is not a return: Tasks 9-10 review C1; both through `ActivityPip.onActivityStarted`/`onActivityStopped`; `MainActivity` hands `ActivityPip` the gate itself as its `AppTrips`, which the tests replace with a recording fake); entering picture-in-picture calls `onLeft` and going back to the full screen `onReturned` (`ActivityPip`, Task 9); the time away is measured only by the monotonic clock, and a second `onLeft` keeps the earlier time. `expectReturn` (before the unlock prompt or the client-certificate chooser) makes the next trip not count, but only if the activity stops within 10 s of it, so a prompt that never stops the activity cannot excuse a later real trip; and `tripDone` ends the excuse as soon as the prompt answers (yes, no or cancel), because a fingerprint `BiometricPrompt` is a system window that never stops the activity at all (final review M1). The unlock prompt, the Settings app-lock prompt and the certificate chooser each call it (`LockBoundaryTest.everyExpectedTripIsEndedWhenItsPromptAnswers`). An excused trip is still capped: back after 2 minutes or more (or "Lock after", if longer) locks anyway (`EXCUSED_CAP_MS`, review M1).
- **Profile changes:** whenever the active profile changes to a protected one, it is locked unless `ProvedSwitches.consume` says its PIN was typed for that switch; a change to an unprotected profile or to nobody opens a profile lock. While `App` is asked the change waits: after the app lock, a protected active profile is asked for. The lock is decided at once from the protected set already in hand, with no read first; the store's own `isProtected` is asked afterwards and can only add a lock (review I3).
- **`openFor` (review I3):** the active session the gate has judged and found open (null while any lock applies, or while the store's answer for a change is pending). The active-profile flow reaches screens before the gate, and a quick kid → adult → kid change can skip the adult in the gate's `combine`, so the UI (`AppRoot`'s cover) and the household check treat any active session other than `openFor` as locked: nothing of a profile shows until the gate has judged that very profile.
- **A failed read (review M6):** if the protected profiles cannot be read, the gate neither crashes nor opens anything: the lock stays as it is, `readFailed` is true (the lock screen shows a plain error), and the read starts again after `READ_RETRY_MS` (5 s). A profile change meanwhile is not judged, so `openFor` keeps it covered. After "Forgot PIN", a store that cannot answer leaves the profile locked. `HouseholdGuard.askNeeded` asks for a grown-up while its read fails. `LockGateTest`.
- **No secure screen lock:** if the phone has none at a check while the app lock is on, the app lock is switched off in `LockPrefs` (removing the phone's screen lock needs the phone's own credential) and the check continues. Every move into `App` or `Profile` ends the household pass.
- **`DeviceAuth`:** the framework `BiometricPrompt` (no extra library): API 30+ `BIOMETRIC_WEAK or DEVICE_CREDENTIAL`, API 29 `setDeviceCredentialAllowed(true)`, no negative button, cancelled with the coroutine. - **Screens of a locked profile still load under the cover** and fetch with that profile's own token (Tasks 5-6 review, I3 residual): nothing is shown, read out or touchable, and the reset pops them; a gated catalog for ViewModels was not built.
- **A failed read of the saved locks on the very first read** leaves the splash with no message until a read works; after "Forgot PIN", a store that cannot answer leaves the profile locked until the next read. Both fail closed.

## Authenticated requests (`ServerApi`)

Every signed-in request in the app goes through `data/api/ServerApi`: `get` (decoded JSON), `post`, `postForJson` (JSON body, decoded JSON answer: PlaybackInfo; not retried unless asked), `delete`, `getBytes` (bounded stream, for artwork and subtitle files). Media bytes for the player are the one exception to "ServerApi sends it": `mediaRoute` hands out a guarded route instead (see "Media route"). Callers pass a `Session(serverId, userId)` (token-free; the UI observes it as `ServerCatalog.activeSession()`, which waits for the token warm gate like the other account reads), a `path` starting with `/` and a `query` list.

1. `store.awaitWarmed()`.
2. `AddressSelector.awaitOnline(serverId)`: nothing verified is `OFFLINE` ("You're offline. Showing what's saved on this phone where possible.") and **nothing is sent**. Only then is the server read from the store (so its addresses and security settings are current; a removed server is `SERVER_NOT_FOUND`), and the verified address must still be one of its saved addresses, or the attempt is treated like a lost connection.
3. The account's client comes from `ServerClients` via `ServerNet.authenticated(..., store::cachedToken)`: the token is read live on every request and never captured, so a signed-out account fails as `NOT_SIGNED_IN` with zero requests sent.
4. The URL is the verified `ServerAddress` (base path kept, e.g. `https://example.org/jellyfin`) plus `path` plus `query`, built only with `HttpUrl.Builder` so everything is encoded. A `path` containing `..`, a `.` segment, `//`, `?`, `#`, a backslash or a control character, or not starting with `/`, is an `IllegalArgumentException` (programmer error, fixed message, nothing sent). Ids are passed already normalised by `JellyfinId` and are not re-validated here.
5. Everything runs on the injected IO dispatcher (main-safe); cancelling the caller cancels the OkHttp call, including during the body read.

- **Unlike sign-in, ordinary requests do not upgrade to https.** If the verified address is the (consented) plain-http home address, that is where the token goes: using the fast home address at home is the feature. The residual risk is the one already recorded under "Residual risk (plain http)".
- **Status mapping** (a response is an answer, never retried): one function, `AppError.fromHttpStatus`, shared with the sign-in gateway: 401 `UNAUTHORISED`, 403 `FORBIDDEN`, 404 `SERVER_NOT_FOUND`, any other 3xx `SERVER_NOT_FOUND` (no client follows redirects, so that address is not serving the API), 304 `SERVER_ERROR` (we never send a conditional request, so a 304 is the server misbehaving), every other 4xx and 5xx `SERVER_ERROR`.
- **Network failure before a response:** the selector is asked to re-probe THIS server only (`refreshIfCurrent(serverId, used)`), and only if the `Connection.Online` the failed attempt used is still its current state (compared by identity: every verification publishes a new instance). So a burst of parallel failures after a network change causes one probe cycle, and a failure from before a newer verification cannot flip it back to `Checking`. The global `refresh()` stays for the UI's manual retry. If the call's `retry` flag is set (default true for GET and `getBytes`, false for POST and DELETE; callers opt in only for idempotent operations), `awaitOnline` is asked again and the call repeated exactly once, to whatever address is verified now (nothing verified: `OFFLINE`); a second failure is `AppError.from`. A guard refusal (`BlockedRequestException`: cleartext, signed out, client certificate, pin) is never retried. A failure while reading the body is mapped (and re-checks) without a retry. **Callers must not wrap `ServerApi` calls in their own retry loops**: retries would multiply (10 s connect and 30 s read timeouts each).
- **`sendOnce` and `sendIf` (opt-in, admin actions only, Milestone 6).** `post` and `delete` take `sendOnce = false` and `sendIf = { true }` by default, so every existing caller (playback reports included) behaves exactly as before. With `sendOnce` the request body is marked one-shot (a DELETE then carries an empty body, `Content-Length: 0`): OkHttp's `retryOnConnectionFailure` no longer resends it after a kept-alive connection fails once the request was written, and OkHttp never follows a one-shot request up (a 503 with `Retry-After: 0`, a 408). OkHttp still recovers when nothing of the request was written (a failure while connecting, an HTTP/2 connection shut down before the stream). `sendIf` is asked once more just before the call is made, after the wait for a verified address: false sends nothing and fails `FORBIDDEN` (the gateway passes `allows(session)`). Only `AdminGateway` passes either (`AdminBoundaryTest`).
- **Bodies** (`JsonBodies`, shared with `JellyfinGatewayImpl`): bounded read on the decoded bytes (one byte past the limit decides; default 4 MiB for `get`), one Json configuration: `ignoreUnknownKeys` only. `coerceInputValues` is deliberately off, so an explicit JSON null for a non-nullable field is a decode failure (fixed `SERVER_ERROR`), never a silent default; DTOs for untrusted responses declare every field nullable with a default. Nothing from a body is ever in a message. `getBytes` hands the caller a source that fails with `SERVER_ERROR` past `maxBytes` (a larger declared length fails before the reader runs); the response is closed when the reader returns or throws and the source must not be kept. The reader's own exceptions, including an IOException such as a failed file write, propagate unchanged and are never treated as a network failure.
- **Rejected sign-in (401):** a 401 from the verified address of a signed-in call means the server no longer accepts this token. `ServerApi` calls `ServerStore.invalidateToken(serverId, userId)`: the in-memory token is removed (later calls fail at once as `NOT_SIGNED_IN` with zero requests, so the app cannot loop on a dead token), the account leaves `usable` (so `accounts`, `activeAccount`, `active()` and `activeSession()` all drop it, and the UI shows the server as needing sign-in), the server's cached clients are evicted, and `warmTokens` will not load it back, after a restart too: `invalidateToken` also writes `rejected_sign_ins` (`AccountDao.reject`; if that write fails the in-memory set still holds it for this process) and `warmTokens` reads `AccountDao.getAllUsable`, which leaves those accounts out, so no request after a restart carries the dead token (Milestone 2 check I4). The database row is kept (and the profile's outbox rows wait); signing in again (`upsertAccount`) overwrites it, clears the rejection in the same transaction and restores normal operation. The call then fails with `UNAUTHORISED` "Your sign-in has expired. Sign in again." It is skipped when the sign-in was replaced after the request began (`tokenGeneration`), so a late 401 for the old token cannot sign out the new one. A 403 does none of this, and anonymous calls (sign-in, probing) never do. **Known limit:** on a plain-http address an impostor that passed the (public) identity check can answer 401 and so sign the user out locally. That is a denial of service only: no credential is exposed beyond what the plain-http residual risk already covers.
- **Network moved after verification:** `awaitOnline` proves the address answered as this server since the last network change the OS reported, not that the phone has not just moved. Ordinary requests have the same window as sign-in has (see "What `awaitOnline(serverId)` proves"); the ordinary-request token goes to the verified address in that window, and the plain-http residual risk applies.
- **Deferred (M9):** every request reads the full `Server` (a Keystore decrypt of custom headers) to build its client configuration. A correct cache needs a settings-version signal from the store; not small, so left for the artwork task, which is where parallel loads make it matter.

**Untrusted-input rules at this boundary (SPEC S11):**
- **Ids** go through `JellyfinId` (normalised: lower case, no dashes). An item whose own id is not a GUID is dropped from a list; a single `item()` fails as `SERVER_ERROR`. Invalid optional ids (`parentId`, `seriesId`, `seasonId`) become null. Ids the caller passes in that are not GUIDs fail as `SERVER_NOT_FOUND` before any request.
- **Display strings** go through `displayText` (`displayParagraphs` for the overview) (control and format characters, including bidi and zero-width, removed): name, series name and sort name 200 characters, official rating 20. The overview (4,000) keeps line breaks (`displayParagraphs` in `core/`: at most one blank line in a row) but loses everything else unusual; HTML is not stripped here, the UI shows it as plain text. A name with nothing visible left is the empty string (the model holds no English text; the UI supplies the placeholder).
- **Numbers** are range-checked: index numbers 0..100,000 else null; year 1800..2200 else null; rating 0..10 else null; runtime, position, counts and percentages must be in range else null (position and play count 0). Ticks become milliseconds with `Ticks`.
- **Dates** (`premiereDate`, `lastPlayed`) parse leniently; an unparseable date is null.
- **Image tags** must match `[A-Za-z0-9]{1,64}` else null (they become cache keys and query values).
- **Element-level tolerance:** list containers keep each element (and an item's `UserData`, and the total) as a raw `JsonElement` and decode them one at a time, so one element of the wrong JSON type (a number for a name, a fractional index, an id that is not a string, an integer beyond Long, a bare string or null in the array) is skipped and never costs the page; an unreadable `UserData` leaves the item with `userData = null`. A numeric string such as `"2020"` is accepted by the decoder and still range-checked. A single `item()` that cannot be read is `SERVER_ERROR`.
- **De-duplication:** in every list (items and views) the first occurrence of an id wins (ids compared after normalisation), because ids become Room keys and `LazyColumn` keys; a duplicate does not use up the limit.
- **Self-links and watched state:** an item that is its own `parentId`, `seriesId` or `seasonId` has that link nulled; a watched item has `positionMs = 0` and no `playedPercentage`.
- **Ordering:** `children` sort keys are sent as above. `episodes` (season, episode number with missing last, sort name, id) and `seasons` are sorted in the gateway, so the app never depends on the server's order. Both use one season rule (`Ordering.kt`): numbered seasons first, then anything with no season number, then season 0 (Specials) genuinely last. The reference's `sortBy` on the episodes endpoint accepts a single value only, so none is sent.
- **Long series:** `episodes` pages with `startIndex`/`limit=500` until the server's own usable count is reached (an empty page ends it; with no usable count, a short page does), at most 10,000 items and 50 requests. `/Shows/{id}/Seasons` has no paging parameters, so seasons are one request (capped at 1,000).
- **Sizes:** lists are capped at the requested limit (views at 100) even if the server sends more; `Page.total` is at most 1,000,000. **A nonsense total is no total:** a `TotalRecordCount` that is negative, zero while elements came back, or smaller than the elements already seen (`startIndex` plus what this response held) is ignored, so `Page.total` is `null` (unknown) and the episodes loop does not stop early on it. **Paging by what the server consumed:** `Page.items` holds only the kept elements (malformed ones are skipped, repeats removed), so a caller must not advance by `items.size`. `Page.nextStartIndex` is `startIndex` plus every element the server sent, and `Page.endReached` is true when the server sent nothing, or the usable total is reached, or (no usable total) it sent fewer than the limit. An all-skipped page is therefore not the end.
- **Unproven until a real server:** the mutations send no `datePlayed`, so a retried mark-as-watched should not count a second play; and comma-delimited `sortBy`/`sortOrder` pairing per key. Both to be confirmed against a real Jellyfin 12.x server.
- Libraries whose collection type is not films, TV, collections or mixed (music, books, photos, live TV, playlists, home videos...) are skipped.

A default audio or subtitle index must name a kept track of that type. Subtitle kind: PGS, VobSub and DVB names are PICTURE, `ass`/`ssa` STYLED_TEXT, `srt`/`subrip`/`vtt`/`webvtt` TEXT, anything else TEXT only if `IsTextSubtitleStream`. `SubtitleTrack.format` keeps the codec name (what the device profile speaks); `fileFormat` is what the subtitle route takes: `subrip`/`srt` `srt`, `webvtt`/`vtt` `vtt`, `ass`, `ssa`; any other TEXT codec (`mov_text`, the usual MP4 subtitle, `text`, `ttml`, or one this app does not know) `srt`, which the server converts it to (**to confirm on a real server**: the reference does not describe the conversion); PICTURE codecs null (never fetched as text). `TranscodingUrl` only through `MediaPaths.checkServerPath` (refused: no transcoding for that source); `TranscodeReasons` is read from that validated URL's query (the 12.4.0 `MediaSourceInfo` has no reasons field), at most 32 names, and names this app does not explain are `OTHER`. `DeliveryUrl` is not read at all: text subtitles are fetched by the app's own `MediaPaths.subtitleFile` path. ## Media route (`ServerApi.mediaRoute`, `MediaRoute`, `GuardedCallFactory`, `MediaPaths`)

Media bytes are fetched by the player (Media3, from Milestone 3 Task 6), which needs an OkHttp `Call.Factory`, not a `ServerApi` call. So `ServerApi.mediaRoute(session)` (internal) does the same steps 1 to 3 as every call (warm gate; `awaitOnline`, none is `OFFLINE`; the server read after it, gone is `SERVER_NOT_FOUND`; the verified address must still be saved, else it is re-checked and `OFFLINE`; a token must be loaded, else `NOT_SIGNED_IN`) and sends nothing. It returns a `MediaRoute` holding the session, the verified address and the account's own cached client from `ServerClients` (so `CleartextGuard`, `AuthInterceptor`, `CustomHeaderInterceptor`, the pin and the client certificate all still apply, and the token is read live per request), wrapped in `GuardedCallFactory`. No new client is built (`HttpClientFactory` stays the only builder; `newBuilder()` is not used). After taking the client the server is read again and its configuration must be the one the client was made for (else the client is evicted and the answer is `OFFLINE`), so a settings save while the route is being made cannot leave a client with the old settings counted as current. `MediaRoute.url(source)` builds address + path + query with `ApiRequest` (paths checked by `ApiRequest.checkPath`). The UI never sees a route.

**What the guard refuses, and why.** A refused request is a `Call` that fails with `BlockedRequestException`, from `execute` and `enqueue` alike, and sends nothing; the reason is logged as a fixed word in debug builds, never the URL.
- **Any method but GET and HEAD** (`FORBIDDEN`): media is read-only, so a hostile playlist cannot make the player write.
- **Another scheme or authority (`host:port`, explicit port), any user name or password in the URL, or a caller-set `Host` header** (`FORBIDDEN`): the token and custom headers go only to the address the selector verified, never to the user's other address for that server, another port, `http` instead of `https` on the same port, or a proxy steered by `Host`. An HLS playlist can name absolute URLs; this is what stops them.
- **A path outside the address's base path + `/videos/`** (`FORBIDDEN`): the base path must match exactly, the `videos` segment in any case (Jellyfin's own `TranscodingUrl` is lower case, the app's direct-stream path is `/Videos/`), and at least one segment must follow. OkHttp has already resolved `.` and `..` (including `%2e%2e`); any segment that is still empty, `.` or `..`, or that decodes to contain `/`, a backslash or `%` (encoded slashes and backslashes, double encoding) is refused. So the route cannot reach `/System`, `/Users`, `/Items` or any other API with the token.
- **A stale route** (`NOT_SIGNED_IN` or `OFFLINE`): the account was signed out; or the selector no longer has exactly that address verified (after a network change it is `Checking`, and a home address on another network may be someone else's machine), until the same address is verified again; or the server's settings or accounts changed, which evicts the route's client from `ServerClients` (`ServerClients.isCurrent`), so a route can never keep sending with old settings such as a withdrawn cleartext consent or an old pin. The player must then ask for a new route.
- **Checked again when sent:** a call that passed when it was made is checked again by `execute` and `enqueue`, and a `clone` is guarded the same way, so a route that went stale between making a call and sending it sends nothing. A response already streaming is not cut off by the guard: the player stops reading when playback ends (`ActivePlayback`).
- **Redirects** are never followed (no client follows them): a 3xx reaches the player as a response.

**Server-supplied paths (`MediaPaths.checkServerPath`).** The app never builds a transcode URL; it plays `MediaSourceInfo.TranscodingUrl` exactly as given, after this check (null means refuse): at most 2,048 characters; starts with exactly one `/` (no scheme, no `//authority`); no white space, control character, non-ASCII, backslash or `#` anywhere; first segment `videos` (any case); every path segment, percent-decoded once, is non-empty unreserved ASCII (`A-Z a-z 0-9 . _ ~ -`) and not `.` or `..` (so `%2e%2e`, `%2f`, `%5c`, `;` parameters and a double-encoded `%252e` are refused); a malformed escape refuses the whole path; then `ApiRequest.checkPath`. Query pairs keep their order and are decoded once (OkHttp encodes them again when sending); a decoded control character refuses the whole path; credential names (`api_key`, `ApiKey`, `X-Emby-Token`, `X-MediaBrowser-Token`, `X-Emby-Authorization`, decoded, trimmed, any case) are removed. Real Jellyfin puts `api_key` in `TranscodingUrl`; the token travels only in the `Authorization` header, and `AuthInterceptor` strips any such name again on the wire. The app's own paths, `directStream` (`/Videos/{itemId}/stream?static=true&mediaSourceId=&tag=`) and `subtitleFile`, refuse ids that are not already validated (`IllegalArgumentException`, fixed message). `StreamSource`, `MediaRoute`, `PlaybackPlan` and `PlaybackReport` never print their contents.

**Known limit:** a 401 on a media request reaches the player as a response; it does not pass through `ServerApi`'s 401 handling, so it does not sign the account out locally by itself (the next `ServerApi` call will). Tests: `MediaPathsTest`, `MediaRouteTest` (real `ServerApi`, `ServerClients` and `HttpClientFactory` against MockWebServer, including a pinned self-signed server).

## Downloads (`data/downloads`)

Milestone 4. What one press does, end to end; each step has its own section below.
- **Tables** (Room v4, see "Download tables" under "Library cache"): `downloads` (the queue row, keyed by server + item: one file per item on the phone, however many profiles keep it), `download_owners` (which profiles keep it, and `fetched`: the one owner whose own sign-in fetched the bytes on the phone), `download_permissions` (the server confirmed THIS profile may download it, with `confirmedAt`), `download_tracks`, `download_segments`, `pinned_artwork`, `download_settings` (per-server "Share downloads between profiles") and `offline_plays`. `DownloadStore` is their one writer and the one writer of `items.pinned`.
- **Pipeline:** the sheet (`DownloadActions`) asks `DownloadPlanner` (online: allowed, playable, size, space) and starts the plan for its own session; `DownloadStore.add` queues it and `DownloadScheduler.kick` starts the one unique WorkManager work; `DownloadWorker` (a `dataSync` foreground worker with a title-free notice) drains `DownloadQueue`, one item at a time: the original through `FileFetcher` on `ServerApi.downloadRoute` (`/Items/{id}/Download` and nothing else), or a conversion through `HlsFetcher` on the plan's own `/videos/` route; then the extras, then `DownloadVerifier` (complete, signature, readable, decodable, length, SHA-256) before COMPLETE. Every step is saved in Room before the next, so a kill, a reboot or a lost connection resumes.
- **Paths:** `DownloadPaths` builds and checks every name (`DownloadBoundaryTest`), on internal storage or, by choice, an SD card's app-specific folder; deletion re-checks the real path and never follows a link.
- **Offline playback:** `SavedCopies` offers a saved copy to the unchanged player (`PlayMethod.LOCAL`, `ItemBytes`), with saved subtitles and skip markers; a LOCAL play writes `offline_plays` and queues its stop in the sync outbox (see "Offline playback").

**The strict sharing rule** (decided after the plan; binding). With "Share downloads between profiles" on, a profile that does not own a COMPLETE download sees it, plays it or inherits it ONLY if the server confirmed that profile's own `CanDownload == true` for the item (a row in `download_permissions`), AND it has its own `visible_items` record for it. Every offline read takes a `Session` and joins `visible_items` (`OfflineLibraryDao.MINE_OR_SHARED`).
- **Who is outside the rule** (final review M-1): only the owner whose own sign-in fetched the copy (`download_owners.fetched`, set by the queue when it starts the bytes under that sign-in, cleared for every other owner). For an original, `/Download` checks that sign-in's own permission; a conversion's `/videos/` does not, so before a fresh conversion under a sign-in that is not yet the fetcher the queue makes one `facts` call for it: true confirms it (dated now) and then marks it, false drops it as an owner (`NOT_ALLOWED` if it is the only one), unknown is `NOT_ALLOWED` and marks nothing (re-review N-1). An owner that inherited the copy, joined it as "already on this phone" (with sharing on or off), or added it while another profile's sign-in fetched it stays under the rule like a non-owner: it is re-asked after 7 days, its stale copy is refused while the server can be reached, and an explicit "no" removes it as an owner (`DownloadStore.refused`; the files go if it was the last owner). With no confirmed permission at all (the server's answer was unknown, so `reconfirm` removed it) such an owner keeps its ownership row but sees, counts, plays and inherits nothing of the ready copy, online or offline, until a later "yes" restores it (`MINE_OR_SHARED`; re-review L-a).
- **Where a confirmation comes from:** the planner's `facts` (a confirmed `true` for a share-only plan; a fresh one restarts an old permission's age), `/Download` serving the file to that profile's own sign-in, and `reconfirm`'s `facts`. A profile can never confirm itself; unknown is not a confirmation. **Age** (`ConfirmationAge`): fresh for 7 days by the wall clock; a confirmation dated more than 5 minutes ahead of the clock is stale too, so setting the date back cannot keep it young (final review L-2).
- **Revocation:** an explicit `false` removes the confirmation at once wherever it is seen (the planner, `reconfirm`, a 403 on `/Download`), and with it the shared copy from that profile's library; the fetching owner keeps it; `reconfirm`'s "no" also removes a non-fetching owner. A refused single-item refresh (403/404) revokes the profile's `visible_items` record, which hides it as well.
- **Re-ask after 7 days, whichever screen is open** (Tasks 13-16 review I-1): `SharingRecheck` runs `DownloadHousekeeping.reconfirm` for the ACTIVE session on a session change, when the connection to its server comes back (`connectionRegained`), and when the app comes to the front (`AppGraph.downloadsInFront`, from `MainActivity.onStart`); the Downloads tab asks for it too. At most one run per profile every 5 minutes (monotonic clock), one at a time, and never while the server cannot be reached; a run with nothing stale is one Room query and no request, and does not count towards the 5 minutes (walkthrough W-3: a profile's first run comes at sign-in, before it has browsed to anything). **At the point of play,** `SavedCopies.plan` refuses a copy this profile's own sign-in did not fetch whose confirmation is stale while the server is `Online`: it asks `SharingRecheck` for the re-ask with that item first (final review L-11) and the item streams meanwhile (the server decides), so a later "no" removes access before the copy is played again. `SavedCopies.media` (the player's saved subtitles and skip markers) applies the same rule (L-3).
- **Offline validity:** while the server cannot be reached, a confirmation that cannot be re-asked stays valid however old (a phone on a plane still plays what the child was allowed to download, and a profile inherits on it). Recorded as a residual risk in `docs/security/milestone-4-check.md`.
- **Removal:** only owners pause, cancel or delete (the store checks; a non-owner's Delete is `NotYours` and the screens show it no control). Delete-for-everyone is Milestone 5. Account and server removal follow "Removal rules".

**Known limits (Milestone 4)**
- No moving downloads between storages (a storage change applies to new downloads only).
- No trickplay previews saved (the app has no trickplay yet).
- A converted download keeps one audio track (the profile's remembered language) and text subtitles; picture subtitles only in originals.
- LOCAL plays send no session reports; their stops reach the server through the sync outbox (`offline_plays` keeps them until a confirmed row covers them).
- Delete for everyone is Milestone 5's watch-and-delete; here a profile deletes only its own ownership (the file goes when nobody keeps it).
- One item at a time (a parameter; parallel downloads only if Ben wants them).
- The notice shows no count, size or progress at all ("Downloading", "Downloads finished"), because the queue is the whole device's (carried Tasks 9-10 Minor 6). The in-app queue line lists the profile's own rows only.
- A profile's own fetched copy is never re-checked with the server while online, and its pinned visibility record only when a screen refreshes the item (final review L-8, for Milestone 5). Any profile may switch sharing on (L-9, Milestone 7's app lock).
- A kick can race a worker that WorkManager starts between reading its state and `REPLACE` (Tasks 13-16 review M-4): the just-started drain is cancelled and the replacing work starts at once, requeueing what was RUNNING (a resume, never a wrong file). Accepted.

## Download call path (`ServerApi.downloadRoute`, `DownloadGateway`, `HlsPlaylists`)

- **`ServerApi.downloadRoute(session, itemId)`** (internal): `mediaRoute`'s steps 1 to 3 exactly, nothing sent. Its `GuardedCallFactory` gets `exactPath = <base segments> + Items/<itemId>/Download`: besides `/videos/`, GET and HEAD may reach that one path for that one validated item, segment for segment (case-sensitive, except the fixed words `Items` and `Download`). Another item's download, `/Items/<id>/File`, `/Items/<id>`, a longer path and any other API stay refused; the method, target, segment and staleness rules are unchanged. An item id that is not a normalised `JellyfinId` is `SERVER_NOT_FOUND`. `mediaRoute` has no exact path, so the player's route cannot reach `/Download` (`DownloadRouteTest`).
- **`DownloadGateway.facts(s, ids)`**: GET `/Items?ids=<≤50, comma-delimited>&userId=&fields=CanDownload,MediaSources&enableUserData=false`, chunked; ids normalised and refused (`SERVER_NOT_FOUND`) before sending if not GUIDs; body at most 4 MiB; elements decoded one at a time. `CanDownload` counts only as a JSON boolean (absent, null or another type is unknown: originals only). One source: the one whose `Id` (normalised) is the item's id, which is the file `/Items/{id}/Download` sends (Jellyfin may list a wider alternate version first: Tasks 5-8 review I-4), else the first of at most 64: `Id` and `ETag` `[A-Za-z0-9]{1,64}`, `Container` the first comma-separated name lower-cased `[a-z0-9]{1,16}`, `Size` a whole JSON number in 1..256 GiB, else null. Ids not asked for are dropped; a repeat keeps the first (`DownloadGatewayTest`, `DownloadGatewayHostileTest`).
- **`HlsPlaylists.parse(text, playlistPath)`** (pure): at most 2 MiB of text and 20,000 segments; `#EXTM3U` first (a BOM and CRLF are tolerated); any other control character refuses the whole playlist; lines cut to 4,096 characters. A master's first `#EXT-X-STREAM-INF` variant is taken and must be a `.m3u8` path. A media playlist must be VOD (`PLAYLIST-TYPE:VOD` or `ENDLIST`), carry `TARGETDURATION` 1..60, and every `#EXTINF` 0 < d ≤ 60 s. Refused outright: `#EXT-X-KEY` other than `METHOD=NONE`, `#EXT-X-MAP`, `#EXT-X-BYTERANGE`, `#EXT-X-DISCONTINUITY`, a URI with a scheme, `//` or a leading `/` (paths are relative to the verified address, which holds the base path, so a root-relative URI would be misread), and any segment not ending `.ts`. Relative URIs are joined to the playlist's folder and must then pass `MediaPaths.checkServerPath` (so `/videos/` first, no `.`/`..`, credential names stripped). Refusal reasons are fixed words. `writeLocal(ms)` writes the app's own VOD playlist naming `seg-00000.ts`... by index only (`HlsPlaylistsTest`).

## Download planner (`DownloadPlanner`, `OriginalChecks`, `PlaybackResolver.checkOriginal`)

What one press will download, before anything is queued. Online only: OFFLINE and every other `AppError` from the server's answers are thrown as they come (an expansion with nothing saved still asks the server about the target itself, so offline is never "nothing to download").

## Resumable fetching (`FileFetcher`, `HlsFetcher`, `FetchSupport`)

Every byte comes through a route `ServerApi` handed out (`downloadRoute` for the original, the plan's own route for a conversion), so the pin, client certificate, custom headers and cleartext rule apply; no client is built here and no redirect is followed. Results are `FetchResult` (`Done`, `Failed(failure)`, `Retry(kind)`, `Unauthorised`, `RestartConversion`); nothing from the server reaches a result, a log or a message.

**`FileFetcher.fetch`** (correct whatever the server does with `Range`, Task 1):
- **Request:** `GET /Items/<id>/Download`, `Accept-Encoding: identity`. Resuming from Room's fsync'd count: the part file is cut to it first (a torn tail; a part shorter than the count starts again from zero), then `Range: bytes=<n>-`, plus `If-Range` with the stored validator. The stored validator is only ever one an earlier response for this file sent (`ETag` as sent, else `Last-Modified`, 1..128 characters of 0x20..0x7E, so HTTP dates pass); the media source's `ETag` is never sent, and with none, no `If-Range` is sent.
- **Refused before writing:** a surely-not-media type (`text/*`, any `html`, `application/json`, `application/xml`) or a `Content-Encoding` other than identity: `Failed(SERVER_ERROR)`.
- **200:** `Content-Length` must equal `Size` when both are known (else `CHANGED_ON_SERVER`); chunked only when `Size` is known, read to one byte past it at most (then `CHANGED_ON_SERVER`). When resuming, a 200 means Range was ignored or If-Range did not match: the file is cut to zero, Room is told so at once (`(0, total, new validator, restarts)`, so it never claims bytes the part no longer holds: review Minor 2), and the file is written whole. That restart counts only when the response's validator differs from the stored one; three in a row is `CHANGED_ON_SERVER`, and a same-validator restart resets the count. A first start on INTERNAL reserves the space (`Volumes.reserve`, by volume; a refusal is `NO_SPACE`).
- **Space (final review M-2):** the queue passes its one space rule (`QueueSpace.fits`: free space above the reserve, 1 GiB internal, 256 MiB card, saturating) as `fits`; it is asked before the first byte of a 200 (`total - from`, the cut part's bytes being freed), and of a 206 when neither `Size` nor a stored total was known, so a server that states no size cannot fill the storage past the reserve. Every `NO_SPACE` (refused, the reservation failing, or `ENOSPC` part-way) cuts the part to zero and tells Room, so a failed download keeps no space.
- **206:** only to a ranged request, from the same version of the file: its validator must equal the `If-Range` sent (a different or absent one is another file: an ASP.NET date `If-Range` means "not modified since", so a replacement dated earlier is served as a 206), and with `Size` unknown its total must equal the total Room stored (`storedTotal`); either is cut to zero and counted as a validator change (Tasks 5-8 review I-2). Then `Content-Range: bytes <n>-<total-1>/<total>` exactly, total in 1..256 GiB and equal to `Size` when known (else `CHANGED_ON_SERVER`), and a matching `Content-Length`. Anything else, or a 206 to an unranged request, cuts to zero and is `Retry(SERVER_ERROR)` (an attempt, not a validator restart).
- **416:** a part already the whole file (by `Size`, else the stored total, else `bytes */N`; a header total that disagrees with the known one is another file) is Done; otherwise cut to zero and retried.
- **Statuses:** 401 `Unauthorised`; 400 and 403 `NOT_ALLOWED` (400 is Jellyfin's answer for an item with no file; the server's answer wins over `CanDownload`); 404 `GONE_FROM_SERVER`; 3xx `Retry(SERVER_NOT_FOUND)`; 5xx `Retry(SERVER_ERROR)`; other 4xx `SERVER_ERROR`.
- **Errors:** a route refusing as stale is `Retry(OFFLINE)` (the queue asks for a new route), signed out `Failed(SIGN_IN_NEEDED)`; `ENOSPC` anywhere in the cause chain (`ErrnoException`) is `NO_SPACE`; any other IOException is a retry, keeping what was fsync'd (the count on disk is forced and saved first). Cancelling cancels the call and saves nothing more.
- **Stalls (review Minor 5):** a body must bring 64 KiB in every 60 s (`StallRule`), enforced by a `StallGuard` moving the deadline of the body's own okio timeout, so no new client is built; a stall is `Retry(TIMEOUT)`.
- **Writing:** a `FileChannel` opened for append; `force` before each progress save (every 2 s or 8 MiB, on a failure, and at the end), so Room never claims bytes that are not on disk; never more than the total. Then the part is renamed to `media.<ext>` in one step.

**`HlsFetcher`** (correct whether or not a server cuts the same segments twice):
- `open(resolved, folder, runtimeMs)`: a TRANSCODE plan with a validated HLS source only; deletes `hls/` first (so after process death a conversion always starts from segment 0 and two sessions' segments are never mixed); fetches the master and media playlists through the plan's route (at most 2 MiB each, parsed by `HlsPlaylists`, so a playlist naming anything outside `/videos/` is refused before any segment request); each playlist call has 60 s in all (`call.timeout()`, review Minor 5); the duration sum must be within 10% of the runtime when known (the converted source's own `RunTimeTicks`, else the item's: controller walkthrough W-1); the conversion's **budget** is 2 x its quality's bitrate / 8 x the longer of the playlist's sum and the runtime, plus 8 MiB, never above the planned size x 3 + 8 MiB (`ConversionSpace.plannedBytes`), and on INTERNAL it is reserved (`Volumes.reserve`, by volume; a refusal is `NO_SPACE`) (Tasks 5-8 review I-3); writes `hls/local.m3u8` (fsync'd). A 404 on a playlist is `RestartConversion`. The `LiveConversion` lives only in memory (the queue's).
- `fetch(live, folder, from)`: before each segment the volume must have that segment's cap free above the plan's reserve (1 GiB internal, 256 MiB on a card), else `NO_SPACE`; the segments already saved count towards the budget; each segment at most its cap, max(4 MiB, 2 x the bitrate x its duration) and never above 64 MiB, and at most what is left of the budget (declared or read; past either is `SERVER_ERROR`); a trickle is cut by the `StallGuard`; not surely-not-media, not compressed, first byte `0x47`, the declared length if any; written to `seg-<n>.ts.part` (`DownloadPaths.segmentPartFile`), fsync'd, renamed to `seg-<n>.ts`, and only then reported. A 404 or 5xx is `RestartConversion` (the server reaped the session); an IOException is a retry within the same session; 401 is `Unauthorised`; nothing is retried in a loop here.

## Download queue (`DownloadQueue`)

Room is the queue; `DownloadQueue.drain` (one at a time, a `Mutex`) runs it for the worker. Every step's result is written to Room (`DownloadStore.update`, which says false when the row is gone) before the next starts. At the start of a drain RUNNING and VERIFYING rows go back to QUEUED. Rows are taken in queue order (`DownloadStore.next`, QUEUED only, so PAUSED rows are skipped) and marked RUNNING under a second lock, `whileNoneStarts`, which Task 12's orphan sweep holds while it reads `sweepInputs()` and sweeps, so nothing can start in between.
- **One item:** the earliest owner (`download_owners.addedAt`) that still has a token fetches (none: `SIGN_IN_NEEDED`). **Every byte through one sign-in** (final review L-7): unless that owner is already the fetcher (`download_owners.fetched`), any `.part` or `media.<ext>` is deleted and Room's count, total and validator cleared before it fetches, and it becomes the fetcher (a conversion marks its fetcher when a fresh session opens, after asking `facts` for a sign-in that is not yet the fetcher: re-review N-1; a held one is reused only by the same session). **Owners and permissions (Tasks 9-10 review I-2):** an original served to the fetcher's own sign-in confirms its permission; a `NOT_ALLOWED` for the fetcher drops it as an owner (when another owner remains) and the item is taken again by the next owner; before COMPLETE every other owner whose permission was never confirmed stops owning it, so nobody keeps a copy fetched under another profile's permission. `DownloadStore.add` adds an owner to an existing copy only for a share-only plan item with a confirmed permission (a copy that appeared after a plan for a new download is Skipped). The item folder on its recorded storage (a card that is out: `STORAGE_MISSING`). Free space above the reserve (1 GiB internal, 256 MiB card) for what is known to remain (an original's stored total, a conversion's bitrate estimate) before any request; an original's `Size` is checked again after `checkOriginal`, before the file is asked for (`NO_SPACE`).
- **Original:** `checkOriginal` again (`OriginalChecks.of(info, itemId)`); not playable now is `NOT_PLAYABLE`, never a silent conversion. Then `extras.tracks`, `downloadRoute`, `FileFetcher.fetch` from the row's `doneBytes`, `validator`, `totalBytes` (`storedTotal`) and `restarts`, with `Size` as `expectedBytes`; the progress callback writes all four values. A `media.<ext>` with no `.part` (renamed before the process died) goes straight to the check only if this same sign-in is the fetcher (its own `/Download` served it); a file fetched under another owner's sign-in is deleted and fetched again under this one, even when this owner's permission is confirmed (Tasks 11-12 review Minor 2, final review L-7). The file is named by `OriginalCheck.Playable.container`, and any `media.<other>` (and its `.part`) left from an earlier container is deleted first (the sweep keeps every allowed media name, so it would not). The media source id written to Room is always one the server's answer passed `MediaPaths.isSafeId` with (`OriginalChecks`, `PlaybackDecision`). There is exactly one `DownloadQueue` per process, `AppGraph.downloadQueue`, which the worker drains (`AppGraphDownloadsTest`).
- **Conversion:** a live conversion in memory for this item, from this process and younger than 30 minutes (monotonic clock), opened for THIS row by THIS account (`HeldConversion`: the same `requestedAt` and quality, the row's container already HLS, and the same fetching session; Tasks 11-12 review I-4, Tasks 13-16 review M-3), continues the same play session at `segmentsDone`; a removed download's is forgotten (`DownloadQueue.forget`, from `DownloadRepository.remove`), and one held for an older row is never reused. Otherwise: for a sign-in that is not yet the copy's fetcher, one `facts` call for its own `CanDownload` first (true confirms it; false drops it as an owner, or `NOT_ALLOWED` for the only one; unknown is `NOT_ALLOWED`: re-review N-1); a PlaybackInfo that sets up no conversion (`checkOriginal`) gives the item's tracks; `TrackChooser` picks the audio with the session's remembered choice for the series and the phone's captions; then `resolve` with `forceTranscode = true` at the row's quality, which must be a TRANSCODE plan with an HLS source (else `SERVER_ERROR`); `extras.tracks` with only that conversion's audio track; `HlsFetcher.open` (which deletes old segments) with `ConversionSpace(storage, volumeId, estimate)`; `segmentsDone = 0`, the live conversion kept, and fetch from 0. Two sessions' segments are never combined. `RestartConversion` drops it, sets `segmentsDone = 0` and counts an attempt, and starts a fresh session at once.
- **Extras** (`segments`, `artwork`) are best effort. **VERIFYING:** `DownloadVerifier.verify`, its length checked against the downloaded source's own runtime (`OriginalCheck.Playable.runtimeMs`, or the conversion plan's), else the row's item runtime (controller walkthrough W-1); Good is COMPLETE with `sha256`, `completedAt`, `verifiedAt` and attempts 0. A first Bad deletes the media (the extras stay), records the failed check in `verifiedAt` and queues it again from 0; a second Bad is `CHECK_FAILED` with the item folder deleted. A UI retry clears `verifiedAt`.
- **Sign-in on media:** `Unauthorised` makes ONE `DownloadGateway.facts` call through `ServerApi`: 401 (the account is signed out locally) is `SIGN_IN_NEEDED`; an answer is `SERVER_AUTH_REFUSED`; anything else a retry.
- **Retries and attempts:** a fetcher's or server call's `Retry(kind)` puts the row back to QUEUED with `attempts + 1` and ends the drain with `QueueRun.Retry(kind)`; the live conversion stays in memory. `Retry(OFFLINE)` first gets one new route (`downloadRoute` again, or `resolver.reroute` for the same session). A cut to zero after bytes were held (a 200 to a resume) and a `RestartConversion` count too. At 8 attempts: `SERVER_ERROR`. Any other exception in an item's run (a card remounted read-only, say) is one attempt too (logged by class), so no item can stay RUNNING at the head of the queue (Tasks 9-10 review I-3); the file fetcher's truncate before a resume is inside its own error handling. A `NO_SPACE` or a retry for a row whose card is no longer mounted is `STORAGE_MISSING` (a pulled card reads as no space or an I/O error; review Minor 5). Server refusals map to `SIGN_IN_NEEDED`, `NOT_ALLOWED`, `GONE_FROM_SERVER` and `NOT_PLAYABLE`. `Failed(f)` is `FAILED(f)` and the queue moves on.
- **Pauses win (Tasks 9-10 review I-1):** the queue takes a row only with `UPDATE … SET state='RUNNING' WHERE … AND state='QUEUED'` (`DownloadStore.claim`), and every later write is `DownloadStore.updateIf(key, {RUNNING, VERIFYING})` in one transaction. A row paused meanwhile stops at its next write and is left PAUSED with its part file and its live conversion (a resume continues the same session); a retry, a stop, a failure or a check never overwrites a pause.
- **Never COMPLETE without a name for its file:** before the check, the row must have a safe media source id and a container whose entry is the file fetched (`QueueSpace.names`), and `DownloadVerifier` refuses a copy with no safe media source (`record`), so every COMPLETE row can be opened by `SavedCopies` and `recheck`.
- **Stopping and deletion:** `shouldStop` between items and at every progress save (the row goes back to QUEUED, the live conversion is kept). A row deleted while running (cancelled, account or server removed) is found at the next write, or after the item's run when its step ended in a retry or a failure (final review L-5): the item's folder is deleted, its live conversion dropped, and the queue moves on.
- **`recheck(key)`** (after a saved copy failed to play): `DownloadVerifier.recheck` against the stored hash; a mismatch is `FAILED(DAMAGED)`.
- **Seams:** the queue drives `OriginalFetch`, `ConversionFetch`, `DownloadExtras` and `PlayableCheck` (`QueueSeams.kt`), each implemented by one production class. Logs are fixed words and enum names only.

Tests: `DownloadQueueTest`, `DownloadQueueFailureTest` (scripted fakes over in-memory Room, the real `PlaybackResolver` over `FakePlaybackGateway`, real `DownloadPaths` over `FakeVolumes`; `ShadowLog` for the logging check).

## Downloads in the background (`DownloadWorker`, `DownloadScheduler`, `DownloadNotifications`, `ShoalwatchWorkerFactory`)

WorkManager only drains the queue in Room; it holds no state of its own that matters.
- **One unique work**, `shoalwatch-downloads` (`DownloadScheduler.kick`: KEEP only while the worker is RUNNING, so it is never cancelled by a kick; otherwise REPLACE, so work waiting out a long backoff (up to WorkManager's 5-hour cap after a night of retries) starts again at once when the app comes to the front or the user acts (Tasks 11-12 review I-3); a state that cannot be read keeps it. Always REPLACE when "Use mobile data" changes while anything is queued, so the new constraint applies). Constraints: `UNMETERED` while mobile data is off (the default, SPEC §3 row 10), `CONNECTED` when allowed, and storage not low. - **`DownloadWorker`** (a `CoroutineWorker`, from `work-runtime` alone): a foreground worker of type `dataSync` (`ForegroundInfo(4201, …, FOREGROUND_SERVICE_TYPE_DATA_SYNC)`; a refused foreground start still lets the work run). ## Downloads seam (`Downloads`, `DownloadRepository`)

What screens use (`AppGraph.downloads`). - **The rule (`ReleaseStore.release`, one transaction under the library write lock).** SAFEGUARDING first: the download must be one the profile may see (`OfflineLibraryDao.getPlayable`: COMPLETE, its own `visible_items` record, its own or shared), else `NotYours` and nothing changes, the same answer as for no download at all. - **`release(s, id, together)`:** a download `s` may not see is `NOT_YOURS` with nothing changed, not even watched. Otherwise, **from the player while the copy is open** (`LocalPlaying.watchedWhileOpen`, one atomic check that also remembers the press for that profile), watched on this phone only: `OfflinePlays.watched` first (a process that dies before the stop still sends watched: recovery queues PLAYED, never a count), then `LocalPlaystate.markWatchedHere` (nothing queued, no refresh; the pending marker kept, past the queue's idle clean-up too, since the item has an offline play, `ItemDao.NO_OFFLINE_PLAY`); the coming LOCAL stop is then a finished watch whatever it reports (`LocalPlaying.takeWatched`; from that take until the copy is let go, a press by that profile goes the "anywhere else" way below, so it is never left over to force a later play: Tasks 13-14 review M1), and its one PLAY carries it, so one watch counts once (Tasks 11-12 review I1). **From anywhere else**, `Playstate.setPlayed(s, id, true)` (the outbox: queued and sent as `s`); with `together`, the same for each of `ReleaseStore.sharers` (`HousekeepingDao.SHARERS_SQL`: other accounts on the same server with their own `visible_items` record that see the shared COMPLETE copy, sharing on, and signed in), each into that profile's OWN outbox; a mark that fails for one of them is skipped and the release goes on, never half-done (Tasks 11-12 review M3: `SERVER_NOT_FOUND`, the item no longer shown to that profile, silently; any other failure logged by its kind; EVERYONE then keeps the download if that profile has not watched it); then auto-download next's `remember` (while the download, and so its quality, can still be read), then the rule (told directly that `s` has watched: `ReleaseStore.release(..., watchedBy)`, so EVERYONE never depends on the saved tick), then `onWatched` (only from outside the player: in it, the stop's `onLocalFinished` runs auto-download next once; Tasks 13-14 review M2). ### Auto-download next (`AutoDownloadNext`, `auto_next_requests`)

Per profile, Off by default (`profile_download_settings.autoNextCount`: 0, 1, 2, 3 or 5; "Download next episodes automatically" in Download settings). Triggered only by a downloaded episode finished in the player or released (the two `HousekeepingRepository` hooks), never by a tick in a list.
- **`remember(s, id)`:** nothing while Off, or for a download `s` may not play (`HousekeepingDao.playable` = `OfflineLibraryDao.PLAYABLE_SQL`), or for anything but an episode of a series. Otherwise one request per (profile, series) is upserted (the newest anchor wins) with the anchor's own quality, before a release can delete its row. The same anchor is remembered once per process (an in-memory set of the last 256), so the press and the stop of one watch plan once. Requests cascade with the account.
- **`runPending(s)`** (one at a time, under a mutex; never throws), per request: Off since → it goes; metered (`QualityDefault.activeNetworkMetered`, a failure counts as metered) with "Use mobile data" off → kept (the next Wi-Fi network re-probes the server, which comes online again); otherwise `Downloads.prepare(s, NextUnwatched(series, anchor, count), defaultQuality ?: anchor's)` then `start`. Nothing to fetch, or started → it goes. `enoughSpace == false` → nothing started, `blockedAt` set (Storage says so), unless every planned item is already on the phone (share-only, 0 bytes): that plan is started, so the reserve never blocks it (Tasks 13-14 review M3). `OFFLINE`, `NETWORK`, `TIMEOUT`, `NOT_SIGNED_IN` → kept. After a `NETWORK` or `TIMEOUT`, that server's `cameOnline` is ignored for 1 min, doubling to 30 min (memory only; a run the server answers ends it), because such a failure makes `ServerApi` re-probe and the probe's new Online is itself a `cameOnline`, which would otherwise re-plan without end on a slow link (Tasks 13-14 review M4); a start, a watch, a Wi-Fi run after `OFFLINE`, and a return after the server was seen Offline (`OnlineEvents.Reconnection.afterOffline`, as for sync) are never paused. Anything else → `tries + 1`, dropped at `MAX_TRIES` (5). A delete or update matches the request as read (anchor and time), so a newer anchor written meanwhile stays.
- **`start()`** (`ShoalwatchApp.onCreate`): runs every waiting request once, then again whenever its server comes online (its own `OnlineEvents` over the servers with requests).
- **SAFEGUARDING:** the plan is `Downloads.prepare`'s: only items the server shows this profile, its own `CanDownload` decides (a refusal for an account is `NOT_ALLOWED`, skipped), and the queue's own constraint still keeps the bytes on Wi-Fi. `NextUnwatched` (planner) is the first `count` unwatched episodes after the anchor in `numbered`'s order (Specials never); an anchor in Specials or not listed plans nothing.

**Known limits (housekeeping)**
- A release pressed just before the process dies keeps watched (and the row is gone), but leaves the files to the next start's orphan sweep.
- Auto-download next follows only downloaded episodes finished in the player or released; a tick in a list, or an episode streamed online, plans nothing.

## Removal rules (`DownloadHousekeeping`)

Wired to `ServerStore`'s hooks in `AppGraph`; each runs in the app scope on IO.
- **Server removed:** its rows, owners, extras, settings and pinned-artwork rows cascade with the server; housekeeping deletes `<root>/<serverId>` on every mounted root. A running item of that server finds its row gone at its next write, stops and deletes its folder. A card that was out is cleaned by the next start's orphan sweep (the server is no longer saved).
- **Account removed** (sign-out removes it here): its owners and offline plays cascade; then `DownloadStore.afterAccountGone`: with sharing on, each download left with no owner passes to every remaining account on the server that has a `visible_items` record for it (it was already in their offline library); only accounts whose own permission the server confirmed (`download_permissions`) qualify, and while the server can be reached only with a confirmation younger than 7 days and not dated ahead of the clock (final review M-1, L-2; offline any age); otherwise, or with no such account, it is deleted, rows, files and its pinned pictures. An heir did not fetch the copy, so it stays under the strict sharing rule. Nothing of the removed account's is left on disk that another profile could not already see. **An expired sign-in** (`invalidateToken`, a 401) calls the same hook but keeps the account row, so its owners stay and nothing is deleted.
- **Start** (`ShoalwatchApp.onCreate`, once per process): interrupted rows back to QUEUED only while no drain runs (`DownloadQueue.requeueIfIdle`); the orphan sweep with `DownloadStore.sweepInputs()` inside `DownloadQueue.whileNoneStarts` (null, so no sweep, while anything is RUNNING or VERIFYING); pinned pictures whose item no download pins any more, row and file; then a kick if anything waits.
- **`reconfirm(s)`** (run by `SharingRecheck` on a session change, the server coming back, the app coming to the front, a stale copy about to play, and the Downloads tab; rate limited): up to 50 downloads (and their series) this profile holds under the strict sharing rule (shared to it with sharing on, or owned without its own sign-in having fetched them) whose visibility record is older than 7 days, or whose permission is missing, was **confirmed** more than 7 days ago (its own age, `download_permissions.confirmedAt`, independent of browsing, which keeps the visibility record fresh; Tasks 11-12 review I-1) or is dated ahead of the clock (L-2), the item about to play first (L-11), then oldest confirmation first, are asked again (`Library.refresh(s, Item(id))`; a 403 or 404 revokes that profile's record, so the item is hidden from it at once while the owner still sees it), then one `DownloadGateway.facts` call records the profile's own `CanDownload`: true confirms it again (an upsert: `confirmedAt` = now), false removes the confirmation and a non-fetching ownership (`DownloadStore.refused`), unknown removes the confirmation. It stops when offline, unauthorised or not signed in, or on a transport or identity failure (network, timeout, TLS, cleartext blocked, client certificate, server mismatch or unsupported, secure connection lost, connection changed: re-review L-d), so a hanging server ends the pass at once; a server error, a refusal or anything unknown for one item's refresh skips that item and carries on (final review L-1). It is asked again next time.
- **Revocation:** an explicit `CanDownload == false` removes this profile's permission at once wherever it is seen: the planner (`DownloadPlanner.decide`), `reconfirm`'s `facts`, the queue's `facts` before a conversion (re-review N-1), and a 403 on `/Download` for that profile (`DownloadStore.dropRefusedOwner`, last owner or not).
- **Offline, a confirmation still counts** however old it is (deliberate: a phone on a plane must still play what the child was allowed to see). It is only re-asked, and can only be withdrawn, once the server can be reached.

## Checked playable (`DownloadVerifier`, `SavedMediaProbe`, `ItemBytes`)

A finished download is marked COMPLETE only after `DownloadVerifier.verify` says `Good(sha256)`. The checks, in order (a `Bad` reason is a fixed word for the log):
1. **complete** (`incomplete`): an original's length equals the expected bytes (an unknown length is never complete); a conversion's `local.m3u8` names `seg-00000.ts` onwards in order, each a non-empty regular file, `hls/` holds exactly those and the playlist (a leftover `.part` fails), and the count equals the planned shape when known. The entry's real path must be inside the item folder, and no file may be a link.
2. **signature** (`signature`): `ftyp` at offset 4 for mp4, m4v and mov; `1A 45 DF A3` for mkv and webm; `0x47` at 0, 188 and 376 for ts, on every segment of a conversion. Any other extension fails.
3. **readable** (`unreadable`, `no-video`, `no-audio`): the probe finds a video track, and an audio track unless the item listed none (`audioListed`).
4. **decodable** (`video-codec`, `audio-codec`): every video MIME type is in `DirectPlayVideo.media3Types`, the one list the device profile also offers the server for direct play (h264 always, the counted codecs, and `video/dolby-vision` with HEVC: Media3 1.9.2's Matroska and MP4 extractors name a DV track so, checked in the 1.9.2 bytecode; Tasks 9-10 review I-4); one audio MIME type maps to a counted audio name.
5. **length** (`length`): the probe's duration within 5% of the runtime (10% for a conversion) when both are known: the runtime of the media source actually downloaded (its `RunTimeTicks` from PlaybackInfo, bounded by the mapper, positive only), else the item's (controller walkthrough W-1: an item's headline runtime may differ from the chosen version's).
6. **fingerprint:** SHA-256 of the media (a conversion's segments in order), read again from disk; `recheck` compares it later (after a playback failure, or "Check again"). It detects later damage; a splice made while downloading is prevented by the fetchers' validator checks, not by the hash.

- **`SavedMediaProbe`:** Media3's `MetadataRetriever.Builder(context, item).setMediaSourceFactory(...)` (present in 1.9.2) with `retrieveTrackGroups` and `retrieveDurationUs`, over a media source factory built like the player's (ItemBytes, the picture-only subtitle parsers) whose network is a `Call.Factory` that refuses everything; at most 30 s in all, then null. Errors are logged by exception class only.
- **`ItemBytes`** is the one `DataSource` the player and the probe use. It reads the current `EngineItem` at every `open`: http(s) only while it is remote; `file:` only while it is saved and the file's real path (links resolved, `toRealPath`) lies strictly inside the real path of its folder; anything else (no item, another scheme, `../`, another item's folder, a link leading out, a missing file) fails at `open` with an `IOException` wrapping `BlockedRequestException(FORBIDDEN)` and a fixed message. **`SavedMediaDataSource`** (not a network source) reads with `RandomAccessFile`, honours the spec's position and length, and refuses anything that is not a regular file or is a symbolic link.
- **`EngineItem`** is remote (route + source) or saved (`SavedMedia`), never both; `MediaItems.build` gives a saved copy its entry's `file:` URI (HLS marked as such). `SavedMedia` (folder, entry, quality, media source id) is never printed.

## Offline playback (`SavedCopies`, `SavedPlans`, `SavedFirstPlaybackGateway`, `LocalPlaybackReports`, `OfflinePlays`)

A download plays through the unchanged `PlaybackController` (SPEC §4 rule 1: no separate offline mode); the controller changed by one line (`engine.load(resolved.engineItem(), …)`).
- **Which copy plays.** `SavedCopies.plan(session, itemId)` is THE lookup (the resolver's `saved` and the gateway's `saved`). It offers a copy only when `OfflineLibraryDao.getPlayable` returns it (COMPLETE, the session's own `visible_items` record, and owned or shared under the strict rule with the session's own confirmed permission), its storage is mounted (`DownloadPaths.itemFolder` not null), and a cheap check passes before every play: an original's media file is the recorded length; a conversion's `local.m3u8` and every recorded segment are there. For playback (`plan`) and its extras (`media`), a copy this profile's own sign-in did not fetch whose confirmation is stale (over 7 days, or dated ahead of the clock) is not offered while the server is `Online`: the re-ask is asked for, that item first, and the item streams (`OfflineLibraryDao.sharedConfirmedAt`; offline it still plays). Every path comes from `DownloadPaths`. Anything else: the item streams as before.
- **`PlaybackResolver.resolve`:** with no forced conversion and no burn-in, the saved copy wins and nothing is asked of the server (quality ignored). `Resolved` holds a route OR a `SavedMedia`, exactly one, and a saved one is always `PlayMethod.LOCAL`. `reroute` hands a saved one back unchanged.
- **`SavedPlans.plan`** (pure): tracks from `download_tracks` (subtitles only where a file was saved, or a PICTURE track inside an original's own file), segments known, no play session, `source` a placeholder never used for an address.
- **Tracks (`TrackRules`):** LOCAL is switched in the player as DIRECT_PLAY is (audio, picture subtitles in the stream, text as FILE) and never asks the server: a language disagreement keeps the player's track, burn-in and "let the server draw" are not offered, and the quality sheet says "This is the copy saved on this phone, so its quality can't be changed."
- **Failure:** a DECODER or FORMAT failure falls back once: `fallBack` tells `savedFailed` (`DownloadQueue.recheck`, in the app scope: DAMAGED if the fingerprint changed), then asks the server for a forced conversion; offline that is the gateway's `OFFLINE`. A second failure is PLAYBACK_FAILED.
- **`SavedFirstPlaybackGateway`** is the `PlaybackGateway` the controller and `SubtitleLoader` get (`AppGraph.playerGateway`): for a saved copy of the same media source, a saved subtitle file's bytes (a regular file, not a link, real path inside the copy's folder, at most 8 MiB, then parsed by the same `SubtitleFiles` parsers), and the saved segments. Everything else is the server's. The download queue's own extras still use the server gateway.
- **Reports:** `RoutedPlaybackReports(server, local)`: a LOCAL report goes to `LocalPlaybackReports`, everything else to `ServerPlaybackReports`; `PlaybackGatewayImpl` refuses a LOCAL report outright (no session report is ever sent for one). `started` opens the copy in `LocalPlaying` (memory only: which saved copies the player holds, so a released download's files go only once it lets go; `whenClosed` runs an action at once, or when the last holder closes) and writes `offline_plays.positionMs`, as does `progress` (process death keeps it); `stopped` writes `offline_plays` first (`played` set once finished and never cleared, `playedAt` set once), then `LocalPlaystate.recordLocalStop` (the local value AND its outbox row in one transaction: a finished watch is one `PLAY` at the stop's time, otherwise a `POSITION`, both `fromOfflinePlay`), then closes the copy, then, for a finished stop that was saved, calls `onFinished(session, itemId)` (`HousekeepingRepository.onLocalFinished`: see "Watch-and-delete"). The outbox sends it when the server can be reached, so **a saved copy played while online reaches the server too** (Milestone 4 sent nothing for any LOCAL play). Once a confirmed row covers the `offline_plays` row (written at or before the row's time) the landing deletes it (`OfflinePlayDao.deleteCovered`); so does a heard online stop of the item, up to the stop's own time (`recordStop(..., reached = true)`; Milestone 5 re-review m1).
- **Recovery at start** (`AppGraph.startSync`, from `ShoalwatchApp.onCreate`, before `SyncScheduler.start()`): `OfflinePlays.recoverUnqueued` queues every `offline_plays` row that no outbox row from an offline play covers (`OfflinePlayDao.unqueued`) in an idempotent form at the row's own time: played is `PLAYED true`, otherwise `POSITION`. It covers a process that died mid-play (positions every 10 s, no stop) and the instant between a stop's two writes, and never queues a PLAY, so it can never add a play count. Running it twice queues nothing new. It never replaces a newer unsent change of the same kind for the item (`OutboxStore.enqueueUnlessNewer`, one transaction; Tasks 6-8 review M2): a later "remove from Continue Watching" or "unwatched" is what the user did last.
- **Markers survive:** the start-up sweep's snapshot and the idle clean-up (`ItemDao.pendingRows`, `clearPendingFor`) skip any `user_data` row that has an `offline_plays` row (`ItemDao.NO_OFFLINE_PLAY`), so a refresh cannot undo an offline watch before it is sent (SPEC §3.2).
- **Player text:** "Playing the copy saved on this phone." plus, for a conversion, "Saved in High quality (1080p)." (Medium 720p, Low 480p), from `PlaybackState.savedQuality`.

## Device profile (`DeviceCapabilities`, `HdrPolicy`, `DeviceProfileBuilder`)

What the phone can play, told to the server with every PlaybackInfo, so the server direct plays what will really show and converts the rest. All in `data/playback`; only the adapter touches Android.

- **`AndroidDeviceCapabilities`** (the `CodecSupport` used in the app; read once per player opening): decoders from `MediaCodecList(REGULAR_CODECS)`, encoders ignored. **Which video decoders count** (`DecoderRules.counted`, pure, over plain `DecoderInfo` the adapter fills in): hardware ones only, never an alias or a `.secure` one; AOSP's software HEVC, VP9 and AV1 decoders exist on practically every phone and cannot keep up with high-resolution or 10-bit video, so they never make a codec, a 10-bit flag, an HDR type or a level "supported". The exception is h264, which every Android device must decode: its software decoders count only when no hardware one exists (so they cannot raise the hardware level). Audio counts any decoder of the type. Video codecs h264, hevc, vp9, av1 by MIME type; audio by MIME type to the Jellyfin names aac, mp3, opus, flac, vorbis, ac3, eac3, dts, truehd. The highest AVC level becomes the Jellyfin level number (5.1 is 51; 41 when none is reported). 10-bit: HEVC Main10 (or Main10HDR10/HDR10Plus), VP9 Profile 2 or 3 (any HDR variant), AV1 Main10 (or its HDR variants). Decoder HDR: the `...HDR10` profiles are HDR10 and `...HDR10Plus` are HDR10+ (Android has no HLG profile, so HLG is judged on the 10-bit flag). Dolby Vision profiles from `video/dolby-vision` decoders (`DvheDtr` 4, `DvheStn` 5, `DvheDtb` 7, `DvheSt` 8, `DvavSe` 9). The screen: the default display's `HdrCapabilities` types, plus (API 34 and later) the current mode's `supportedHdrTypes`. No audio channel count is read or sent: Media3 downmixes what the phone decodes, and a channel cap (`PlaybackInfoDto.MaxAudioChannels`) would make the server convert 5.1 AAC, Opus or FLAC that plays as it is. **It never throws:** any platform failure gives the minimal profile (h264 + aac, level 4.1, SDR, stereo), logged by exception class only.
- **`HdrPolicy.directPlayRanges(codec, caps)`** lists the `VideoRangeType`s a codec may direct play. HDR is direct played only when the decoder can decode that format AND the screen can show it; otherwise only SDR is listed and the server tone-maps. h264 is SDR only. HDR10 needs an HDR10 decoder and screen; HDR10+ plays through that same HDR10 path (its dynamic metadata is then unused) or a native HDR10+ decoder and screen; HLG needs the codec's 10-bit decoder and an HLG screen. Dolby Vision (HEVC only): DOVI (profile 5) needs a DV screen and profile 5 in the DV decoder; DOVIWithHDR10, DOVIWithHLG and DOVIWithHDR10Plus (8.1, 8.4) play as DV with a DV screen and profile 8, otherwise through their base layer on the HDR10, HLG or HDR10+ path; DOVIWithSDR (8.2) always plays, as SDR; profile 7 (DOVIWithEL, DOVIWithELHDR10Plus) and DOVIInvalid never direct play (black screens; research complaint 12). Unknown never direct plays.
- **`DeviceProfileBuilder.build(caps, quality, forceTranscode, burnInFormat)`** (internal), ported from AAFin, every name and enum value checked against the 12.4.0 schemas `DeviceProfile`, `DirectPlayProfile`, `TranscodingProfile`, `CodecProfile`, `ProfileCondition`, `SubtitleProfile`: `Name` Shoalwatch; `MaxStreamingBitrate` and `MaxStaticBitrate` from the quality; one `Video` direct-play profile (`mp4,m4v,mov,mkv,webm,ts,mpegts`, the decodable codecs, h264 and aac always); one `Video` transcoding profile (`ts`, h264, aac, `hls`, `Streaming`, `MaxAudioChannels` "2", `CopyTimestamps` and `EnableSubtitlesInManifest` false, `MinSegments` 1, `SegmentLength` 6, `Width` and `Height` `LessThanEqual` the quality's width and 16:9 of it, none at Maximum), so a converted HDR source arrives as 8-bit SDR; codec profiles: h264 `VideoBitDepth <= 8` and `VideoLevel <=` the decoder's level, hevc/vp9/av1 `VideoBitDepth <=` 10 or 8 and `Width`, `Height`, `VideoFramerate <=` the counted decoder's largest picture and its top rate there (`VideoLimits`, read from `videoCapabilities`; no data is 1080p at 30, never no limit), plus for hevc `VideoLevel <=` its level in Jellyfin's numbering (30 times the level, 5.1 is 153; VP9 and AV1 levels are not sent), and for every decodable codec `VideoRangeType EqualsAny` the `HdrPolicy` names joined with `|` (an SDR phone sends `SDR|DOVIWithSDR` for hevc); with `forceTranscode` (which the resolver passes for a forced transcode AND for a burn-in, since a burn-in is always a conversion) the size ceiling is also a codec condition (the server applies those to every conversion; the request has no MaxWidth field). No condition is `IsRequired`. Subtitles: srt, subrip, vtt, webvtt, ass, ssa `External`; pgs, pgssub, dvdsub, vobsub, dvbsub `Embed` and `Encode`; a format the user asked the server to draw is `Encode` only. `ContainerProfiles` is empty.

Tests: `HdrPolicyTest`, `DeviceProfileBuilderTest` (the encoded JSON's property names against the reference, every rule above), `AndroidDeviceCapabilitiesTest` (Robolectric `ShadowMediaCodecList` and `ShadowDisplay`). Only a real phone and a real server can prove the HDR rows (see the milestone's open risks).

## Playback decision (`PlaybackDecision`, `PlaybackResolver`)

How an item is played, decided once per opening (and again on a quality, audio or burn-in change). `AppGraph.playbackResolver` is the instance.

- **The body** (`PlaybackInfoDto`): `UserId` the session's user; `MaxStreamingBitrate` the quality; `AudioStreamIndex` the asked track; `SubtitleStreamIndex` the burn-in track, else the PICTURE track, else **-1** (left unset, the server may pick a subtitle and burn it in, forcing a needless transcode: AAFin's finding; text tracks are never sent, the app fetches them itself); `DeviceProfile` from `DeviceProfileBuilder` (capabilities read off the main thread for every ask; a burn-in track's format listed Encode only); `EnableDirectPlay` and `EnableDirectStream` off for a forced transcode or a burn-in; `EnableTranscoding`, `AllowVideoStreamCopy`, `AllowAudioStreamCopy` on; `AlwaysBurnInSubtitleWhenTranscoding` for a burn-in. `StartTimeTicks` is never sent: every stream starts at zero and the player seeks (HLS playlists cover the whole runtime).
- **The order** (pure, `PlaybackDecision.decide`): a refusal (`NotAllowed`, `NoCompatibleStream`, `RateLimitExceeded`) is thrown as its `AppError` kind; the server's first source is used (none: `NO_COMPATIBLE_STREAM`); **direct play** (`/Videos/{itemId}/stream?static=true&mediaSourceId=&tag=`, built by `MediaPaths.directStream`) when the source allows it and nothing forces a transcode (a forced transcode or a burn-in); otherwise the server's own `TranscodingUrl`, labelled **direct stream** when the source allows it and nothing forces a transcode, else **transcode**; otherwise `NO_COMPATIBLE_STREAM` (no static-stream guess). A PICTURE subtitle needs no rule of its own: the profile lists picture formats Embed and Encode, so a server that would have to encode one already answers `SupportsDirectPlay` false. Transcode reasons are kept for direct stream and transcode (empty for direct play). Audio: the asked track if the source has it, else the server's default, else the first.
- **Validated twice:** the models are public data classes, so the decision re-checks what the mappers already did. An item id that is not a normalised `JellyfinId` is `SERVER_NOT_FOUND`; a source id outside `[A-Za-z0-9]{1,64}` makes the source unusable; an unsafe play session id or tag is dropped; a server path must still keep `checkServerPath`'s rules (`MediaPaths.isServerSource`: `/videos/` first, unreserved non-dot segments, no credential name or control character in the query), else it is not offered.
- **One forced retry, one fallback:** a burn-in whose answer has no transcoding path is asked exactly once more as a forced transcode (`needsForcedTranscode`; never a third time). `fallBack(plan)` (the controller calls it at most once per item, after a decoder failure in direct play or direct stream) asks exactly once with direct play and direct stream off. Neither loops; `ServerApi` does not retry PlaybackInfo.
- **Routes:** `resolve` and `fallBack` ask for the `MediaRoute` only after the decision (a refusal or `OFFLINE` makes none), so it is to the address verified now, and check it belongs to the same session. `reroute(resolved)` gives the same plan a new route without asking the server: what the player does when a route refuses to send because it went stale (see "Media route"). `Resolved` never prints its plan or route.

Tests: `PlaybackDecisionTest` (fixtures decoded through the real mappers; hostile and hand-built answers), `PlaybackResolverTest` (the body, the retries, failures, routes; `FakePlaybackGateway` in `PlaybackFakes.kt`).

## Progress reports and teardown (`PlaybackReports`, `ProgressReporter`, `ActivePlayback`)

What the server (and this phone's saved library) hears while something plays, and how playback ends when the profile changes. Reports never stop the film.

- **The seam (`PlaybackReports`)**: `started`, `progress`, `ping`, `stopped(finished)`, each sent as the `Session` passed in and only as it, each answering `Sent` or `NotSent(kind)` and never throwing (except cancellation). `AppGraph.playbackReports` is `ServerPlaybackReports`: the gateway's report calls (so `ServerApi`, off the main thread) and, for a stop, `Playstate.recordStop`, so Continue Watching on this phone is right at once. Failures are logged by kind only.
- **A stop is durable before it is sent** (Tasks 6-8 review M3): `stopped` first saves it and queues it in the outbox at the stop's own time (`recordStop(..., reached = false, kick = false)`: a POSITION, or the finished stop's PLAYED tick) with no send asked for, then sends the report. So if the app is closed while the report is on its way, the row is still there for the next app start (not the `shoalwatch-sync` job: the job is enqueued only by `changed`, after the send; final review M2). Afterwards: an unfinished stop the server heard (sent, or the server answered about the item: `SERVER_NOT_FOUND`; an allow-list, Tasks 9-10 review M2; not a 403, which may be a firewall refusing everything: its row stays and the sender proves it as the profile before anything is dropped, Milestone 5 re-review m3, as final review I1) is recorded again with `reached = true`, which takes back that item's unsent POSITION rows made up to the stop's own time, and deletes its offline plays written up to then (`OfflinePlayDao.deleteCovered`, so the next start's recovery cannot queue an older offline position over the stop's; Milestone 5 re-review m1), in the same transaction (both records of one stop carry the time `stopped` took, `recordStop(..., stoppedAt)`: two overlapping stops of the same item never share a cut-off; Tasks 11-12 review M5) (the report carried the newest position, so it is never sent twice); a position the user changed after it (a removal from Continue Watching while the report was in flight) stays queued and keeps its value on the phone (Tasks 9-10 review M1); anything else left (a stop that did not reach the server for any other reason: no connection, a 5xx, a 401, a TLS or identity failure, not signed in, unknown, kept like the account's other rows; a finished stop's PLAYED tick) is handed to the outbox only then (`SyncScheduler.changed`), so the report reaches the server first. Nothing here resends a stop (a session report is never replayed), so Milestone 3's in-memory pending stop, its resend without `PlaySessionId`, and its loss on process death are gone (carried M-3, check I4). An old stop cannot overwrite a newer position (M-2): POSITION rows coalesce per item, a heard stop takes back older ones, and the conflict rule sends a position only if the server has no newer change. **While the report is in flight the item is held** (`StopsInFlight`, memory only, shared with `SyncSender`; Tasks 9-10 review I1): any drain of that profile, one already running included, passes over the item's rows (and its later rows) until the report lands or fails, then `changed` makes it look again, after every stop, heard or not (Tasks 11-12 review M1: a change made during the hold is sent then). So a finished stop's PLAYED tick never reaches the server before the report, and the report and the tick cannot together count the play twice or leave a resume point beside "played". After a process death nothing is held, and the next start sends the rows. The store hooks no longer call it: a removed account's rows go with it.
- **`Playstate.recordStop`** (see "Tidy-up actions"): finished is watched on this phone and **always** queues a `PLAYED` tick, reached or not (Tasks 6-8 review I1: "Finished" fires at the Outro start or 90%, but the server marks a stop played only from 90%, so below that it keeps a resume point that would overwrite the phone's "watched"; the tick is absolute and `AlreadyThere` when the server has it played, so it never counts a play twice). Otherwise the saved position is set, queued only when the stop did not reach the server; a reached unfinished stop clears at once the markers no unsent row covers, then `resume` and `nextUp` are refreshed. Same per-user queue and write gate; an item this user was not shown is `SERVER_NOT_FOUND` with nothing written.
- **Teardown (`ActivePlayback`, `AppGraph.activePlayback`):** the one record of who is playing. The controller registers (`begin(session, onEnd)`, main thread) and releases with its own token. It ends at once, clearing the record first and calling `onEnd` exactly once on the main thread (synchronously when already there, else posted): `end(server[, user])` from `ServerStore`'s `onAccountGone` and `onServerRemoved` hooks (`SIGNED_OUT`); the active-session flow (`ServerCatalog.activeSession()`, collected in the app scope) when it names another session or none; and a second `begin` (another playback taking over). **It fails closed:** it remembers the active session the flow last named, and a `begin` for any other session, for nobody, or before the flow has named one at all, is never registered and ends at once through its own `onEnd` (the flow says each change once, so a stale screen cannot start an old profile's playback under the new one). `ShoalwatchApp.onCreate` starts it, so the active session is known long before a player opens. A session change is `SESSION_CHANGED` only while the old account is still signed in (its token is loaded), else `SIGNED_OUT`. The controller's `onEnd` releases the engine and media session and drops queue, position and title; it sends a final stop for the old session only for `SESSION_CHANGED`, and only as that session (`ServerApi` sends nothing for a signed-out one anyway). Reports are bound to their session, so nothing of the old session's playback can be sent as the new one.

**Known limits:** a stop whose send overlapped a `forget` of its own account or server is neither kept nor saved locally (rare, and safe); another account's `forget` does not affect it.

Tests: `ProgressReporterTest` (virtual time and a hand-moved monotonic clock), `ServerPlaybackReportsTest`, `PlaybackOutboxTest` (the real actions and outbox), `ActivePlaybackTest`, `PlaystateRecordStopTest` (real `PlaystateRepository`, in-memory Room).

## Data model (servers and accounts)

- **Tables:** `servers` (id, name, version, home/away address strings, allowCleartext, pinnedSpkiSha256, clientCertAlias, customHeaders BLOB), `accounts` (PK serverId+userId, userName, accessToken BLOB), `active_account` (single row, `slot = 0`).
- **Ids:** server and user ids are GUIDs from the server, validated and normalised at the gateway (`JellyfinId`: 32 hex digits, dashes optional, stored lower-case without dashes); anything else is `SERVER_UNSUPPORTED` (public info) or `SERVER_ERROR` (sign-in). So the same server cannot become two rows, comparisons are plain equality, and an id is safe as a route segment or (Milestone 4) part of a file name. Server name and user name are capped at 80 characters, the version at 40, with control characters and every Unicode format character (category Cf: bidi, zero-width, soft hyphen, tags, ...) removed; a name left empty becomes a fixed default ("Jellyfin" for a server, "Unnamed user" for a user). The Quick Connect code is shown on screen, so the gateway accepts only 4 to 12 ASCII letters or digits and treats anything else as `SERVER_ERROR`.
- **Secrets at rest:** access tokens and custom headers are stored only as `SecretBox` ciphertext in BLOB columns (tests assert the raw bytes contain neither). The account lists, the active-account flow and `active()` wait for the first `warmTokens()` (the cold-start gate) and show only accounts whose token is loaded (`ServerStore.usable` mirrors the token map's keys), so what is listed always agrees with what could send a request. An account whose token cannot be decrypted (lost Keystore key), or that a failed warm never loaded, is hidden everywhere, consistently, until the user signs in again or a retry succeeds (`WarmGateTest`); unreadable headers load as none.
- **Keystore off the main thread, and only when needed (I7):** what screens read (`ServerSummary` lists, `AccountSummary` lists, the active account, "is anyone signed in") selects only non-secret columns (`ServerRow`, `AccountRow`) and never calls `SecretBox`. Every seal and open (warm, saving an account or server, the revocation reads `token`/`tokens`, full server reads for the selector and the settings screen) runs on the store's injected IO dispatcher (`TokenFreeReadsTest`). Opened custom headers are memoised in a small bounded in-memory map keyed by a SHA-256 of the sealed bytes (never the plaintext): the row is still read on every `server()` call, a changed header is a different ciphertext so the memo cannot go stale, an unreadable blob is never remembered, and the map is emptied when a server is saved or removed (`HeaderMemoTest`).
- **Integrity:** accounts cascade-delete with their server; `active_account` cascades from the account, so removing the active account (or its server) leaves nobody active, and the single-row key means there can never be two. Writes use `@Upsert`, never `REPLACE` (REPLACE deletes first and would cascade away accounts). No destructive-migration fallback; the schema is exported to `app/schemas/`.
- **Observed reads fail closed (I4):** `summaries`, `activeAccount`, `accounts(serverId)` and `observeServer` are wrapped by `ReadHealth.guard`, which builds each source flow inside the guarded flow (Room throws while BUILDING a flow on a closed database, before a `catch` could see it). Room throws a failed query (damaged or full database) into the collector, which in a ViewModel or composition would end the app; instead the failure is logged by class only, `readFailed` (on `ServerCatalog`) becomes true, and the read emits its fail-closed value: nobody active, empty lists, no server, never the value from before the failure. `readFailed` is set BEFORE that value is emitted. Home shows its existing "Something went wrong opening your saved servers" state with Try again while it is true; start-up shows its failure screen (never first-run Welcome); Servers shows an empty list; a server's settings screen closes as if the server had gone. Try again (`retryWarmIfFailed`) clears the flag and subscribes every failed read again; a read that has not failed is never restarted. `ReadHealthTest`, `StoreReadFailureTest`.
- **Id guard:** `upsertServer` and `upsertAccount` `require` every id they are given to equal its `JellyfinId`-normalised form (fixed message, never echoing the id), so nothing but the gateway's normalised GUIDs can become a key. Tests make valid ids with `testId(label)` (`TestIds.kt`).
- **Pins:** `upsertServer` rejects a malformed pin (`IllegalArgumentException`, fixed message). A damaged pin already in the database loads as `pinnedSpkiSha256 = null` with `Server.pinInvalid = true`; `ServerNet` then throws `TLS_UNTRUSTED`, so the next connection prompts for re-trust rather than silently falling back to system trust. Saving other edits to such a server keeps the damaged column untouched. Re-trusting a changed certificate pins it only after the address answers, with the new pin, as the same server.
- **One place for security settings:** `ServerNet.anonymous(addresses, draft-or-Server, device)` and `ServerNet.authenticated(addresses, server, userId, device, tokens)` are the only code that turns a server's settings into a `ServerNetConfig`.
- **Device identity:** random UUID generated once, kept in private SharedPreferences (excluded from backup); client name `Shoalwatch`, version from `BuildConfig.VERSION_NAME`, device name from `Build.MODEL` sanitised.

## Library cache (Room v2 to v6)

The on-phone copy of what the server told us, and the only thing browsing screens read (SPEC section 4, rule 1: the network writes, screens observe Room, so offline browsing is just "what is in these tables"). Package `data/db/library`.

**Scoping: why items are per server and user data per user.** Two profiles signed in to the same server share the same `items` rows (and, in Milestone 4, the same downloaded file: SPEC 3.3), while each keeps its own watched state, resume position, favourites, libraries and home rows. So item metadata is keyed by `(serverId, itemId)` and everything a user does or sees is keyed by `(serverId, userId, ...)`. The same item id on two servers is two rows.

| Table | Primary key | Foreign key (ON DELETE CASCADE) | Extra indices | Holds |
|---|---|---|---|---|
| `items` | `serverId, itemId` | `serverId` to `servers.id` | `(serverId, parentId)`; `(serverId, seriesId, seasonId, parentIndexNumber, indexNumber)` | everything the `Item` model carries, plus `nameKey` (the folded name, for offline search), `fetchedAt`, `pinned` (default 0; written only by `DownloadStore`, Milestone 4: an item a download needs, with its season and series) |
| `user_data` | `serverId, userId, itemId` | `(serverId, userId)` to `accounts` | `(serverId, itemId)` | played, positionMs, playedPercentage, playCount, favourite, lastPlayed, unplayedItemCount, `updatedAt` (last local write), `pendingSyncAt` (non-null: a local change the server has not confirmed) |
| `views` | `serverId, userId, viewId` | `(serverId, userId)` to `accounts` | none | a user's libraries, in server order (`position`) |
| `list_entries` | `serverId, userId, listKey, position` | `(serverId, userId)` to `accounts` | `(serverId, itemId)` | ordered membership only: `itemId` at `position` |
| `visible_items` | `serverId, userId, itemId` | `(serverId, userId)` to `accounts` | `(serverId, itemId)` | `seenAt`: "the server showed this user this item" (see "Visibility") |
| `list_state` | `serverId, userId, listKey` | `(serverId, userId)` to `accounts` | none | `total` (server's count; null when it gave no usable one), `loadedCount`, `nextStartIndex`, `pagesLoaded`, `endReached`, `refreshedAt` |

- **Visibility (safeguarding, a design rule).** Item rows are shared per server, but the app shows a user only items THE SERVER HAS SHOWN THAT USER: a restricted profile (a child) must never see a title another profile on the same server cached. `visible_items` records it, written inside the same `LibraryStore` transaction as every server-sourced item write for the session (list pages, a single-item fetch, search results; views are not items), and recording only what was returned (the series of a returned episode is not inferred); `seenAt` is refreshed by every such write. A user is shown only items the server has returned to that user on this device, re-confirmed within the last 30 days (or downloaded, or in one of their current lists). An item the server later refuses for that user is hidden from them at once. Every read that returns an item for a user joins to it: list reads, `observeItem`/`getItem`, `observeEpisodes`/`getEpisodes`, and `searchByName`; an item the user was not shown is treated exactly as absent. The only unfiltered reads are `ItemDao.getItemEntity` and `countItems`, which are `internal` and exist for the store and tests. **Revocation:** when a single-item refresh for a session fails with `SERVER_NOT_FOUND` or `FORBIDDEN`, `LibraryStore.revokeVisibility` deletes THAT user's record and removes the item from each of that user's lists (`removeEntry`, so no gap), in one transaction through the write gate; the shared row and other users' records stay, and a later server return makes it visible again. **Expiry:** maintenance deletes records whose `seenAt` is older than 30 days unless the item is pinned or is in one of that same user's current lists. Eviction also deletes the record of items it deletes and keeps it for pinned items: Milestone 4's shared downloads rely on this record as the "allowed to see" check. Account removal cascades it; signing in again keeps the account and so the record. `LibraryVisibilityTest`, `LibraryRepositoryRevocationTest` and `LibraryRepositoryItemSearchTest` cover it.
- **No foreign key from `user_data` or `list_entries` to `items`**, on purpose: user data and lists can arrive before their item row or outlive it, and watched state must survive eviction of metadata (it is needed by sync in a later milestone). Maintenance removes orphans instead.
- **Cascades:** removing an account deletes that user's `user_data`, `views`, `list_entries`, `list_state` and `visible_items` and leaves `items`; removing a server deletes everything for it. Both are tested through the real `ServerStore.removeAccount` and `removeServer`. Room keeps `PRAGMA foreign_keys` on; writes are `@Upsert` or explicit upserts, never `REPLACE` (it deletes first and would cascade).
- **Times** are epoch milliseconds (`INTEGER`); `kind` is the `ItemKind` name (`TEXT`, via `ItemKindConverter`; a name this version does not know reads as `OTHER`); view kinds are `LibraryKind` names (unknown reads as `MIXED`).
- **Ids** are the gateway's normalised `JellyfinId` strings; the cache stores what it is given and never builds a request from it.

**The list model.** A list is `list_entries` (membership and order, no item data) plus `list_state`. `ListDao.entryIds` returns a list's ids in order without the join (for de-duplicating the next page). `ListDao.observeList/getList(serverId, userId, listKey, limit)` is `list_entries` JOIN `items` LEFT JOIN `user_data` (that user's), `ORDER BY position LIMIT n`; an entry whose item row is missing, or that the server never showed this user (see "Visibility"), is simply not returned. A list key is an opaque caller-supplied string of 1 to 200 characters (`resume`, `nextUp`, `latest:<viewId>`, `children:<parentId>:<kinds>:<sort>:<filter>`, `seasons:<seriesId>`, `episodes:<seriesId>:<seasonId|all>`; search results are not cached). Positions are contiguous from 0. `ItemDao.observeEpisodes/getEpisodes(serverId, userId, seriesId, seasonId?)` reads episodes straight from `items` (season number, episode number, missing numbers last, then sort name and id), so a series shows whatever is stored even if no list names it. `ItemDao.searchByName` is case-insensitive in every script (SQLite's `LIKE` and `lower()` only fold ASCII, so the lower-cased `nameKey` column is compared instead) and treats `%`, `_` and `\` in the query literally.

**Writing a page** (`LibraryStore.writePage(session, listKey, start, page, total, now)`) is one transaction: upsert the items; upsert the user data of the items that came with some (an item with none leaves stored user data untouched); delete the list's entries from `start` on (`start == 0` replaces the whole list) and insert the page at `start`; write `list_state` (`total`, if known, raised to at least `loadedCount`; plus the paging state `nextStartIndex`, `pagesLoaded`, `endReached`, which default to "read in one go"). `nextStartIndex` is the server index to continue from and is NOT `loadedCount`: the gateway drops unusable elements, so fewer rows are stored than the server sent. A `start` past the end of what is stored (or a state that is no longer the one the caller read) is reported as `PageResult.Stale` and nothing is written; an empty or over-long key is refused. Any failure rolls everything back. `LibraryStore.writeItems` is the same without a list (detail fetches); `replaceViews` makes a user's views exactly the given list in one transaction.

**Upsert rules for items** (`ItemDao.upsertItems`, read and write in one transaction): `pinned` is never touched; **`overview` keeps the stored value when the incoming one is null**, because the list endpoints do not ask for it (`fields=Overview` only on episodes; the detail call returns it); **`childCount` is always taken as sent, null included (null means unknown and the UI shows no badge)**, because Jellyfin's count is per user while the row is shared, so a kept value could be another user's number; every other column takes the incoming value, null included (an image that was removed stays removed). `fetchedAt` is the time of the write. `user_data.updatedAt` is when that row was last written on this device. The targeted updates `setPlayed`, `setFavourite` and `setPosition` create the row if missing (`INSERT OR IGNORE`, then `UPDATE`, in one transaction).

**Maintenance** (`LibraryStore.evict(now, EvictionPolicy)`, one transaction per server, defaults 30 days and 20,000 unpinned items): (1) delete `list_entries` and `list_state` of lists not refreshed since the cutoff; (2) delete unprotected items fetched before the item cutoff; (3) if the server still has more unpinned items than the cap, delete the oldest-fetched unprotected ones; (1b) delete `visible_items` records not re-confirmed within the item cutoff unless pinned or in that user's current lists; (4) delete `user_data` whose item no longer exists, except rows that are `played`, `favourite`, have a resume position or hold an unsynced change; (5) delete the `visible_items` record of items that no longer exist (a pinned item still exists, so its record stays). **Protected** (never deleted): pinned items, items named by any list entry on that server (any user), and the `seriesId`, `seasonId` and `parentId` of such items, so a pinned or listed episode keeps its season and series. The cap can only be exceeded by protected rows.

**Migration 1 to 2** (`Migration1To2`, explicit; there is no destructive fallback). Version 2 has not shipped, so the paging columns of `list_state` were added to the v2 schema and to this migration in place (and `2.json` regenerated), not as a version 3: `MigrationTest` compares a migrated database with a fresh one, so the hand-copied SQL cannot drift from the entity. Creates the six tables (`items`, `user_data`, `views`, `list_entries`, `list_state`, `visible_items`) and five indices with Room's own generated SQL, copied from `app/schemas/app.shoalwatch.data.db.AppDatabase/2.json` (Room validates the migrated database against that file when it opens, and a difference crashes the app). **No SQL newer than SQLite 3.22.** `minSdk` is 29 and Android 10 ships SQLite 3.22, while Robolectric and Room's own query verifier use a newer one, so a statement that needs a later SQLite passes every unit test and fails on an Android 10 phone. So: no SQL UPSERT (`INSERT ... ON CONFLICT ... DO UPDATE/NOTHING`, 3.24), no `RETURNING`, window functions, `UPDATE ... FROM`, `RENAME/DROP COLUMN`, generated columns, `STRICT`, `->`/`->>`, `IIF`, `MATERIALIZED` and the like. Create-or-update is `INSERT OR IGNORE` plus `UPDATE` in one `@Transaction` (Room's `@Upsert` is fine: it is an insert then an update, not SQL UPSERT). `SqlCompatibilityTest` scans every SQL string in the Kotlin sources and the exported schema for these and names the file and line; `LibraryCacheOnDeviceTest` (androidTest) runs every statement shape on a real device's SQLite.

**Pending local changes (`user_data.pendingSyncAt`).** SPEC 3.2: a watched mark is never undone by a sync. A non-null `pendingSyncAt` means "this row holds a local change the server has not confirmed". The ONE function that stores server-provided user data, `ItemDao.writeServerUserData` (reached only through `LibraryStore.writePage`/`writeItems`; the raw upserts are not callable from outside), ignores a server row for any (server, user, item) whose stored row is pending; every other row is replaced as before and is never itself pending. `ItemDao.setPlayed/setFavourite/setPosition(..., pending)` set the local value and the marker in one transaction (without `pending` an existing marker is left alone); `LibraryStore.markPending`, `clearPending` (keeps the local value) and `deleteUserData` (rolls back an optimistic action on a row that did not exist) are the rest. Eviction never deletes a pending row. The Milestone 5 playstate outbox builds on this marker; `ListCache` has no reconcile hook any more.

**Changing one list entry.** `LibraryStore.removeEntry(session, listKey, itemId)` deletes every occurrence of the item, moves later entries down (the tail is rewritten after the removed position, so the key is never violated), lowers `loadedCount` and a known `total` (never below `loadedCount`) and leaves `nextStartIndex`, which is a position on the server. `insertEntryAt(session, listKey, position, itemId)` is its undo (later entries move up; the list must exist and `position` be within its length). Each is one transaction. `writePage` checks that the stored positions really are contiguous (`MAX(position) + 1 == COUNT`, re-packing if not) instead of trusting the count, and returns `PageResult.Written` or `PageResult.Stale`: **Stale** (nothing written at all) when the page starts beyond the stored entries, or when the caller passed `basedOn`, the list state it read before fetching, and the stored state has since changed (a refresh replaced the list while the page was on its way). The repository drops a stale page. A negative start or a bad list key is still an `IllegalArgumentException` (a programming error).

**Authoritative item writes.** List endpoints do not request `Overview` (and only some request `ChildCount`), so a list write keeps a stored `overview` when the incoming one is null (`childCount` is always as sent, see the upsert rules). A detail fetch does request it, so `writeItems(..., authoritative = true)` (the repository's single-item refresh) writes nulls as nulls and an overview the server has removed is cleared. `pinned` is never touched by either.

**Search folding.** `nameKey` is the name with accents and other combining marks removed (NFD, then `\p{M}` stripped), Turkish dotted and dotless I both read as `i`, then lower-cased with `Locale.ROOT`; the same function is applied to the query, and `nameKey` is rewritten on every upsert (so changing the function needs no migration). "elite" finds "Élite", "istanbul" finds "İstanbul", "angstrom" finds "Ångström". A search with no kinds covers every row, including one whose stored kind this version does not know.

**Maintenance protects one level of links:** the `seriesId`, `seasonId` and `parentId` of a pinned or listed item, not the parents of those parents (an episode carries both its season and its series, so that is enough for the item kinds in use). **`pinned` has a single writer**, `DownloadStore` (Milestone 4); nothing in the cache writes it, and every item write preserves it.

**Episode order** in `ItemDao.getEpisodes/observeEpisodes` is the gateway's (`Ordering.kt`): numbered seasons, then no season number, then season 0 (Specials) last of all; then episode number (missing last), sort name (or name), id. `LibraryOrderAndJoinTest` compares the two on the same shuffled data. User data is `LEFT JOIN`ed with the user condition in the `ON` clause, so another user's data can never decide whether a row is returned (mutation-checked).

**Query plans** are asserted in `LibraryPerformanceTest` (5,000 items and entries, a 200-row page): the list query is four index searches (`list_entries`, `items`, `visible_items`, `user_data`) with no sort and no scan of `items`; the episodes query searches `items` by the `(serverId, seriesId, ...)` index. Offline name search is the one query that scans a server's items (a leading wildcard cannot use an index); the cap on stored items bounds it.

## Library repository (`LibraryRepository`)

`data/library/Library` is the only thing browsing screens use (home, listings, series, item detail, search, pull-to-refresh); `LibraryRepository` implements it on `LibraryGateway` and Room. It exposes only models from `data/library` (no DTOs, entities, `ServerApi` or HTTP types) and no flow throws because of the network: a failed refresh is `Freshness.Stale(kind)`. `AppGraph.library` is the lazy instance. Every read and write is for a `Session(serverId, userId)`: item rows are shared per server, user data and lists per user, so switching user shows that user's lists and watched state at once and never the other's.

**Cache first, refresh behind.** Collecting a flow emits what Room holds at once (even if empty), then starts a refresh in the background if the list was never loaded or is older than its window. Collecting never waits for the network. Screens only observe Room; the network only writes to it (`ListCache`). Refreshes run in the repository's own scope (the app scope), so one that has begun is written to Room even if its collector leaves.

| List | Window | Saved as |
|---|---|---|
| home rows: libraries (`views`), `resume`, `nextUp`, `latest:<viewId>` | 2 min | limits 24, 24, 16 per library |
| `children:<parentId>:<kinds>:<sort>:<filter>` (a library or folder) | 15 min | pages of 100 |
| `seasons:<seriesId>`, `episodes:<seriesId>:<seasonId or all>`, the series item | 10 min | whole lists |
| `item:<itemId>` (detail) | 5 min | one item, no entries |

**List keys** (`ListKey`, the only place they are built): opaque strings of at most 200 characters in `list_entries.listKey` and `list_state.listKey`. Ids are normalised 32-digit ids, so `:` is a safe separator; `kinds` is `ListShape.key` (`movie_r`, `series_r`, `box_set_r`, `any_d`...). `views` and `item:<id>` hold state only (a `list_state` row with no entries) because that row's `refreshedAt` is how current they are. `ListKeyTest` checks distinct inputs give distinct keys, within the limit.

**Freshness** (`Fresh`, `Refreshing`, `Stale(kind)`) is the in-memory outcome of the last attempt per (session, list key) combined with the Room flows. Idle with a saved state is `Fresh`; a running refresh or load is `Refreshing`; a failure is `Stale(kind)` (`OFFLINE`, `NETWORK`, `TIMEOUT`, `SERVER_ERROR`, `SERVER_NOT_FOUND`, TLS kinds, and `UNAUTHORISED` / `NOT_SIGNED_IN` so the screen can offer sign-in; nothing is deleted). A never-loaded list that fails is empty and `Stale`; nothing saved with nothing running (the work vanished) is `Stale(UNKNOWN)`, never a spinner that no one will stop (the cold start is `Refreshing` because the first refresh is started before the first emission). `Home.viewsFreshness` reports the libraries list the same way, so a failed libraries refresh is visible while the saved libraries stay. After a restart nothing is in memory, so staleness is recomputed from `list_state.refreshedAt`. A brief `Fresh` with the old rows can show between a write committing and Room re-emitting; a state that says "loaded" beside no rows is treated as still arriving.

**One refresh per list.** `Refresher` keeps at most one piece of work per (session, list key): concurrent collectors and an explicit `refresh()` join the one in flight; `loadMore` is declined while anything is running for the list; a refresh asked during a `loadMore` waits for it, then runs (a refresh replaces the list, so they must not overlap). At most 4 requests run at once across all lists, so home rows load in parallel without flooding the server, and a failing row does not blank the others. No retries here: `ServerApi` already retries a lost connection once, and callers must not add their own.

**Paging.** Page size 100; `loadMore` continues from the stored `nextStartIndex` (the server index the last page ended at, so skipped or repeated elements cannot cause a re-fetch), never stops because a page kept nothing, and stops only on `endReached`. An id already in the list keeps its first position. The hard ceiling is 200 pages per list; `canLoadMore` is "not end reached and under the ceiling". A failed `loadMore` leaves the list as it was and sets `Stale(kind)`. **A refresh replaces the list with page 0 in one transaction** (so items removed on the server disappear) and resets the paging state: anything beyond the first page is dropped and loaded again by scrolling. `Listing.items` can be empty while `canLoadMore` is true (a page whose elements were all unusable).

**What a listing asks for** (`ListShape.forLibrary`): films library `{MOVIE}` recursive, TV `{SERIES}` recursive, collections `{BOX_SET}` recursive, mixed and folders the direct children of any kind (`ListShape.DIRECT`).

**Series.** `series(session, seriesId, seasonId?)` gives the series, its seasons and the episodes of the selected season, each with its own list key and refresh; `freshness` is Refreshing if any part is, else the first failure, else Fresh. With no `seasonId` the season is the one holding the next unwatched episode when the saved episodes show it (Specials never decide), else the first numbered season, else Specials. The choice is sticky while the screen is open, so marking an episode watched does not jump seasons. No episodes are fetched until a season is known.

**Item detail** emits the saved row at once (it may lack the overview if it was only seen in a list), then refreshes the single item. `ItemDetail.item` is null until the item is saved for this user (see its `freshness`). When the server answers `SERVER_NOT_FOUND` or `FORBIDDEN` for the item, it is revoked for this user: the flow emits `ItemDetail(item = null, freshness = Stale(SERVER_NOT_FOUND))`, i.e. THE ITEM DISAPPEARS for this user (it is also taken out of their lists); the screen should say it is no longer available. Other users are unaffected. **Search** online asks the server and saves the results as items (not as a list) so detail screens open instantly; if that fails as `OFFLINE`, `NETWORK` or `TIMEOUT` it searches the saved names (case-insensitively) and returns `SearchResult(offline = true)`. Any other failure is thrown as an `AppError`. A blank term sends nothing. A local failure (a raw database exception) in `loadMore`, `search` or `refresh` is thrown as `AppError(UNKNOWN)`, never as a raw exception.

**User data precedence.** Everything the server sends is saved through one function, `ItemDao.writeServerUserData` (via `LibraryStore`): the server's copy overwrites the cached one unless the stored row has `pendingSyncAt` set, in which case the local change wins (see "Library cache"). Milestone 5's playstate outbox sets and clears that marker. (There is no precedence hook in the repository any more: this one function in the store transaction is the place.)

**Eviction** (`LibraryMaintenance`): `LibraryStore.evict` with the default policy (lists not refreshed for 30 days, unreferenced unpinned items older than 30 days, at most 20,000 unpinned items per server), at most once every 24 hours for all servers together (so no server more often; a recorded run in the future, from a clock that went back, counts as due). The last run is kept in memory and in a private preferences file (`PrefsMaintenanceLog`, one number). It starts the first time the library is used each day, off the main thread, and takes the same write lock as every list write, one server at a time, so it never overlaps a refresh write and never holds one back for long; a failure is not recorded and is tried again. After a clear-out the refresher forgets its "finished" records, so a live list whose saved state was just removed reads `Stale(UNKNOWN)` (the next collection refreshes it) rather than spinning.

**Failures, retries and malformed ids.** After a refresh fails, a new collection of the same list does not start another refresh for 30 seconds (injected clock), so a screen that is reopened again and again cannot become a request storm; pull-to-refresh (`refresh()`) always tries. The remembered failures are per (session, list), dropped when the account is removed, signed out or signed in again (`ServerStore` tells the repository: `onAccountGone`, `onAccountSignedIn`, so a list never keeps showing `Stale(UNAUTHORISED)` after a fresh sign-in) (`ServerStore` tells the repository) or the server is removed, cleared by the next success, and capped at 500 entries (oldest dropped). Anything a refresh throws, including a non-`AppError` from the store, ends as `Stale(UNKNOWN)`; a refresh never stays `Refreshing`. A malformed id (a navigation argument, saved state) never throws from the seam: a flow emits one empty result with `Stale(SERVER_NOT_FOUND)` and sends nothing, `loadMore` and `refresh` do nothing.

**Guidance for screens.** Pass a `Session` into every call and restart the flow when the account changes. Do not refresh on every resume: collecting already refreshes what is due. `Listing.items` can be empty while `canLoadMore` is true, so load more rather than show "empty"; call `loadMore` again when freshness returns to `Fresh` while the end of the list is still on screen. Never read the DAOs or `LibraryStore` from UI code.

**Threading.** All Room and network work runs on the injected IO dispatcher, including `refresh`, `loadMore` and `search` whatever the caller's dispatcher (`withContext(io)`); flows are safe to collect on the main thread; there is no `runBlocking`. Tests (`LibraryRepository*Test`) use a fake `LibraryGateway` (programmable answers, call log, a gate to hold calls, forced failures), a real in-memory Room under Robolectric, and an injected clock for time.

## Tidy-up actions (`Playstate`)

`data/library/Playstate` is what screens call to take an item off Continue Watching, mark it watched or unwatched, or favourite it, and what the player calls when it stops; `PlaystateRepository` implements it (`AppGraph.playstate`, lazy). Screens observe Room, so the screen updates at once. **An action returns once its change is saved on this phone and queued in the outbox; nothing waits for the server, nothing is rolled back, and offline an action succeeds.** It throws an `AppError` only for what can still fail: an item this user was not shown (or a malformed id), `SERVER_NOT_FOUND` with nothing changed; or a local failure, with nothing changed and nothing queued.

**The sequence** (the same for every action):
1. The item must be one this user was shown (the visibility join); otherwise `AppError(SERVER_NOT_FOUND)`, nothing changed.
2. Under the library write gate (`LibraryRepository.writeGated`, the lock every list write and eviction takes), in ONE transaction: the local change (`PlaystateLocal`, every row it writes marked `pendingSyncAt`, noted in `LocalChangeLog`) **and** `OutboxStore.enqueue(session, change, marks, refreshKeys)`. The marks are every row the change marked (`Touched.markedIds`, badges included); the departures are the list entries it took out (`Touched.removed`, as (item, list key), including the intent recorded for an item not in the saved list); the refresh keys are the lists the server recomputes (`Recompute.key()`: `resume`, `nextUp`, `seasons:<id>`, `episodes:<id>:<id>`, `item:<id>`; `parseRecompute` reads them back and re-validates every id). A failure anywhere rolls back both.
3. `SyncScheduler.changed(session)` (send now, and the background job), then return.

| Action | Change queued |
|---|---|
| `setPlayed` (any kind) | `PLAYED(played)` for the item itself (a season or series too: the server marks its children) |
| `setFavourite` | `FAVOURITE(favourite)` |
| `removeFromContinueWatching` | `POSITION(0)` |
| `recordStop(..., reached)` | finished and reached: nothing (the report did it); finished and not reached: `PLAYED(true)` (never a PLAY: the server may already count it from its own session); unfinished: `POSITION(p)` only when not reached |
| `recordLocalStop` | finished: `PLAY` at now, `fromOfflinePlay`; else `POSITION(p)`, `fromOfflinePlay` |

**Landing (`PlaystateLanding`, the sender's `SyncLanding`).** Under the write gate, in one transaction: `OutboxStore.take(seq)` (null: a newer row replaced it while in flight and carries it, so there is nothing to do); for every item the row marked that no other row still marks, the marker is cleared and the item noted in `LocalChangeLog` again, with the lists it left (the confirmation is a change too: a refresh asked for before this moment, answered from the server's old state, cannot overwrite it); for a `fromOfflinePlay` row, and for every PLAYED, POSITION or PLAY row whatever its flag (a later change may have replaced the play's own row; final review I2), `OfflinePlayDao.deleteCovered(session, item, occurredAt)`, so the next start's recovery cannot queue an older offline position again; `touchSynced`. Then the row's lists are refreshed (`refreshInBackground`), plus the item itself when the row was **overruled** (the server's newer copy won, or it refused the item), so the server's copy replaces the local one: a refused change does not stay on screen. A landing that fails (a database fault) rolls back whole and leaves the row; the next drain sends it again (idempotent) and lands it.

**Markers now mean "send".** The pending marker still makes `ItemDao.writeServerUserData` ignore a server row for a changed row, so a refresh cannot undo a change before the server has it (SPEC 3.2: a watched mark is never undone by a sync). It is cleared only by the row's landing, or, for a marker no outbox row covers, by the idle clean-up and the start-up sweep (below). **Lists:** `LibraryStore.writePage` leaves out of list L every item an unsent row took out of L (`OutboxDao.leftList`), in the same transaction, whenever the page was asked for: a refresh after a restart cannot put an unsent "off Continue Watching" back. This is the durable form of `LocalChangeLog`'s list memory, which is process-local.

**What each action changes locally, and what it refreshes afterwards**

| Action | Local change (all rows pending) | Refreshed once the server has it |
|---|---|---|
| `removeFromContinueWatching` | `positionMs = 0`, `playedPercentage = null`, `played` untouched; entry removed from `resume` (not `nextUp`: the server's Next Up is unaffected) | `resume` |
| `setPlayed`, film or other kind | the store's `setPlayed`: watched is `played`, position 0, no percentage, `playCount = max(playCount, 1)`, `lastPlayed = now`; unwatched is `played = false`, position 0, `playCount = 0`, `lastPlayed` kept. Out of `resume` either way (position 0) | `resume`, `nextUp` |
| `setPlayed`, episode | as a film, and the cached `unplayedItemCount` of its season and series rows moves by one (down when marked watched, up when unwatched; never below 0; only where the row has a count; not at all if the episode was already in that state) | `resume`, `nextUp` |
| `setPlayed`, season | the season row as a film, with `unplayedItemCount = 0` (watched) or null (unwatched: the server's count is not guessed from a partly saved list); every saved episode of that season this user was shown the same way; those episodes out of `resume`. Episodes that are not saved get no row | `resume`, `nextUp`, `seasons:<series>`, `episodes:<series>:<season>`, the series item (its badge) |
| `setPlayed`, series | the series row, every season in the saved `seasons:<series>` list, and every saved episode, as above | `resume`, `nextUp`, the series item, `seasons:<series>`, `episodes:` of every season seen |
| `setFavourite` | `favourite` only; no list is edited | nothing. A list filtered by favourites (`children:...:fav...`) shows the change after its next refresh; the screen can ask for one with `Library.refresh` |
| `recordStop` (the player stopped) | finished: as `setPlayed` watched. Otherwise `positionMs` as given (below 0 is 0), `played` untouched. A stop whose report reached the server queues nothing and clears at once the markers no unsent row covers | `resume`, `nextUp` |
| `recordLocalStop` (a saved copy, Milestone 4) | as `recordStop` | `resume`, `nextUp` |

**One action at a time per user:** sibling episodes share the season and series badge rows, and a season or series action touches many items, so actions queue per `Session` in the order the calls were made (the queue slot is taken synchronously in the caller), and each starts from the previous one's state. Each holds the queue only for its local transaction (milliseconds), so the next tap shows at once; the sends are ordered by the outbox, not by this queue. Another user's actions do not wait. When a user's queue goes idle, any marker on that user's rows that no outbox row covers (a stop the server heard, or a leftover) is cleared.

**Not abandoned:** the work runs in the app scope and the caller awaits it (`CompletableDeferred`): a screen cancelled after the action started stops waiting and the action still finishes. An action started on a scope that is already dead ends with a cancellation and has changed nothing. A process that dies after the transaction keeps the change and its row; the next start (or the background job) sends it (`ClosedAfterTickTest`, `PlaystateOutboxTest`).

**The rule: a server answer never overwrites user data for an item that was changed locally after that answer was asked for. Ordering is by a sequence number, never by time.** `LocalChangeLog` (one instance, made in `AppGraph`, required by `LibraryStore` and `LibraryRepository`) holds a process-wide counter. Every local change (optimistic write, confirmation, rollback, badge change) takes the next number and is noted per (server, user, item), with the lists an action took the item out of. Every request reads the current number (`LibraryStore.requestStamp()`) immediately BEFORE its gateway call and passes it, as the REQUIRED `requestedAtSeq` (no default), with its answer to `LibraryStore.writePage` or `writeItems` (list pages, `loadNextPage`, the single-item refresh, search results). An answer is dropped for an item exactly when the item's change number is GREATER than the request's stamp: `writeItems` skips that user's `user_data` row (the shared item row and visibility are still written), and `writePage` leaves the item out of a list an action took it out of, including when it was not in the saved list (the intent is recorded either way). A request stamped at or after the change applies, with no time passing at all; one stamped before is dropped, however the wall clock moves. The wall clock plays no part: setting it back cannot hide fresh answers and setting it forward cannot let stale ones through. This holds for every kind of request, because it is applied where server user data is written; `PlaystateStalenessTest`, `PlaystateStampTest` (every recipe reads its stamp before its call) and `LocalChangeLogTest` cover it. **Expiry and cap:** an entry is forgotten after 10 minutes by a MONOTONIC clock (`SystemClock.elapsedRealtime`, injected as `MonotonicClock`; a request that old would have timed out long since), and at most 5,000 entries are kept, oldest evicted first, which ends protection for an evicted item early (it needs more than 5,000 distinct items changed within 10 minutes). The same monotonic clock spaces the sweep's retries. Freshness windows and the failure cooldown still use the wall clock, which is safe because they only decide when to ask again: a clock set back keeps a list fresh a little longer and the cooldown guard (`0 until` window) treats a negative age as expired. After a rollback the restored value stands against any stale page asked for during the pending window (the page is dropped for that item); the next refresh, asked for after the rollback, heals it. Since Milestone 5 nothing waits for the server inside an action: the pending marker, kept until the change's outbox row lands, protects an unsent change for as long as it waits (see "Markers now mean 'send'").

**Start-up sweep (`StartupSweep`, owned by `LibraryRepository`).** A marker an outbox row covers means "send this" and is never swept: `ItemDao.pendingRows` (the snapshot) and `ItemDao.clearPendingFor` (the idle clean-up) both leave out every row with a `sync_marks` mark for that (server, user, item) (`ItemDao.NO_SYNC_MARK`), and every row with an `offline_plays` row (`NO_OFFLINE_PLAY`). What is left is a leftover of a process killed before Milestone 5 (or a database fault), which would hide the server's copy of that row for as long as it stands (and eviction keeps pending rows). Every entry point waits for the sweep before it reads freshness or writes anything: the list flows (`ListCache.ensure`: home, children, series, item), every refresh and "load more" (`Refresher` work), `search`, and every tidy-up action (`LibraryRepository.writeGated`). It clears exactly a SNAPSHOT of the rows that had a marker when it first managed to look (one query, its first step, taken before any entry point lets an action run), minus any row this process has touched since, and ages the lists only of users who really had a leftover cleared (by an hour: more than the longest window, far less than eviction's 30 days) so the server's copy arrives promptly and decides. If an attempt fails it is logged (the exception type only) and tried again on the next entry-point call at least 30 s later (monotonic clock), at most 5 times in all; the snapshot is kept across attempts, and a retry can therefore never clear the marker of an action that is waiting on the server right now (a failed first attempt does let actions run before the retry; their rows are excluded as touched). Until an attempt succeeds a stuck marker makes that row ignore the server.

**Known limits**
- A refresh asked for before a change is ignored for the changed item's data and cannot put a removed item back into `resume` (tests: `PlaystateStalenessTest`, `PlaystateStampTest`); it still replaces the REST of the list with data from before the change, until the refresh that follows the landing. `LocalChangeLog` entries are forgotten after 10 minutes and capped at 5,000 (see the rule); the outbox's marks protect an unsent change for as long as it waits.
- Only the kinds a screen offers are modelled: a box set or folder marked played changes its own row only.
- **Offline plays are spared (Milestone 4):** the start-up sweep and the idle clean-up also skip a `user_data` row that has an `offline_plays` row (`ItemDao.NO_OFFLINE_PLAY`); since Milestone 5 every offline play is also an outbox row, whose landing deletes the `offline_plays` row it covers.

**What screens must do:** catch `AppError` from each call and show its `userMessage` (now only an item not shown to this user, or a local failure); a list filtered by favourites needs `Library.refresh` to show a favourite change; an action completes even if the calling screen has gone, so a screen never needs to retry or clean up.

Tests: `PlaystateInstantTest` (20 ticks while the server is held), `PlaystateOutboxTest` (what each action queues, one transaction, offline, coalescing, restart), `PlaystateLandingTest` (confirm, overrule, a refusal per item, refresh keys), `PlaystateResumeTest`, `PlaystatePlayedTest`, `PlaystateSeriesTest`, `PlaystateConcurrencyTest`, `PlaystateRefreshRaceTest`, `PlaystateStalenessTest`, `PlaystateStampTest`, `PlaystateCoalesceTest`, `PlaystateSweepTest`, `PlaystateRecordStopTest`, `LocalChangeLogTest`, `SourceShapeTest` (the real repository, sender and landing on a real in-memory Room, the `FakeLibraryGateway` as the server through `LibrarySync`, an injected clock).

## Sync-back (`data/sync`: `OutboxStore`, `ConflictRule`, `SyncGateway`, `SyncSender`, `StopsInFlight`, `SyncScheduler`, `SyncWorker`, `OnlineEvents`)

SPEC §3.2: a profile's watched-state changes are kept on the phone until the server confirms them, item by item, and are sent in order, once, and only as that profile. The tidy-up actions, the player's unheard stops and every play of a saved copy write its rows (see "Tidy-up actions", "Progress reports and teardown" and "Offline playback").

**The tables** are `sync_outbox` (one row per change, `seq` the send order), `sync_marks` (which cached rows and list departures each row covers), `sync_state` (`lastSyncedAt`) and `rejected_sign_ins`; see "Sync and housekeeping tables (Room v5)" under "Library cache". `SyncBoundaryTest` scans the source: only `OutboxStore` calls `OutboxDao`'s writes, only `OutboxDao` (and `Migration4To5`) holds SQL that writes the two tables, nothing in `ui/` names the outbox, sender, gateway, release store, `HousekeepingDao`, `LocalPlaying` or WorkManager, only `SyncGateway.kt` names the user-data route in `data/sync`, nothing in `data/sync` names `/Sessions/Playing`, `datePlayed` appears nowhere, and no WorkManager input data is built.

**`OutboxStore`** (`data/sync`, over `OutboxDao` in `data/db/sync`) is the only writer of `sync_outbox` and `sync_marks`.

- `enqueue(session, change, marks, refreshKeys)` must run inside the caller's transaction, so the local change and its row commit (or roll back) together. It refuses (`IllegalArgumentException`, fixed words) an id that is not a normalised `JellyfinId`, an empty list key, a refresh key that is empty or holds a comma, and refresh keys over 2,000 characters joined.
- **Coalescing:** a new PLAYED, FAVOURITE or POSITION replaces any row of the same (profile, item, kind) that is still there (unsent, or in flight), marks and all, and takes a new `seq` at the end. PLAY is never coalesced: each is a separate watch. A row replaced while in flight is simply not found by its later `take`, which returns null: the newer row carries it.
- **Order (`head`)**, reading a profile's rows in `seq` order, 50 at a time: a row deferred by a 5xx that is not yet stuck and not yet due holds back the whole profile (null). A **stuck** row (`serverErrors >= 10`) not yet due is passed over, and so is every later row for the same item, so one item the server keeps refusing cannot block the rest and nothing for that item overtakes it. A stuck row is still sent when it is due.
- `markSending` is committed before a request leaves: `sentOnce = 1`, `attempts + 1`, and for PLAY the absolute count, kept if already set (`COALESCE`). `deferAfterServerError`: `serverErrors + 1`, `notBefore = now + min(60 s × 2^(serverErrors − 1), 6 h)`.
- `take(seq)` deletes the row and its marks in one transaction and returns `Landed`: the row's item, kinds, date, `refreshKeys`, and `unmarked`, the items it marked (plainly or as having left a list) that no other row of that profile still marks. `hasMark` and `leftList` answer the same per profile.
- A row whose `kind` this version cannot read is deleted on read, with its marks, and logged in fixed words.
- `status(session, signedIn)`: waiting rows, stuck rows, `needsSignIn` (rows waiting and not signed in), `lastSyncedAt` from `sync_state`. It and `serversWithWork` are guarded like the store's reads (`ReadHealth`): a failed read emits `SyncStatus.NONE` (or no servers) and never throws. `touchSynced` writes `sync_state` only for an account that still exists.

**`ConflictRule`** (pure) decides what to send from the row and the server's copy (`GET /UserItems/{id}/UserData`). "Newer on the server" is `server.lastPlayedAt >= row.occurredAt − 2 min`: inside the margin the server wins, because there is no server-time endpoint to measure clock skew and the server's copy is the one that cannot lose "watched".

| Row | Server copy | Sent |
|---|---|---|
| PLAYED true, film or episode | played | nothing (`AlreadyThere`) |
| | not played, or unknown | `Played`, `PlayCount = max(count, 1)` (left out when unknown), position 0 |
| PLAYED true, season, series or other | not read | `POST /UserPlayedItems/{id}` (the server marks the children) |
| PLAYED false | not played | nothing |
| | played and newer | nothing: the server's copy shows (**watched is never undone by a sync**) |
| | played and older, or unknown | `DELETE /UserPlayedItems/{id}` |
| FAVOURITE | not read | `POST` / `DELETE /UserFavoriteItems/{id}` |
| POSITION p | newer | nothing: the later change wins |
| | older, or unknown | the position, and `LastPlayedDate` only when p > 0 |
| PLAY at t | sent before and the server's count has reached the stored one | nothing (the earlier send landed) |
| | otherwise | `Played`, the stored count or else server + 1 (left out when unknown), and `LastPlayedDate = t` and position 0 only when not newer on the server |

**Known limit (the margin; final review M1):** the 2-minute margin also catches the user's own change made soon after a server-side date, including one this phone's own PLAY just set: an unwatch (or a removal from Continue Watching) within 2 minutes of the server's `LastPlayedDate` is `ServerIsNewer`, and the item quietly shows as watched (or back in Continue Watching) after the refresh. Watched is never lost; the user's later unwatch is.

**Why a retry cannot double-count:** a PLAY's count is computed once, from the server's copy, stored by `markSending` before the request leaves, and every retry sends that same absolute number, or nothing once the server shows it. No request ever carries `datePlayed`, so the server's "add one per dated mark" path is never used. The worst case (another device plays the item between the read and the write) is one play under-counted, never one over.

**`SyncGateway`** (`data/sync/api`, `SyncGatewayImpl` on `ServerApi` and `LibraryGateway`): every call is as the row's own `Session`, `userId` is always that session's user, paths are built only from normalised ids (anything else is `SERVER_NOT_FOUND` with nothing sent), and every call opts in to `ServerApi`'s one network retry (a read, or an absolute or idempotent write). Bodies are `UpdateUserItemDataBody` encoded by `SyncJson.ENCODER` (`explicitNulls = false`: only the fields meant are sent); dates are whole seconds in UTC (`2026-11-15T14:05:00Z`). The user-data read is bounded at 64 KiB, decoded with every field nullable (a wrongly typed field is `SERVER_ERROR`), and range-checked by `UserItemDataDto.toServerUserData` (`Mappers.kt`): `PlayCount` 0..100,000 else unknown, position 0..`Long.MAX_VALUE / 10,000` ticks else 0, `LastPlayedDate` 2000-01-01..2200-01-01 else unknown. A 404 from the user-data route asks `GET /Items/{id}`: found means a server without the route, and that item's own `UserData` is the copy (the same range checks; null only when it has none that can be read; device run W-2/W-3: an unknown copy let an older untick undo a later watch); its own failure passes through, and an item that is not safe to hand on is `SERVER_ERROR`. `itemGone` is true only when `GET /Items/{id}` is `SERVER_NOT_FOUND` and `GET /UserViews` then succeeds: a redirect or a proxy answering 404 for everything is not "gone".

**`SyncSender`** drains one profile at a time per profile (`kick` joins a running drain; a per-profile lock means two never overlap, even just after `forget`), at most four at once in all. One drain: wait for the saved sign-ins to load; no token for the session means `WAITING_FOR_SIGN_IN` and nothing sent; then for each `head`: read the server's copy if the rule needs it, decide, and either land it at once (`AlreadyThere`: `SyncLanding.confirmed`; `ServerIsNewer`: `SyncLanding.overruled`) or `markSending`, make the one request and confirm. The token is checked again before every request. A drain that empties the outbox sets `lastSyncedAt`; rows left (deferred or stuck) give `BACKING_OFF`. `drainAll` drains every profile with rows and returns the worst result, from least to most in need of another attempt: `EMPTY`, `WAITING_FOR_SIGN_IN`, `BACKING_OFF`, `WAITING_FOR_CONNECTION`, `STOPPED`. `forget(serverId, userId?)` (for the store hooks) cancels that account's (or server's) drain, ending any wait or held request, so nothing more is sent for it, even when called straight after a `kick`, before the drain has started. A `kick` that joins a running drain makes it look once more before it ends; a drain that has found nothing due stops being joinable in the same locked step, so a kick after that starts a new drain (which waits for the old one) instead of joining one that will never read its row.

| Failure (`AppError.Kind`) | The row | The drain |
|---|---|---|
| `OFFLINE`, `NETWORK`, `TIMEOUT` | stays as it is | stops (order is kept): `WAITING_FOR_CONNECTION` |
| `SERVER_ERROR` | deferred | goes on with the next head (none unless only stuck rows wait): `BACKING_OFF` |
| `UNAUTHORISED`, `NOT_SIGNED_IN` | stays (`ServerApi` has already invalidated the token) | stops: `WAITING_FOR_SIGN_IN` |
| `FORBIDDEN` | `GET /UserViews` answers as the profile: overruled (the server's answer about this item for this profile); it answers 403 or 404 too (a proxy or WAF refusing everything): deferred, never dropped (final review I1); any other failure of that check: by its own kind | goes on |
| `SERVER_NOT_FOUND` | `itemGone` true: overruled; false (a redirect, a proxy): deferred, never dropped | goes on |
| TLS kinds, `CLIENT_CERT_REQUIRED`, `CLEARTEXT_BLOCKED` | stays | stops (the user must fix the connection): `WAITING_FOR_CONNECTION` |
| anything else, or a local database failure | stays | logged by kind or class; stops: `STOPPED` |

No row is ever deleted for failing: only a confirmation, an overruling answer from the server, coalescing, or the account's removal ends one. A landing that leaves its row in place stops the drain (`STOPPED`) rather than sending it again. Log lines are fixed words plus a kind or an exception class; `Change`, `SyncStatus`, `ServerUserData`, `UserDataUpdate`, `Landed`, `OutboxRow` and the entities print no id, position or date.

**When sending happens (`SyncScheduler`, `SyncWorker`, `OnlineEvents`).**
- **After every change** (`changed(session)`, called once the row is committed): the profile's drain is kicked in this process AND the one unique job `shoalwatch-sync` is enqueued with `REPLACE`: a `OneTimeWorkRequest` for `SyncWorker`, `NetworkType.CONNECTED` (any network: these are small requests, and a home-only address simply waits for home), exponential backoff from 30 s, no input data, not expedited and not foreground (no notification, no permission). `REPLACE` is safe because the worker only awaits `SyncSender.drainAll()`, which runs in the app scope: replacing the job cancels a wait, never a send, and the newest request always covers the whole outbox (`KEEP` could drop a change enqueued just as a finishing job still counts as running; `APPEND_OR_REPLACE` would grow a chain while offline). A failure to reach WorkManager is logged by class and never fails the change.
- **The worker:** `EMPTY` and `WAITING_FOR_SIGN_IN` are success (a sign-in kicks again); anything above `WAITING_FOR_SIGN_IN` in `drainAll`'s order (`BACKING_OFF`, `WAITING_FOR_CONNECTION`, `STOPPED`) is retry, so one profile waiting for a sign-in never hides another that needs another attempt.
- **A change just before the app is closed:** the row is committed before the action returns and the job is enqueued in the same call, so if the process dies before the in-process kick sends it, WorkManager runs the job in a new process when a network is there, and the worker drains it (`ClosedAfterTickTest`). After a reboot WorkManager's own reschedule receiver brings the job back. Doze and OEM battery rules can delay the job; the next app start or reconnection sends regardless.
- **Start-up** (`ShoalwatchApp.onCreate`, `start()`): every profile with rows is kicked, and the job is scheduled only if there are any, so WorkManager is not reached while the outbox is empty.
- **Reconnection:** a kick that joins a drain while its request is failing for want of a connection (the reconnection's own kick, racing the old connection's failure) buys that drain one more pass instead of letting it stop, so the row goes now rather than at the job's back-off (Tasks 6-8 review M1); with no kick joined, a no-connection stop is not retried. `OnlineEvents` watches the connection of each server that has rows (`OutboxStore.serversWithWork`; a server that leaves the set is no longer watched) and emits its id each time it becomes `Online` after being anything else (`Checking`, `Offline`, or a different `Online`); the first reading of a newly watched server never emits, because whoever added it already sent. Each emission kicks that server's profiles only. After a `NETWORK` or `TIMEOUT` failure that server's emissions kick nothing for 1 min, doubling to 30 min (`SyncSender.holdsReconnection`, per server as auto-download next, memory only), because such a failure makes `ServerApi` re-probe and the probe's new Online is itself an emission, which would otherwise re-send the head row without end on a slow link (carried from Tasks 13-14 review M4). Any answer from the server (a send landed, or a 5xx, 401, 403 or 404) ends the hold, and `OFFLINE` starts none. A real reconnection is never held: `OnlineEvents.reconnections` marks an Online as `afterOffline` when the server was seen `Offline` since it was last Online (a re-probe goes only through `Checking`), and that one always kicks. A change, the start-up kick, a sign-in and the job are never held either.
- **Sign-in:** the store hook `onAccountSignedIn` calls `signedIn(server, user)`, which kicks that profile (and schedules the job) if it has rows.

### Sync seam (`Sync`, `SyncRepository`; the sync line)

What screens use; they never name the outbox or the sender. Every read is for one `Session`, and nothing of one profile is ever read for another.
- **`status(s)`**: `OutboxStore.status` for that profile, with `needsSignIn` true when it has rows and its token is not loaded (`ServerStore.usableAccounts`, the same set the lists and `active()` use). Never throws: a failed read emits `SyncStatus.NONE`.
- **`waiting(s)`**: the count; 0 when the outbox cannot be read (a closed database's own cancellation counts as a failed read; a real cancellation propagates).
- **`sendNow(s, timeoutMs)`**: kicks (or joins) the profile's one drain and waits for it at most `timeoutMs`, then returns what is still waiting. Only the wait ends at the timeout: the drain runs on in the app scope, so a request in flight is not cut off. Never throws.

**The sync line** (`SyncText`, pure; `SyncStatusLine`): under the Downloads tab's top bar (the active session, the first item of its list, so at twice the text size it scrolls away) and under each profile on Servers and accounts. In order: needs a sign-in ("Sign in again to send 3 changes."), changes the server keeps refusing (`stuck`, with any others waiting on the detail line), changes waiting ("3 changes waiting to sync", "They're sent when your server can be reached."), then "All your changes are on your server." Nothing is shown when nothing waits and the profile has never synced. "Last synced at 14:05" today, else "Last synced on 12 November", in the phone's time zone, `Locale.UK` with digits 0-9 (counts are passed as text, so they are 0-9 too). Plain text (14sp and up) that wraps, read by TalkBack as one element; it is a polite live region only in the frame its main words change, so a new "Last synced" time alone is not announced.

## Download files (`DownloadPaths`, `Volumes`, `DownloadPrefs`)

**Where files go.** App-private storage only: no storage permission, removed on uninstall, never backed up (`allowBackup="false"`; the backup rules exclude `file` and `external`). INTERNAL (the default) is `filesDir/downloads`, sandboxed and covered by file-based encryption. REMOVABLE, only by explicit choice, is `<app-specific dir>/downloads` on a card: an entry of `Context.getExternalFilesDirs` after index 0 whose `StorageVolume` is removable, `MEDIA_MOUNTED` and has a uuid matching `[A-Za-z0-9-]{1,36}` (the uuid is the download's `volumeId`; a volume without one is not offered). A card is not encrypted at rest (see the plan's decisions). Every root gets a `.nomedia` file. `freeBytes` is `StorageManager.getAllocatableBytes` on INTERNAL (falling back to `usableSpace` if it throws) and `usableSpace` on a card; `reserve` calls `allocateBytes(getUuidForPath(folder), bytes)` on INTERNAL only: by volume, never by file descriptor, because the descriptor form makes the file full length (`posix_fallocate`, else `ftruncate`) and the fetcher appends to it; the file's length is unchanged (**device check:** only a real phone shows the platform's behaviour). Tokens, the database and artwork are never on the card. `AndroidVolumesTest` (Robolectric `ShadowStorageManager`/`ShadowEnvironment`; the app-dir list, mount state, allocatable bytes and the allocate call are constructor seams).

**File names: `DownloadPaths` is the only code that turns ids into names.** Under a root: `<serverId>/<itemId>/media.<ext>` (`.part` while fetching; ext one of `mp4 m4v mov mkv webm ts`), `sub-<0..10000>.<srt|vtt|ass|ssa>`, `hls/seg-00000.ts` to `seg-19999.ts` (`.part` while a segment is written, `segmentPartFile`), `hls/local.m3u8`; and on INTERNAL only `<serverId>/art/<itemId>-<SLOT>-<tag>.img`. Every builder `require`s ids equal to their `JellyfinId`-normalised form, a tag `[A-Za-z0-9]{1,64}`, an index in range and an extension or format from the fixed sets (fixed messages, never the input), that a folder argument is exactly an item (or `hls`) folder, and then that the result's real path lies strictly inside its root. Real paths resolve every link in the part that exists (`Path.toRealPath`, which also sees a Windows junction that `File.canonicalPath` does not), and a path with a `.` or `..` part is refused outright. `deleteInside` deletes only what is inside a root (never a root itself) and never follows a link: a symbolic link (or junction) is removed as itself and its target is untouched. `DownloadPathsTest` (on this Windows build machine the link cases use directory junctions, since symbolic links need a privilege).

**Orphan sweep** (`DownloadPaths.sweep(known, servers, artwork)`, run by housekeeping, Milestone 4 Task 12): under each mounted root it deletes a `<serverId>` folder whose server is not saved, an `<itemId>` folder with no download row, an `art/` file with no `pinned_artwork` row (and any `art/` on a card), and anything whose name is not in the layout above (links included, removed as themselves); `.nomedia` stays. At most 100,000 entries per run (`SweepResult.stoppedAtLimit`); a root that disappears mid-sweep is skipped. Its inputs come only from `DownloadStore.sweepInputs()`: every download key, saved server and pinned picture read in one transaction (an artwork slot this version does not know is read as text and left out), and **null, so no sweep, while any download is RUNNING or VERIFYING**; the caller holds the queue's lock while sweeping so nothing starts in between (Task 12). `OrphanSweepTest`, `SweepInputsTest`.

**Device settings** (`DownloadPrefs`, private SharedPreferences `download_prefs`, as `playback_prefs` holds the player's): mobile data (default off: Wi-Fi only), storage and volume (default internal), default quality (default null: ask each time). An unknown name, a wrong type, or a removable choice without a valid volume id reads as the default. "Share downloads between profiles" is per server and lives in Room (`download_settings`). `DownloadPrefsTest`.

## Artwork (`data/images`, `ui/components/Artwork`)

Posters, backdrops and thumbnails: loaded, bounded and cached so the screens never hold a URL. The UI passes an `ArtworkRef` to the `Artwork` composable and nothing else.

- **`ArtworkRef(session, itemId, type, tag)`** has a private constructor; `ArtworkRef.of` is the only way to make one and returns null unless `itemId` is a normalised `JellyfinId` and `tag` matches `[A-Za-z0-9]{1,64}`. It is a plain class (no `copy`), so an unchecked ref cannot be derived from a valid one, and its `toString` carries no id or tag. `Item.primaryArtwork` / `backdropArtwork` / `thumbArtwork` (extensions in `data/images`, since `data/library` is not edited here) build refs from the item's own tags; an episode with no primary image falls back to its series poster (`seriesId` + `seriesPrimaryTag`).
- **Guidance for screens:** use only `Artwork(ref, ...)` with refs from `Item.primaryArtwork(session)` and friends; never construct a Coil type, loader, request or URL in a screen (`ArtworkBoundaryTest` fails the build on a reference to `ImageLoader`, `AsyncImage`, `ImageRequest` or `coil3` outside the artwork code); do not retain refs across an account change (they carry the session; see "Session check"); a failed picture shows the placeholder and the UI never retries it.
- **Request** (checked against the 12.4.0 reference, `GET /Items/{itemId}/Images/{imageType}`): through `ServerApi.getBytes`, path `/Items/{itemId}/Images/{Primary|Backdrop|Thumb}`, query `tag`, `maxWidth` (the width bucket), `quality=90` and `format=Webp`. Everything else the endpoint offers (`maxHeight`, `width`, `height`, `fillWidth`, `fillHeight`, `blur`, `backgroundColor`, `foregroundLayer`, `imageIndex`, `percentPlayed`, `unplayedCount`) is unused. `format` is `ImageFormat.Webp` (the enum also has Bmp, Gif, Jpg, Png, Svg): WebP decodes on Android 10 and later with no extra library; AVIF is not requested. Real Jellyfin serves images without authentication, but every request goes through `ServerApi` (verified address, token in the header) so that no unauthenticated or unverified request path exists. No retry loop here: `ServerApi` makes its one retry after a lost connection, and a 401 signs the account out locally there; the composable just shows the placeholder.
- **Width buckets** 160, 320, 480, 720, 1280: the smallest bucket at least the width Coil resolved for the composable (clamped to 1280; 480 when the size is undefined).
- **Cache keys** (memory and disk): `art:<serverId>:<itemId>:<TYPE>:<tag>:<bucket>`, built from the validated ref only, so never from an address (switching between the home and away address reuses the cache) and a new `tag` (the server changes it when the picture changes) is a new entry. **The key deliberately has no userId:** the picture of an item is the same bytes for every user, and who may see an item is already decided by the per-user visibility rule: a screen can only build an `ArtworkRef` (which needs a `Session`) for an item the app showed that user, and nothing can build one from raw strings except `ArtworkRef.of`. Two profiles on one server therefore share cached pictures, which costs no privacy the visibility rule does not already give. The memory cache is Coil's default.
- **Session check:** the first interceptor also asks whether the ref's session is still a usable signed-in account (`ServerStore.cachedToken(serverId, userId) != null` after the warm gate: an in-memory, token-free check, no network) before ANY hit, memory or disk, so a signed-out session gets `NOT_SIGNED_IN` and the placeholder, never a saved picture. The saved entries themselves stay for other accounts of the server. Screens must still not keep refs across an account change.
- **Disk cache and clearing:** one Coil `DiskCache` per server (`ArtworkDiskCaches`: folder `cacheDir/artwork/<serverId>`, each capped at 250 MB, so the cap is per server), evictable (pictures kept with downloads are `PinnedArtwork`, below). Coil's cache cannot list its keys, so a per-server cache is the simplest correct way to clear one server's pictures as a unit. `ArtworkEviction`, called from `AppGraph`'s store notifications, runs off the main thread: on **server removal** it removes the server's memory entries (keys starting `art:<serverId>:`), clears its cache and deletes its folder; on **sign-out** the pictures stay (another account of that server on this phone may still be signed in) unless no usable account remains for the server, which is then treated as removal. Failures are logged by kind only. Coil's own single disk cache is switched off.
- **Hostile-input bounds** (all tested in `ArtworkHostileInputTest`, `ArtworkPixelBudgetTest`; images are the largest volume of untrusted bytes the app handles):
  1. Body at most 8 MiB (`getBytes` enforces it on the declared length and while reading, chunked or not).
  2. `Content-Type` must be `image/jpeg`, `image/png` or `image/webp` (case-insensitive, parameters ignored; `image/jpg` is refused) before the body is read; SVG, GIF, HTML, anything else or missing is refused.
  3. The first bytes must show JPEG (`FF D8 FF`), PNG (signature) or WebP (`RIFF....WEBP`; another RIFF such as WAVE is refused), and the kind they show must EQUAL the kind the header named, else refused with nothing decoded or cached.
  4. The body must be complete **and exact** (JPEG end marker, PNG ends with `IEND`, WebP RIFF length equals the size). A genuine image with trailing bytes after its end is therefore refused and shows the placeholder (the price of reliable truncation detection).
  5. Animated images are refused, not shown as a still: an APNG (an `acTL` chunk before the image data) and an animated WebP (the `VP8X` animation flag). Detection is a few bytes. GIF is refused at steps 2 and 3.
  6. The declared dimensions are read from the header only (`inJustDecodeBounds`, no pixels) and refused above 8192 px a side or 40 megapixels.
  7. Only then is anything written to the disk cache (the editor is aborted on failure), so a refused or failed download leaves no entry. A saved entry gets the same checks, read once, before it is served; a bad one is deleted and fetched again. A snapshot or editor is always closed or ended, even when the caller is cancelled while it is being opened (`ArtworkResilienceTest`).
  8. Decoding (`ArtworkDecoder`, the only decoder) repeats the first-bytes and dimension checks before any pixel is allocated, then uses a power-of-two sample size (`ArtworkLimits.sampleSize`): the width stays under twice the bucket and the decoded bitmap never exceeds **4,000,000 pixels (16 MB at ARGB_8888)**; anything that cannot meet that is refused. At most 2 decodes run at once. A picture that fails to decode is evicted from the cache, so the next request downloads it again.
- **Worst-case transient memory for a full grid.** Decoding: at most 2 decodes x 16 MB = 32 MB (a normal 320-wide poster is about 0.6 MB, so a screenful of about 20 held by Coil's memory cache is roughly 12 MB, an LRU that Coil trims to its percentage of memory). Downloading: a body is held whole while it is checked (the buffered source and the byte array, up to about 16 MB for an 8 MiB body) and OkHttp runs at most 5 requests per host at once, so the pathological ceiling (five hostile 8 MiB bodies) is about 80 MB, plus the decodes; real posters are 20 to 100 KB.
- **Component allowlist.** `ArtworkLoader` builds the one `ImageLoader` (`AppGraph.imageLoader`). The composable takes it from `LocalArtworkLoader`, provided once in `MainActivity` with **no default**: without one, a screen showing a ref fails loudly in debug builds and tests, and shows the placeholder in release (logging a fixed line), so the app can never silently fall back to a default Coil loader. `ShoalwatchApp` also implements `SingletonImageLoader.Factory` with the same loader (belt and braces, proved with the real application class by `ShoalwatchAppImageLoaderTest`). Coil's service-loader discovery is off, and `coil-network-okhttp` (or any Coil network module) is not a dependency, so nothing in the app can fetch a URL. Final component list: interceptor `ArtworkOnlyInterceptor` (first), keyer `ArtworkKeyer`, fetcher `ArtworkFetcher.Factory`, decoder `ArtworkDecoder.Factory`. Coil 3.3.0 always adds its own built-in mappers, keyers and fetchers after those (string and path to Uri, file, content, resource, asset, data, byte array, bitmap, drawable) and its bitmap decoders: they cannot be removed. They are unreachable because `ArtworkOnlyInterceptor` runs first and fails any request whose model is not an `ArtworkRef` (`ModelNotAllowedException`): a `"https://..."` String, an `android.net.Uri`, an `HttpUrl`, a `File`, a path, `file:` / `content:` / `data:` strings and a byte array all fail with no request (`ArtworkLoaderTest`, `ShoalwatchAppImageLoaderTest`). Our decoder is consulted first and always decides.
- **Pinned with downloads (`PinnedArtwork`, Milestone 4).** A download's pictures live outside the evictable cache, on INTERNAL storage only: `<root>/<serverId>/art/<itemId>-<SLOT>-<tag>.img` (`DownloadPaths.artworkFile`) with a `pinned_artwork` row each (written INSERT OR IGNORE then UPDATE; the slot read back as text, an unknown one dropped). They are fetched by `ArtworkRequest.download`, the loader's own request and checks (one shared function, so no other parser touches server bytes), at 720 px (BACKDROP 1280), and every read re-runs `ArtworkValidation.check`: a file that fails (cut short, tampered with) is deleted with its row, and the placeholder shows. `ArtworkFetcher` reads memory, then the disk cache, then `PinnedArtwork.find` (any width, the same tag), then the network; the session check runs first, so a signed-out profile sees no pinned picture either. An episode's fallback to the series poster finds the pinned series poster. `AppGraph.pinnedArtwork` is passed to `ArtworkLoader.build`. Tests: `PinnedArtworkTest`, two cases in `ArtworkFetcherTest`.
- **Offline.** Reads go memory, then disk, then pinned, then network. With a disk hit the picture shows with no request; with none, `ServerApi` fails `OFFLINE` (or a network error) and Coil's error state shows the placeholder: never a crash, never a loop. Cancelling (a list scrolling away) cancels the OkHttp call and leaves nothing cached.
- **Composable.** `Artwork(ref, contentDescription, modifier, aspect, title)` is stateless (no ViewModel). The box is `POSTER` (2:3), `WIDE` (16:9) or `SQUARE` from the first frame (`aspectRatio`, so nothing jumps); the caller sets the width. A rounded brand-tinted block (surface variant, leaning 8% to 29% towards the primary or tertiary container by a pure function of the item id; the letter is at least 3:1 against every tint in both themes, `PlaceholderContrastTest`) with the title's first letter in `headlineMedium` shows while loading, on every failure and when `ref` is null: no broken-image icon and no animation. Once the picture has loaded the block is removed and the picture sits on the theme surface, so a transparent PNG cannot show the letter through. The picture fades in over 150 ms, none when the system "remove animations" setting is on. The request sets `Precision.INEXACT` itself (a request built without it is `EXACT` and would never hit Coil's memory cache for a bitmap of a different size). The letter is not announced; `contentDescription` is exposed as given (null for a decorative picture inside a labelled card).
- **Logging:** a refusal logs its reason (a fixed word) through `AppLog` in debug builds; never a ref, tag, URL or response content. Exceptions carry fixed messages.
- **Deferred (M9)** from "Authenticated requests" still stands: every artwork request reads the full `Server` to build its client configuration, which is now a per-image cost when a grid loads; a settings-version signal from the store would remove it.

## Jellyfin client decision (SDK vs direct)

**Decision: `JellyfinGateway` is implemented directly on OkHttp + kotlinx.serialization; the Jellyfin Kotlin SDK is not used for any request.**

- AAFin's `JellyfinClients.kt` shows `OkHttpFactory(httpClient)` does accept an injected `OkHttpClient`, so injection is possible. But the SDK builds its own requests and applies its own authorisation and client options (its sources were not audited for this task), and proving that *every* byte of SDK traffic passes our guards and trust policy would need an audit of the SDK internals on each upgrade.
- The sign-in surface is seven small endpoints, so a direct implementation is cheaper than that audit and gives one auditable HTTP path: every call goes through `HttpClientFactory.clientFor(config)`, so the cleartext, header, token and client-certificate guards, the trust policy and the pin all apply.
- Endpoints: `GET /System/Info/Public`, `GET /QuickConnect/Enabled`, `POST /QuickConnect/Initiate`, `GET /QuickConnect/Connect?secret=`, `POST /Users/AuthenticateWithQuickConnect`, `POST /Users/AuthenticateByName`, `POST /Sessions/Logout`. Unauthenticated calls send `Authorization: MediaBrowser Client, Device, DeviceId, Version` without a token (the interceptor applies it from the config).
- **Untrusted responses (S11):** bodies over 1 MiB are refused, JSON is decoded with `ignoreUnknownKeys`, a missing token or user id is an error, ids must be GUIDs, display strings are sanitised. Error text never includes response content.
- **Documented exception to "no secrets in URLs":** the Quick Connect `secret` is sent as a query parameter for the `Connect` poll because the Jellyfin API requires it. It is short-lived, never logged, and the client logs no URLs.
- **No redirects on any call:** credentials sit in bodies and queries that OkHttp would resend on a 307/308, so no factory client follows redirects and any 3xx is an error (`SERVER_NOT_FOUND`).
- **Client holder and eviction:** `ServerClients` (data/servers) holds one client per configuration. `ServerNetConfig` equality is by value (authorities, cleartext flag, pin, client-cert alias, headers, `authKey`) and excludes the token-provider lambda; `authKey` is null for anonymous calls or `serverId:userId`. `ServerStore` reports every account upsert, account removal (in a `finally`), server removal and server upsert (old and new addresses) to `ServerClients.evict`, which drops matching clients and evicts their idle connections from the shared pool (other servers' idle connections may go too; harmless).

### Token rules

- `ServerStore` keeps an in-memory `(serverId, userId) -> token` map (`cachedToken`, suspend-free, no per-request decryption).
- It is **never filled as a side effect of reading rows** (a stale snapshot could resurrect a revoked token). It is written only by `upsertAccount` (new token) and `warmTokens()` (loads all saved accounts once; `AppGraph.tokensWarmed` starts it at app start; safe to repeat).
- **Cold-start gate:** `awaitWarmed()` completes when the first `warmTokens()` has finished, successfully or not; `awaitActive()` is `active()` after it. Anything that needs the active account for an authenticated request goes through them.
- `warmTokens` never throws (except cancellation): a Room or Keystore failure is logged by kind only and leaves the map empty, so requests fail closed as `NOT_SIGNED_IN` while start-up still proceeds.
- `removeAccount` and `removeServer` run in `NonCancellable`, so the token clear and client eviction happen even if the caller is cancelled. All writers share one `Mutex`, and `warmTokens` re-reads the rows inside the lock, so a removal that finished first is simply absent.
- `authenticated` is handed `store::cachedToken`, so a cached client (which keeps the first provider for its key) sends the current token after a re-sign-in.
- **A missing token fails loudly:** an authenticated request whose lookup finds no token is refused before it is sent (`BlockedRequestException` wrapping `NOT_SIGNED_IN`), never sent anonymously.
- **Revocation** reads the account's token explicitly (`ServerStore.token`, on IO) and sends it with `ServerNet.revocation`, the one place a captured token string is allowed. `JellyfinGateway.logout` always runs that configuration through `ServerClients.oneOff`: a client built for that single call by `HttpClientFactory`, never stored in the per-account cache (its key starts `revoke:`, so it could not equal a live `serverId:userId` key anyway, and `ServerClients.clientFor` refuses such a key with a `require`), after which the shared connection pool (one pool for all clients) is trimmed of idle connections in a `finally`. Nothing is put in the token map, a live authenticated client for the same account is neither reused nor touched, and no client holding the revoked token is left behind (`RevocationClientCacheTest`). Then the account is removed.

## Home / away address selection

- `AddressSelector` (data/servers) turns a server's home and away addresses into a live `StateFlow<Connection>` (`Checking` / `Online(address, isHome)` / `Offline`), one probe loop per server id (`connection(serverId)`; `refresh()` for every server; `refresh(serverId)` for one; `forget(serverId)`, called by `ServerStore.removeServer`).
- **Coming back after an outage.** Nothing is sent while the state is `Offline`, and a probe otherwise re-runs only on a network change or a settings change, so two things bring a server back. (1) **A user's own refresh** (pull, a banner's Try again or Retry, Home's menu Refresh, Search's retry) first asks `refresh(serverId)` when that server is `Offline` (`reprobeIfOffline`, called from `ItemActions.pull` and `SearchViewModel.retry`, one place for every screen): the state becomes `Checking` at once, so the library refresh that follows waits in `awaitOnline` for the new probe and is sent only if it verifies; if the server is still down the user sees the offline state. (2) **Without the user:** while BOTH something collects an `Offline` server's connection (`subscriptionCount`; in practice Home's ViewModel always does, and it lives on in the background) AND the app is in the foreground (`ProcessLifecycleOwner` at least `STARTED`, injected into `AddressSelector` from `AppGraph` as a `Flow<Boolean>`), and the reason is ordinary unreachability of a saved server, the selector re-probes after 5 s, doubling to 60 s; the wait resets when the server is `Online`, on a network change, and on coming back to the foreground, which also probes at once. These automatic probes are quiet: the state does not go to `Checking` first, so a probe that fails again publishes an equal `Offline` and the connection chip neither flickers nor is announced again; only a success (or a new reason) shows. A user's own refresh still goes to `Checking`. A security reason (changed or untrusted certificate, cleartext blocked, client certificate needed, damaged pin) is never retried by itself; nothing is probed for a server nobody has asked about, and `refresh(serverId)` / `refreshIfOffline` never start probing for an unknown or removed server (one lock for the look-up and the reset, so a `forget` cannot leave an orphan entry). Cost: one or two small anonymous requests at most once a minute once settled, and none while the app is in the background. `HomeViewModel`'s `connectionRegained` then refreshes Home. `AddressSelectorRecoveryTest`, `AddressSelectorForegroundTest`.
- **Settings from the store:** each probe reads the server from its `ServerSettingsSource` (`ServerStore`) when it starts, and the selector watches the store: a change of addresses, pin, cleartext consent, client certificate or headers resets the state to `Checking` at once and re-probes; a server that is no longer saved is `Offline` and is never probed. A store failure on a probe's read publishes `Offline` and the loop carries on. If the store's `servers` flow itself fails, the watcher publishes `Offline` for every live server and drops in-flight results, then resubscribes after a backoff of 1 s doubling to 30 s (reset by a healthy emission); the first emission after a failure re-probes every live server. During the outage a probe started meanwhile (it reads the store directly) can still publish `Online`, and settings changes made during the outage are picked up within the backoff; `AuthRepository` re-reads the store before sending anything, so a stale `Online` cannot send a credential with old settings (`AddressSelectorStoreTest`).
- **Probing is anonymous** (`ServerNet.anonymous`, `publicInfo`): no token reaches an address before it has proved to be the server. An address counts only if its reported id equals `server.id`; a different server there is unreachable.
- **Timing:** home 1.5 s, away 5 s, probed concurrently with coroutine timeouts (a timed-out or no-longer-needed probe cancels its HTTP call). Home answering correctly wins at once; otherwise away is used when it answers; otherwise `Offline`. A missing address is skipped.
- **States:** `Checking(previous: Online?)`, `Online(address, isHome)`, `Offline(reason: AppError.Kind?)`. `reason` is set for security problems the user must act on (`TLS_PIN_CHANGED`, `TLS_UNTRUSTED`, `CLEARTEXT_BLOCKED`, `CLIENT_CERT_REQUIRED`, and a damaged saved pin as `TLS_UNTRUSTED`), preferring one if home and away fail differently; null for ordinary unreachability and identity mismatch. No address is ever in a state's text.
- **Re-probing and staleness:** on every `NetworkMonitor.changes` emission and on `refresh()` the state becomes `Checking(previous = the old Online)` **synchronously**, so a pre-change `Online` is never still published; a generation counter makes check-and-set atomic and discards any in-flight probe that started before the latest change. The probe then starts after a 500 ms debounce for network changes or at once for `refresh()`. Requests collapse through a conflated channel: one more probe after the running one, never overlapping. `forget(serverId)` publishes `Offline()` first, so a collector still holding the flow stops showing Online.
- **What `awaitOnline(serverId)` proves:** the address answered as this server, with the settings saved when the probe started, since the last network change the OS reported. It does not prove the answer came from the real server on plain http, or that the phone has not just moved network; that is why `AuthRepository` repeats the identity check on the chosen address immediately before sending (see "Credentials"). A caller whose request fails calls `refresh()`.
- `AndroidNetworkMonitor` registers `registerDefaultNetworkCallback` when the first collector arrives and unregisters after the last (`shareIn` with `WhileSubscribed`), with signal-strength-only capability updates ignored. `AppGraph` owns the process-wide `appScope` they run in.

**One rule for every screen: the session.** Each ViewModel takes `ServerCatalog.activeSession()` and restarts its flow with `flatMapLatest` when it changes; the first thing a new session emits is an empty "loading" state, and Home also compares the session of the content with the session on screen, so even a late emission from the old flow is dropped. `UiState` carries the `Session` its items belong to, and artwork references are built in composition from `Item.primaryArtwork(session)` and friends, never kept. **The back stack goes with the session.** `ClearBrowsingOnSessionChange` (in `AppNavHost`) watches `ServerCatalog.activeSession()`: when it changes from one session to another, or to nobody (account switch from Home or Servers, sign-out, a removed account or server, a 401 that ends the sign-in), the whole back stack is popped (no `saveState`) and the app goes to Home, or to Welcome when no server is left. The tabs' saved states are cleared on every path, BEFORE the new start is navigated to (`clearBackStack` restores what a tab saved and then pops it, so after the navigate it would take the new Home with it). **Account screens are not tied to a session:** if Servers, a server's settings, Add server or Sign in is on top, the stack becomes `[Home or Welcome, that screen]`, and it is the very same entry and ViewModel (popped with `saveState` and restored on top), so a sign-out or removal made there still shows "signed out here only / may still be live on the server" or its error, and a plain switch on Servers leaves the user on Servers. The first value (start-up) and a change from nobody (the sign-in flow navigates to a fresh Home itself) do nothing, and a fresh Home already alone on the stack is left as it is, so `fresh=true` is never lost. When the store's update for a sign-in arrives before the sign-in screen has navigated, the kept Sign in entry still navigates to its own fresh Home, which is the only Home ever composed. **A store failure is not a sign-out:** a nobody that comes with `readFailed` is ignored (it watches `activeAccount`, which does not drop a repeated value, and compares with the session from before the failure). Meanwhile every screen shows its signed-out state, so nothing of the session is shown, but the stack stays; when Try again reads the same session back nothing moves, and if the store then says another account or nobody, the reset happens at that point. Library, Series and Detail opened by one account therefore never run as another (`SessionChangeNavigationTest`). No session shows the Milestone 1 signed-out notice (`SignedOutNotice`, a button to Servers and accounts).

**Freshness to UI.**

| `Freshness` | Shown |
|---|---|
| `Fresh` | nothing |
| `Refreshing` | a 4dp progress line at the top (`RefreshLine`, always reserving its height); skeletons only when there is no content yet |
| `Stale(OFFLINE / NETWORK / TIMEOUT)` | banner "You're offline. Showing what's saved on this phone.", Retry |
| `Stale(UNAUTHORISED / NOT_SIGNED_IN)` | banner "Your sign-in has expired", Sign in (to `sign_in/{serverId}`) |

**Refresh triggers.** Pull-to-refresh (Home, library grid, series, detail) and every Retry call `Library.refresh` with the right `RefreshTarget`; a screen also refreshes when the connection of the active server becomes `Online` after being `Offline` or `Checking` (`connectionRegained`, which does not fire for the first reading), and Home refreshes once when it is the one reached by a successful sign-in (`fresh`; signing in clears the back stack, so Home is the only screen left to refresh). Nothing refreshes on a resume or a recomposition: collecting already refreshes what is due.

**Paging (library grid).** One continuous grid (`GridCells.Adaptive(112dp)`, two columns on a phone) with no pages. The grid tells the ViewModel whether the end is within about two screens; the ViewModel calls `loadMore` when `canLoadMore` AND nothing is running AND the last attempt did not fail AND (the list is empty OR the end is in view), and calls it again when freshness returns to `Fresh` with the end still in view; a failure stops the chain until Retry. An empty list that can load more loads, it never says "empty". The same `(parentId, ListShape, Sort, ItemFilter)` tuple is used for `children`, `loadMore` and `RefreshTarget.Children`; the shape is `ListShape.forLibrary(kind)` from the library's entry in Home's views (a collection or folder uses the direct children of any kind). Sort and filter live in `BrowseMemory` (in the app graph, per account and library, memory only) so they are remembered while the app is open; the grid state is a saveable `LazyGridState`, so the scroll position survives rotation and returning from a detail page. After a favourite change in a list filtered by favourites the list is refreshed.

**The item-actions helper** (`ItemActions`) is the only code that calls `Playstate`, and the one guard for a screen's other background calls. It runs each action in the ViewModel scope as the session it was asked for, keeps a set of work per session (`OwnedWork(session, Work(itemId, kind))`) so the tapped control shows a small spinner until the server has answered (actions queue per user, so a second tap's change shows only when the first has finished; a second tap on the same control, for the same session, is ignored while it works), and sends an `AppError`'s `userMessage` (or a plain message for anything else) to a channel the screen shows in a snackbar. Each message travels with its session and is checked again when it is received, so one that waited past a switch of account is dropped; the snackbar on screen is dismissed when the session changes (`CollectMessages`, `DismissOnSessionChange`, also on the Search tab). If the change worked but `onDone` (the refresh after it) failed, the message says so ("Your change was saved, but the list could not be refreshed.") and never that the change failed. `guard` catches a failure of a Room-backed library flow at the ViewModel (never `CancellationException`), reports it and emits an empty `Stale(UNKNOWN)` value, so Home, a grid, a series or an item shows an error state with Retry instead of ending the app; the failed flow then waits for the next `pull` (every Retry and pull-to-refresh) and subscribes again, so Retry brings the screen back once the database works (one mechanism for all four screens; a flow that has not failed is never restarted; `RetryAfterLocalFailureTest`). Home shows a local failure as ONE message that says what's saved on this phone could not be read, with Try again, and no refresh banner (`HomeUiState.localFailure`). The grid's Retry while its shape is not known (Home's libraries not saved yet, or its own flow failed) refreshes the list of libraries instead of doing nothing, re-probing an offline server first like every user refresh. `pulling` is a set of sessions, counted per session, so overlapping pulls keep the indicator until the last ends. The grid keeps its page loads in flight per session (A -> B -> A starts no second load) and turns a local page-load failure on an empty grid into the error state with Retry; its scroll position is keyed by session. Nothing is shared between sessions: a screen shows only the work of the session on screen (`forSession`), the pull indicator and page-load flags are per session, and a failure whose session is no longer on screen is dropped, not queued for the next user. `pull` (the user's own refresh) and `attempt` (every other refresh, load more and switching account) catch any failure, so a full disk or a lost account shows a message and never ends the app. A rolled-back change reappears on screen by itself, because the screens observe the database.

## Server admin (`data/admin`, `ui/admin`)

Native screens (SPEC §3.4) for an account its own server confirms as an administrator: a dashboard (server name, version, "Restart needed", who is watching and whether the server is converting it, with Message, Pause and Stop), Libraries (scan all or one, with progress), Scheduled tasks (run now, stop), Users (enable or disable), Activity, Devices (remove one), Restart or shut down, and a button that opens the full dashboard in the browser. No web view, no logs screen, no password reset or user creation (those stay in the browser dashboard; see the decisions below).

**The gate (who is an administrator).** `AdminAccess` (the one `AdminRights`) asks `GET /Users/Me` as the session and answers ADMIN only if the answer's `Id` is that user and `Policy.IsAdministrator` is true and `Policy.IsDisabled` false. It holds **one `(Session, AdminStatus)` in memory, for the active session only**, and forgets it on every active-session change (to anyone or nobody), fed by `ServerCatalog.activeSession()` in `AppGraph`. A check for a session waits (at most 5 s) until that session is the active one, then takes a generation; an answer that arrives after another change is dropped (NOT_ADMIN). Being unreachable (OFFLINE, NETWORK, TIMEOUT, SERVER_ERROR, TLS) keeps an earlier answer for the same session; 401, 403 and NOT_SIGNED_IN are NOT_ADMIN. Nothing is saved: after process death the app starts with no rights and asks again. `allows(session)` is true only for exactly `(session, ADMIN)`.

- **Entry:** "Server admin" shows on the active account's server card in Servers and accounts only while `allows` holds; `ServersViewModel` checks once per active session.
- **Each screen's guard (`AdminGuard`):** the screen belongs to the session that was active when it opened. The gate is Checking until the rights answer, then Open, and closes **for good** (never to reopen in that ViewModel) when the active session is anything else (even the owner again later), the rights stop saying `(owner, ADMIN)`, a 401 or NOT_SIGNED_IN ends the sign-in (then `rights.lost`), or a 403 that a fresh check confirms. While the screen is visible, open and online the rights are re-checked every 60 s. Offline keeps the gate Open with `online = false`: nothing loads and every action is off.
- **Closed means gone.** Every UI state is built from `frames` and masks everything once Closed; `dropLoaded` clears lists, confirmations and typed text (`messageText`, the typed word); every poll writes only while Open; `AdminWork` runs `onDone` only while Open; `AdminScaffold` draws nothing; `AdminRouteEffects` calls `leaveAdmin`, which pops every admin screen at once and never pops Home. Admin routes are deliberately **not** account routes, so `ClearBrowsingOnSessionChange` pops them on any session change too. A closed gate says nothing (a message would tell the next profile something about the last one).
- **The gateway refuses too (defence in depth).** `AdminGateway` checks `allows(s)` before every call except `me` (nothing is sent: FORBIDDEN), refuses this phone's own device and the signed-in administrator's own account, and asks `allows(s)` again **immediately before each action is written** (`ServerApi`'s `sendIf`): a profile switch while an action waited for the server's address sends nothing. `AdminWork` also cancels an action still running when its gate closes.

**Endpoints** (each checked against `docs/reference/jellyfin-openapi-12.4.0.json`; every call through `ServerApi`, so warm gate, verified address only, the account's own client, the token only in `Authorization`, 401 signs the account out locally):

**Untrusted input** (`AdminDtos`, `AdminMappers`, the S11 boundary). Every DTO field is nullable with a default and decoded with `JsonBodies.JSON` (`ignoreUnknownKeys` only), with a byte cap per answer (1 to 4 MiB; 256 KiB for a policy read). `DeviceInfoDto.AccessToken`, `SessionInfoDto.RemoteEndPoint`, `SystemInfo.LocalAddress`, every path and folder location, `IconUrl`, `LongErrorMessage` and `Overview` are **never declared**, so never mapped into a model, kept, logged or printable (`AdminBoundaryTest`). The whole answer is first parsed into a temporary JSON tree that is dropped once the declared fields are read, so those values do pass through memory for that moment. Lists are capped (sessions 100, libraries 100, tasks 200, users 500, devices 500, activity 1,000 in all) and de-duplicated by id (the first copy wins), so lazy-list keys cannot collide; one bad element costs only itself. Every display string goes through `displayText` with a bound; numbers are range-checked (a NaN or out-of-range progress is null); dates parse leniently to null. Ids: user and library ids are normalised `JellyfinId`s; session and task ids `[A-Za-z0-9]{1,64}`; a device id is listed if it is printable ASCII (one over 256 characters is listed under a `#`-prefixed digest), and **removable only inside `[A-Za-z0-9._~+/=:-]{1,256}`**, because `DELETE /Devices` takes `id` as an array the server may split on a comma. The gateway accepts only ids in the form this seam returns (anything else is SERVER_NOT_FOUND, nothing sent). A device listed by several accounts is one row naming every user, with the newest row's name.

**The policy round-trip** (`UserPolicyEdit`). `POST /Users/{id}/Policy` replaces the whole policy, so the body is the server's own `Policy` object as just read, copied key by key with only `IsDisabled` replaced: every key (known, unknown or future), number literal, null and nested array goes back as it came. Nothing is posted when the answer's `Id` is not the user asked for, there is no `Policy` object, or `AuthenticationProviderId` / `PasswordResetProviderId` (required by the schema) is missing.

**Every action is sent once and never retried.** All ten actions go through the gateway's one `send`: `retry = false` (no `ServerApi` retry) and `sendOnce` (see "Authenticated requests"), so OkHttp neither resends one on a dropped kept-alive connection nor follows a 503 `Retry-After: 0` or a 408 with a second copy. One action runs at a time per screen (`AdminWork.running`), every action button is off unless online and idle, and every ViewModel entry re-checks the same rule. Destructive actions are confirmed naming the target; the confirmed target is re-checked in the latest list before sending (gone: "That's no longer on the server", list refreshed, nothing sent), and Pause, Stop and Message also check that the session still plays the item the dialog named (else CHANGED, nothing sent). Restart and shut down need the typed word ("restart" / "shut down", trimmed, any case, spaces collapsed; a blank word never matches); the IME action only hides the keyboard; after a request both buttons stay off on that screen. Scans and Run now are not confirmed (they can simply be repeated, and are off while one runs); stopping a task is.

**Loading only while visible** (`AdminPoller`). A screen loads only while it is started, its gate is Open and the server Online, one load at a time, through `collectLatest` on `AdminGuard.live`; leaving cancels a load in flight and a kick while not live is not remembered. A failed load is retried after 15 s (reads only). Dashboard: status then sessions every 5 s. Libraries: every 3 s while a scan runs, else only on a kick. Tasks: 3 s while one runs, else 30 s. Users, Devices, Restart: on open and on Refresh. Activity: page 0 on open and Refresh; older pages only by "Show older entries", from `nextStartIndex`, de-duplicated, sorted newest first on the client (the server's own order is unproven), at most 1,000, and a page arriving after a Refresh or a close is dropped. No WebSocket: it would be a new token path outside `ServerApi`.

**`FLAG_SECURE` on every admin screen and dialog.** They show other household members' names, viewing, devices and sign-in times; on a shared tablet the recents preview would keep that under the next profile. Every `*Screen` draws through `AdminScaffold` (its own Scaffold and `LazyColumn`, 840dp cap), which holds `SecureWindow` in every gate state; every dialog is `AdminDialog`, an `AlertDialog` with `properties = SecureDialog` and the obscured-touch filter. `AdminBoundaryTest` fails on a screen function without the scaffold, a raw `AlertDialog`/`Dialog`/popup in `ui/admin`, or a route without `AdminRouteEffects`.

**Nothing persisted.** Admin data lives only in ViewModel memory while its screen exists. No Room table, `SharedPreferences`, DataStore, file, `SavedStateHandle`, navigation argument (no admin route carries one), clipboard or notification; the message text and the typed word live only in the ViewModel. Logs carry the call name and `AppError.Kind` only. `AdminBoundaryTest` scans `data/admin` and `ui/admin` for every storage, logging and printing API, and the UI for `ServerApi`, `data/admin/api`, OkHttp, `Uri.parse` and `Intent.ACTION_VIEW`; admin endpoint paths may appear only in `AdminGateway`, where every call but `me` must open with `gated(` and the POST/DELETE must carry `sendOnce = true` and `sendIf`.

**The browser dashboard** (`BrowserDashboard`). "Open the full dashboard in your browser" opens `{verified address}/web/` (base path kept) with `ACTION_VIEW` and `CATEGORY_BROWSABLE`, from the application context (a new task), after `awaitOnline`. Nothing of the sign-in goes with it: no token, header, query, fragment, user name or password (refused if the URL has any). The address is one the user saved, never a server-supplied string. The browser asks for its own sign-in. On a plain-http home address the link is plain http (the user chose http; no credential is sent by the app).

**Choices in the screens.** `AdminScreenModel.frames` is protected and `dropLoaded` is named so (not `clear`, which clashes with `ViewModel`). `AdminNotice.fallback` shows a neutral word ("Unnamed user") for an empty argument; notice arguments are format arguments, never format strings. `AdminWork.fail` shows a problem without sending anything. `sendMessage(context)` and `openDashboard(context)` use the context synchronously (the header string) or keep only its application; `PowerViewModel` reads the typed words through the application context. ViewModel tests run through `ModelsInTest` / `adminTest`, which stops a failed test's pollers spinning in virtual time (production pollers already stop when not visible).

**Decisions** (the plan's "Decisions made", in short): coverage follows SPEC §3.4, plus read-only extras from the same answers (users' administrator, downloads and libraries lines; Pause beside Stop); no logs screen (logs hold addresses, paths and tokens); no password reset or user creation; no Resume button; `FLAG_SECURE` on every admin screen; admin status in memory only; the gateway refuses without `allows`; the entry is on the active account's server card; a closed gate leaves silently; admin routes are session-bound; polling, not the WebSocket; every action sent once; scans and Run now unconfirmed; targets re-checked before sending; the policy round-tripped, never re-encoded from a DTO; you cannot disable yourself or remove this phone's device here (Sign out in Servers and accounts is the tool); `activeWithinSeconds=960`; per-library scan with documented parameters only; full-scan progress from the `RefreshLibrary` task, per-library from `VirtualFolderInfo`; activity sorted on the client; one row per device id; secret-bearing fields never declared; device ids only as a query value; `/web/` on the verified address; strings in `strings_admin.xml`; no new `AppError` kinds.

**Known limits.**
- The client gate is a convenience: the server enforces the real permission. A hostile or compromised server can claim anyone is an administrator; that only shows screens the server itself would refuse.
- Between a demotion on the server and the next re-check (≤ 60 s) or 403, read-only screens can still show what that account could read without elevation (`/Sessions`, `/Users`, `/System/Info` are `DefaultAuthorization`).
- An action already written when the profile changes completes on the server; only its answer is dropped.
- Disabling a user does not end their current playback (Jellyfin's behaviour).
- After an UNKNOWN answer (server unreachable at that moment) the Servers screen does not ask again until it is opened again or the session changes (review 1-6 M4, carried).
- A device id outside the strict set, or over 256 characters, can be removed only in the browser dashboard; the Devices screen says so.
- Navigation's implicit route deep links could open `MainActivity` on `admin`; the gate shows "Checking…", then closes and pops for a non-admin (review 1-6 M9; a device check). Closed in Milestone 7: `MainActivity.sanitised` drops every intent's data (see "App lock").
- Unproven until Ben's server: see `docs/security/milestone-6-check.md` §5.

## Player engine and controller (`PlayerEngine`, `ExoPlayerEngine`, `PlaybackController`)

One controller per player screen, bound to one `Session`, on the main thread. It drives a small `PlayerEngine` interface, so all behaviour is unit-tested with `FakePlayerEngine` under virtual time; ExoPlayer is touched only in `engine/ExoPlayerEngine.kt` and `engine/MediaItems.kt`, Media3's cues and subtitle view only in the engine's subtitle files (`SubtitleFiles.kt`, the app's own readers `SrtFile.kt`, `VttFile.kt`, `AssFile.kt` and `SubtitleScanner.kt`, `SubtitleFrame.kt`, `SubtitleSurface.kt`; Media3's text parsers nowhere) (`Media3BoundaryTest`). Screens get a controller from `AppGraph.playbackController(session, scope, autoplayNext)` and read `state` (`PlaybackState`: no URL, route, token or Media3 type).

- **The engine (`ExoPlayerEngine`):** `ExoPlayer.Builder` with audio attributes usage media / content movie and audio focus handled by ExoPlayer; `setHandleAudioBecomingNoisy(true)` (reported as `BecameNoisy`); seek increments 10 s; **no wake mode** (the player screen keeps itself on; `Media3BoundaryTest` bans `setWakeMode`). Since Milestone 4 the app holds `WAKE_LOCK` for WorkManager's foreground download work only (see "Downloads in the background"); the player never uses it.
  - **Bytes:** one `DefaultMediaSourceFactory(ItemBytes.Factory(OkHttpDataSource.Factory(calls)) { current })`. `ItemBytes` (see "Checked playable") passes http(s) to `OkHttpDataSource` only while the current item is remote, whose `Call.Factory` delegates to that item's `MediaRoute` call factory (the account's own guarded client: pin, client certificate, custom headers, cleartext guard, token in the header only), and opens a file only while the current item is saved and the file is inside its folder. `load` switches the current item and `release` clears it, so after release nothing can be read. No other data source exists in the app: `Media3BoundaryTest` forbids the default HTTP, file and data sources and the cache source anywhere, a media source factory over the context, the stock HLS and progressive factories and the stock bitmap loader anywhere, allows `SavedMediaDataSource` only in the engine, and requires every media source factory (the player's and the probe's, exactly two) to be built with `DefaultMediaSourceFactory(ItemBytes.Factory(OkHttpDataSource.Factory(...` and every media session with its own bitmap loader (M-8).
  - **What Media3 is handed (`MediaItems.build`):** the URI from `MediaRoute.url` (verified address + path + query; credential names already stripped by `MediaPaths`), `application/x-mpegURL` for HLS, no subtitle configurations, and the title metadata.
  - **Media session:** `MediaSession.Builder(context, player).setId("shoalwatch-player-<n>")`, built at the engine's first `load` (so only after `ActivePlayback.begin` has ended, and so released, any earlier player) with an id unique per engine (Media3 refuses two live sessions with one id: Task 6 review I-1; `ExoPlayerEngineTest`, and the order is asserted with `FakePlayerEngine` in `PlaybackControllerReviewTest`), no `MediaSessionService` (no notification, no exported component, no permission), released in `release()`. Its artwork loader (`NoArtwork`) loads nothing, so Media3's own one (over a default data source, outside the guarded client) is never used (Task 6 review M-5). Its callback accepts every controller with only play/pause, seek back/forward/in item, current item and metadata, and no session commands, so a headset or Bluetooth controller cannot set media items, speed or tracks. The session is built over `ExoPlayerEngine.sessionPlayer`, a `ForwardingPlayer` that refuses `play()`, `playWhenReady = true`, and the `prepare()` and `seekToDefaultPosition()` that its play action runs first on a failed or ended player (final-fixes review m-3), while the host is stopped (`PlayerEngine.setHostStopped`, set by `PlaybackController.onHostStopped` and cleared by `onHostStarted`), so a headset, Bluetooth or media-button play cannot start the film behind a locked screen or after Home; pause and seek still work, and the app's own calls go to the player directly (final review N-4; `ExoPlayerEngineTest`, `HostStoppedTest`). Because the app's own load goes to the player directly, the controller keeps the host state too: while it is stopped (`onHostStopped` until `onHostStarted`) every `engine.load`, the one place the engine is loaded, is made with `playWhenReady = false`, whether the load was already running (an open, a quality, audio or subtitle reload) or starts later (a fallback to a transcode, a re-resolve, a new route, the audio re-ask on Ready, a burn-in re-ask), so nothing plays sound behind the lock screen; once in front again the user's Play plays (final-fixes review I-3, subtitle-parsers review I-3; `HostStoppedTest`). The media item's id is the constant `MediaItems.MEDIA_ID` and its metadata only the title and series line, so the Jellyfin item id never reaches a Bluetooth device or another app (final review N-1; `MediaItemsTest`).
  - **Picture (`VideoOutput`, `PlayerEngine.video`):** the screen hands over a plain `SurfaceView`'s `SurfaceHolder` (`attach`; HDR output needs a SurfaceView, not a TextureView) and takes it back when the view goes (`detach`, only if it is still the attached one); `aspectRatio` (width over height with the pixel shape, null until known) sizes the view. Android framework types only, so the screen never names Media3. `release()` lets the surface go; `attach` after it is ignored (`ExoPlayerEngineTest`). `PlaybackController.video` exposes this and nothing else of the engine.
  - The text renderer is disabled unless a picture-subtitle track is chosen, and `load` turns text off (and clears the text override) before it sets the new item, so Media3 can never pick a default text track of the new item between two loads; the chosen picture track is applied again once the new item's tracks are known (Milestone 3 carried n-1) (its cues come out as `EngineEvent.PictureCues`, a `SubtitleFrame`). Events come in a fixed order per change (error, noisy and seek from their own callbacks, then state, then playing), so a rebuffer reads as Buffering, not a pause. Media3's logging is off (`Log.setLogLevel(LOG_LEVEL_OFF)` in `ShoalwatchApp.onCreate`): its messages carry URIs.
- **Errors (`MediaItems.failureOf`):** by `PlaybackException.errorCode` only, never the message.
  - Decoder init / query / decoding / exceeds capabilities: `DECODER`. Format unsupported, container unsupported or malformed, manifest malformed: `FORMAT_UNSUPPORTED`. Connection failed or timed out: `NETWORK`. Bad HTTP status with a 401 (`InvalidResponseCodeException` in the cause chain): `HTTP_UNAUTHORISED`, else `HTTP_OTHER`. Behind live window: `BEHIND_LIVE_WINDOW`. Anything else: `OTHER`.
  - A route refusal is found by type (`BlockedRequestException` in the cause chain, whatever the code): `OFFLINE` is `ROUTE_STALE`, `NOT_SIGNED_IN` is `NOT_SIGNED_IN`, any other refusal (a hostile playlist naming another host or path) `OTHER`.
- **Open:** `ActivePlayback.begin(session)` first (a refused begin ends the controller before anything is asked). The item comes from `Library.item` (first answer with an item, at most 5 s; none is `SERVER_NOT_FOUND`, nothing sent). RESUME starts at the saved position unless it is under 5% or over 90% of the runtime (then 0); BEGINNING at 0. Resolve; the title goes to the media session only now, just before `engine.load(item, start, playWhenReady = true)` (never the next episode's title over the paused old stream while it resolves; Task 7 review m-7): the player **seeks** to the start, no start position goes to the server. Segments (only when the plan has them; a failure leaves no skip buttons) and the episode's neighbours (`EpisodeNavigator`) follow without holding playback up.
- **Positions:** the engine's position is believed only while really playing and not 0; otherwise the last believed one stands (the start, a seek target, or the last read while playing). So a pause from becoming noisy, an error, or a close before the resume seek landed never reports 0 (Task 5 review I-1, with the reporter's own start floor).
- **Reports:** one `ProgressReporter` per play session (start position as its floor), sending in the app scope. Every pause from anywhere (the user, audio focus, a headset, becoming noisy, the sleep timer, the screen stopping) is one paused report with the real position; a rebuffer is not a pause. The stop is sent when leaving the item (next, previous, Up next, a quality change, a fallback, a failure, a close); a failure's or a fallback's stop is `failed`.
- **Finished (SPEC 3.1):** playback (not a seek) carries the position across the Outro start or 90% of the runtime, whichever comes first (a jump of over 3 s between two 250 ms ticks is a seek, e.g. from a headset); or the item ends after a position before that mark.
- **Up next:** for an episode with a next one, at the Outro start (or the end, if there is no Outro). With autoplay, a 10 s countdown of time not paused, then the next item (this one's stop first); `cancelUpNext` stops it for good; without autoplay it waits for the user. Seeking back before the mark withdraws it; the screen stopping cancels it.
- **Next and previous** come from `EpisodeNavigator`: neighbours in the season, else the next season's first or the previous season's last episode, in the app's season order (Specials last, and never crossed into or out of: after the last numbered season there is no next; within Specials next and previous stay there); each read is the first non-`Refreshing` answer within 5 s; nothing known is no neighbour. `previous` within 5 s of the start goes to the previous episode, else restarts.
- **Skip:** `segmentNow` while the position is inside any of the five segment kinds (each tick and after seeks); `skipSegment` seeks to its end. Never automatic.
- **Sleep timer (`SleepControl`):** 15, 30, 45 or 60 minutes by the monotonic clock, or end of item (offered as "End of this episode", or "End of this film" when the item has no series line; pauses there, no Up next). When it fires: pause, report, off (each due choice is taken once). Due while the next item resolves, or while a reload is in flight, the item is loaded paused (`PlayingItem.startPaused`; Task 7 review m-3).
- **Speed:** 0.5 to 2.0 in quarter steps only. **Quality:** asks again at the current position (a new play session). **Default quality (`QualityDefault`, final review I-2):** a device setting (not per user, not a secret) under `default_quality` in the private `playback_prefs` file subtitle appearance uses; the player screen sets it on the controller before the first open (`PlayerViewModel.start`), and a quality chosen in the Quality sheet is saved as the new default. With nothing saved: 8 Mbps when `ConnectivityManager.isActiveNetworkMetered` (the already-declared `ACCESS_NETWORK_STATE`; no service or a failure counts as metered), otherwise Best available. Asked at each start, so a phone moved to mobile data starts the next film at 8 Mbps.
- **Recovery:**
  - `DECODER` or `FORMAT_UNSUPPORTED` in direct play or direct stream falls back once (`resolver.fallBack`) at the same position (`fellBackToTranscode`); a second, or one in a transcode, is `PLAYBACK_FAILED`.
  - `NETWORK` or `HTTP_UNAUTHORISED` re-resolves once (a new verified address; a dead token is invalidated by `ServerApi` there); a second is `FAILED` with that kind; a resolver failure is `FAILED` with its kind.
  - `ROUTE_STALE` takes a new route for the same plan (`resolver.reroute`, no server call, same play session), up to 3 times without the engine getting ready, then `OFFLINE`. `NOT_SIGNED_IN` ends playback as signed out.
  - `HTTP_OTHER`, `BEHIND_LIVE_WINDOW` and `OTHER` are `PLAYBACK_FAILED`.
- **End (`end(reason)`):** at once, and once. Every coroutine of the controller is cancelled (a late resolve is discarded); the stop is sent for a normal close (null) and for `SESSION_CHANGED` (as the old session), nothing for `SIGNED_OUT`; `engine.setMediaMetadata(null, null)` then `engine.release()` (which releases the media session and stops every load); the record is released (only its own: a no-op when `ActivePlayback` ended it, and a controller that ended itself, such as on a signed-out route, never stays held); `PlaybackState.CLOSED` is published (`EMPTY` with `closed = true`: no session, item, title, queue, position or error, and a screen can tell it from "not opened yet", including a refused open, and leaves). An ended controller does nothing more.

## Tracks and subtitles (`TrackChooser`, `TrackControl`, `SubtitleLoader`, `SubtitleSettings`)

Subtitles done properly: text subtitles are always fetched as files and drawn by the app, so switching is instant, delay works both ways and styling can be the user's; picture subtitles come from the stream or are burned in by the server.

- **Starting tracks (`TrackChooser`, pure), by identity, never by index** (language compared by meaning through `Languages`: `eng`, `en-GB`, bibliographic `fre`/`ger` all match; `und` is unknown). Audio: the remembered language (that language's default track first) -> the server's default -> the first. Subtitles: remembered "off" (then only a forced track in the audio's language) -> the remembered language (matching forced and hearing-impaired flags first) -> system captions on: a track in the caption language, else the phone's (not forced, hearing-impaired first) -> a forced track in the audio's language -> the server's default (`DefaultSubtitleStreamIndex`, which applies the user's subtitle mode on the server; now on `PlaybackPlan.defaultSubtitleIndex`) -> off. Chosen after the first PlaybackInfo answer; the server is asked once more, before anything loads, only when the choice needs another stream (an audio track outside DIRECT_PLAY, a picture track outside DIRECT_PLAY, an external picture track).
- **Delivery (`TrackRules`, pure):** TEXT and STYLED_TEXT: FILE, whatever the play method (`SubtitleTrack.fileFormat`: `srt` for any text codec without a route format of its own, `vtt`, `ass`, `ssa`); never sent in PlaybackInfo (`SubtitleStreamIndex` -1). PICTURE: IN_STREAM during DIRECT_PLAY (the engine's text renderer, by position among the stream's own picture tracks), otherwise BURNED_IN (asked again with `pictureSubtitleIndex`); an external picture track (`.sup`) is always BURNED_IN (`burnInSubtitleIndex`). After every answer the delivery is worked out again from the new plan (a fallback to a transcode burns in a picture track that was in the stream).
- **Switching (`selectAudio`, `selectSubtitle`, `burnInSubtitle` on the controller):** a text track never asks the server again (leaving a burned-in track does). Audio during DIRECT_PLAY switches in the player by position among the stream's audio tracks, when that position's language agrees with Jellyfin's track (`PlayerEngine.audioLanguages`, once known); any disagreement asks again as a conversion with `audioIndex` (a direct play cannot change its audio). Once the stream is ready in DIRECT_PLAY with a non-default track, the same check runs once more (`TrackControl.onReady`, at most once per item). DIRECT_STREAM and TRANSCODE ask again with `audioIndex` at the current position (a new play session). A change made in the player is reported (`ProgressReporter.onTracksChanged`, ignored before playback starts). **Changes made before the server answers (Task 7 review I-1):** every step is built from the item's latest wanted request (`PlayingItem.wanted`: set by the first answer, every change, a quality change and a fallback's conversion, and from each loaded plan), not from the plan still playing, and is compared with it ("the same track" is the wanted one); while anything is still being asked (`TrackControl.Host.reloading`) every change asks again with everything wanted, so a change of mind, an audio change then a picture subtitle, or a picture subtitle during a fallback all end as chosen. The fallback, the re-resolve and the audio check on Ready ask with the wanted request too, and a stale route while a change is still being asked for asks again with it rather than putting the old plan on a new route (Task 8 review m-1). A picture track is shown as burned in only when the loaded stream's request carries it (`TrackRules.carries`); otherwise it is asked for once that load is done, through `TrackRules.step` like any change (so an external picture track is a burn-in; Task 8 review m-2) (`PlaybackControllerRaceTest`). `burnInSubtitle` asks again with `burnInSubtitleIndex`, `forceTranscode` and the track's format, which the device profile then lists as Encode only.
- **Remembering (`TrackPreferences`, Room `track_choices`):** each user change of audio or subtitles (episodes only) is saved for the series at once (in the app scope) and kept in the controller, so the next episode (Up next, next, or the next time the series is played) starts with it even before the write lands. Only the session's own row is read; another profile's choice is never seen or inherited.
- **Files (`SubtitleLoader`, `engine/SubtitleFiles`), untrusted:** fetched through `PlaybackGateway.subtitleFile` (8 MiB by declared length and while reading); checked again before parsing (and again in `SubtitleFiles.parse`), so an oversized file is never copied; parsed on a background dispatcher and waited for at most 10 s. **Parsed by the app's own readers, never by Media3's text parsers (final-fixes review I-1, I-2):** four review rounds each found another crafted SubRip, WebVTT or ASS file that made Media3's `SsaParser`, `SubripParser` + `Html.fromHtml` or `WebvttParser` do quadratic work or run out of memory inside 8 MiB, and Media3 hands nothing back until it finishes, so neither cancellation nor the 10 s wait could stop the CPU. Guarding someone else's parser did not converge, so `engine/SrtFile`, `engine/VttFile` and `engine/AssFile` (with the shared `engine/SubtitleScanner`) read the file and build Media3 `Cue`s directly (only for `SubtitleView` to draw); `Media3BoundaryTest` fails the build if `androidx.media3.extractor.text`, `SsaParser`, `SubripParser`, `WebvttParser`, a `SubtitleParser` factory or `Html.fromHtml` appears anywhere in `src/main`. **Text tracks inside a played file are not parsed either (subtitle-parsers review I-1):** Media3's `DefaultMediaSourceFactory` and `DefaultExtractorsFactory` would otherwise parse every text sample of every text track in a directly played MKV/MP4/WebM during extraction (`DefaultSubtitleParserFactory`, on the loading thread, before track selection), with the same SSA, SubRip and WebVTT parsers. The engine's one media source factory is given `engine/PictureSubtitles` as its subtitle parser factory (it forwards it to the extractors factory and HLS): it supports only PGS, VobSub and DVB and builds those parsers directly. For any text type `supportsFormat` is false, so Media3 1.9.2's `SubtitleTranscodingTrackOutput` creates no parser and passes the samples through unparsed under their own type (checked in the 1.9.2 bytecode); playback does not fail. The text renderer is never enabled for those tracks (`applyTracks` disables text unless a picture group is chosen), and if it were, Media3's legacy text decoding is off by default, so the renderer would fail rather than parse. Text tracks stay in the track list (it comes from Jellyfin's `MediaStreams`) and are fetched as files as above. `Media3BoundaryTest` also bans `DefaultSubtitleParserFactory`, `DefaultExtractorsFactory`, the parse-during-extraction and transcoding switches, legacy decoding and the other text parsers; its one exception is `PictureSubtitles.kt`, which may name `SubtitleParser`, and `.setSubtitleParserFactory(PictureSubtitles)` is the only factory any media source factory is given (`PictureSubtitlesTest` reads the engine's factories by reflection).
  - **Decoded once (`SubtitleLines`):** charset from a UTF-8, UTF-16 LE or UTF-16 BE byte order mark, otherwise UTF-8 with U+FFFD for anything invalid; NUL and every other control character except tab removed, and U+2028, U+2029 and U+FEFF removed (never line breaks); lines split at `\r\n`, `\n` or a lone `\r` and read one at a time (no list of all lines).
  - **Linear by construction:** building a cue's spans costs at most a constant (32 runs); every reader is a single pass over the lines with a fixed number of looks at each; no regular expression anywhere; no cue looks at an earlier one; a tag (`<…>`, `{…}`) counts only when its closer follows on the same line (one `lastIndexOf` per line) and is then skipped to that closer, so an unclosed `<` or `{` is literal text and no character is read more than twice; style tags are depth counters, not a stack; every id, style name and setting is at most 64 characters (a longer one is ignored). The timeline sorts once (n log n) and sweeps the starts and ends with a sorted set; `frameAt` is a binary search.
  - **Caps, and what happens over each:** 8 MiB of bytes: refused. 50,000 cues (every timing line, or every ASS `Dialogue:` line, read or not): refused ("Too many subtitles."). 2,000 characters of one cue's text after tags are removed, and 16 lines per cue: the rest of that cue is dropped, never the file. 32 styled runs (bold, italic, underline changes) per cue: later style changes in that cue are ignored and the text kept (subtitle-parsers review I-2: Android's `setSpan`, and `SubtitleView`'s span removal on the main thread when the file's styling is off, each scan every span already there, so spans must stay few; bold and italic share one span). 256 ASS styles: later ones ignored (and the first of a name wins). 4,096 characters for an ASS header line (`[Script Info]` and style lines, any `Format:`), checked before it is split: over it, refused (review m-1; a `Dialogue:` line is text and is not limited this way). 64 characters per id, style or setting token: that token ignored (an over-long style name is an unknown style). 16 cues and 4,000 characters shown at one instant (review m-2: the view lays them out on the main thread): the first cues in start order (file order for the same start) while both caps hold, drawn in ASS layer order. A cue starting after 48 hours is dropped; one ending later ends there. Refused means the fixed `IllegalArgumentException`, so `subtitleNotice = UNREADABLE`.
  - **Cancellation really stops the work:** the parse asks the loader's `cancelled()` (the parsing coroutine's `isActive`) before the first line, at every 1,000th line, every 50th cue and every 1,000th timeline step, and throws "Stopped."; the 10 s limit, leaving the player, choosing another track or the next episode therefore end the CPU use within about 1,000 lines (`SubtitleHostileTest`). `OutOfMemoryError`, a stack overflow and any runtime exception are still the fixed "unreadable" (`SubtitleFiles.guarded`, a last line of defence).
  - **SubRip (`SrtFile`; also what the server sends for `mov_text` and every other text codec it converts):** a cue starts at a line holding `-->` (the index line is optional and ignored): `[HH:]MM:SS,mmm --> [HH:]MM:SS,mmm`, `.` also accepted, 1 to 3 fraction digits (a decimal fraction: `,5` is 500 ms, which Media3 read as 5 ms) or none (whole seconds, as hand-made files have; review m-3), anything after the end time ignored; a negative, unreadable or reversed time drops that cue. Text runs to the next blank line, each line trimmed: `<i>`, `<b>`, `<u>` and their closers style; `{\anN}` before any visible text places the cue (8% in from the side or edge it names, as Media3 placed it); every other `<…>` or `{…}` tag is removed; `&amp; &lt; &gt; &nbsp; &lrm; &rlm;` are decoded (as `Html.fromHtml` did), any other `&` is literal.
  - **WebVTT (`VttFile`):** a `WEBVTT` first line is required (otherwise refused); `NOTE`, `STYLE` and `REGION` blocks are skipped without being interpreted (no CSS is parsed); an optional cue id; `[HH:]MM:SS.mmm --> [HH:]MM:SS.mmm` (the fraction may be left out) and settings, of which only `line` (percent, or a line number, with `start`/`center`/`end`), `position` (percent, with `line-left`/`center`/`line-right`) and `align` are read, by a plain split at spaces; unknown or over-long ones are ignored. Text: `<i>`, `<b>`, `<u>` style; `<c…>`, `<v …>`, `<lang …>`, `<ruby>`, timestamps and any other tag are removed (the voice name is not shown); ruby base text is kept and `<rt>` text dropped; the same six entities are decoded.
- **ASS/SSA (`AssFile`, no native code; see `research/2026-11-styled-subtitles-spike.md`):** `[Script Info]` `PlayResX`/`PlayResY`; `[V4+ Styles]` and legacy `[V4 Styles]` (legacy alignments mapped to the keypad) through their `Format:` line: Name, Bold, Italic, Underline, PrimaryColour, Alignment. `[Events]` through its latest `Format:`, which must have Start, End and Text with **Text last** (the text is the rest of the line), or the file is refused, so every other field (Style among them, review I-1) is one comma-free token; `Format:`, `Style:` and `Dialogue:` are matched case-sensitively at a line's start as Media3 matched them, and a `Dialogue:` under another `[section]` is not an event. Times `[H:]MM:SS.cc`: hours optional, 1 to 3 fraction digits read as a decimal fraction, `:` also accepted before them. Text: `\N`/`\n` break the line, `\h` is a hard space; an override block `{…}` is scanned once: from the **first block only**, `\pos(x,y)` (as a fraction of PlayRes; ignored without PlayRes, as Media3 did), `\an1`–`\an9`, legacy `\a`, `\i0/1`, `\b0/1` (or a weight of 700 or more), `\u0/1` and `\c`/`\1c&Hbbggrr&` apply to the **whole cue** (kept simple on purpose), even when that first block is mid-line: `I {\i1}really{\i0} mean it` is drawn wholly italic, where Media3 drew it plain (review m-4, accepted); in any block `\p1`… starts a drawing whose text is dropped and `\p0` ends it; every other tag is removed. An aligned cue without `\pos` sits 5% in from the side or edge (Media3's placement). **Drawn:** style and override colour, bold, italic, underline, alignment, `\pos`, layer order (lower layers first, later drawn on top). **Not drawn:** font sizes from the file (the user's size always applies), `BorderStyle=3` boxes and outline/back colours, strike-out, margins, override tags after the first block (a mid-line `{\i1}` does not italicise part of a line), karaoke `\k`, `\t` animation, `\move`, `\fad`/`\fade`, `\p` drawings, `\clip`, `\fn`, `\fr`/`\org` rotation and embedded fonts. When a file uses any of `\k`, `\K`, `\kf`, `\ko`, `\t(`, `\move(`, `\fad(`, `\fade(`, `\p1`–`\p9`, `\clip(`, `\iclip(`, `\fn`, a non-zero `\fr`/`\frx`/`\fry`/`\frz` or `\org(` (`AssEffects`, applied to each removed tag; rotation added by review m-5; cosmetic `\fsc`, `\bord`, `\shad`, `\blur`, `\be` are not flagged), `CueTimeline.usesEffectsThePhoneCannotDraw` is set, `PlaybackState.subtitleEffectsNotDrawn` is true (the menu offers "Let the server draw these subtitles", `burnInSubtitle`) and the user is told once per item (`subtitleNotice = EFFECTS_NOT_DRAWN`, `dismissSubtitleNotice`).
- **Behaviour changes from Media3's parsers (all accepted):** an ASS file whose events `Format:` does not end with Text, or lacks Start or End, is refused; a WebVTT file without its header was already refused; hour-less ASS times play (Media3 alone threw on them); lines that start at different times stack in start order, not file order; a cue's text is cut at 2,000 characters and 16 lines (was 1,000 characters per line and 20 lines); an unclosed `<` or `{` shows as text; SubRip `<font color>` and other HTML styling beyond bold, italic and underline are no longer drawn; WebVTT `STYLE` blocks (CSS) and `size`/`vertical`/`region` settings are ignored; ASS `\c` overrides, `\i`/`\b`/`\u` overrides, underline and legacy `[V4 Styles]` are now drawn; ASS fractions of 1 or 3 digits are decimal fractions (Media3 read every fraction as hundredths). Out-of-order cues are sorted; overlapping cues show together. A failure leaves playback running, subtitles off and `subtitleNotice = UNREADABLE` ("These subtitles couldn't be read."). Nothing from a file is logged.
- **Drawing:** `PlaybackController.cues` (`StateFlow<SubtitleFrame>`, opaque outside `engine/`) is the text timeline's frame at (position - delay), refreshed every 50 ms while playing and on every state change (a seek, a pause, a delay change), or the stream's picture cues (`EngineEvent.PictureCues`) for IN_STREAM. `engine/SubtitleSurface` (Media3's `SubtitleView`) draws it; Task 8's screen hands it each frame and each appearance. `PlaybackState` carries no Media3 type.
- **Delay:** per item (`setSubtitleDelay`, -10,000..+10,000 ms in steps of 100; later is positive), FILE delivery only (ignored for IN_STREAM and BURNED_IN, whose controls say why), kept across seeks and reloads of the item, never saved.
- **Appearance (`SubtitleSettings`, private `playback_prefs`):** size (50 to 300%), colour (white, yellow, cyan, green), background (none, shaded, solid), edge (none, outline, drop shadow), keep file styling (ASS colours and positions kept, the user's size still applies; off: the user's colour, background and edge replace the file's), bottom margin. A `StateFlow`, so a change applies at once. Until the user changes anything in the app it follows the phone's caption settings (`CaptioningManager`: font scale always; colour, background and edge only when captions are switched on, since otherwise the style is the system's preset); `refresh()` re-reads them; once the user chooses, theirs wins.
- **Session rule:** everything above lives in the item's `PlayingItem` (choice, file, timeline, delay, notice) or the controller (the last choice), both dropped with the item or the controller; a subtitle file that arrives for an item no longer playing is discarded; `end()` empties `cues` at once.

The top bar's "Picture-in-picture" button (only where the phone has `FEATURE_PICTURE_IN_PICTURE`) enters whenever a wish exists, even with the setting off. **"Keep playing in a small window when you leave the app"** (Settings, Playback; `PipPrefs`, key `pip_auto` in `playback_prefs`, default on, a device setting with no grown-up check) governs only entering by itself. **In the window** (`PlayerScreen(inPip = true)`): only the picture and its subtitles, no controls, gestures, Up next or watch-and-delete card, sheets or snackbars (a notice waits for the full screen; ignoring the watch-and-delete prompt leaves the download, SPEC §3.1). Up next still counts down and plays the next episode if the profile allows. Back to the full screen the controls show once. **The lock:** entering counts as leaving (`LockGate.onLeft`) and back to the full screen as returning (`onReturned`), so a window left running past "Lock after" shows the lock (and resets the stack, stopping the player) when expanded, never the protected profile. Closing the window stops the activity before Android reports the mode change, so that is not a return (the activity's own `onStop`/`onStart` count the trip) and the player pauses on the stop as it always has. A stop and start while the window stays up (the screen off and on, the keyguard, a recreation for dark mode) is not a return either: `onActivityStarted` reads `isInPictureInPictureMode` and counts a return only outside the window, so expanding hours later still locks (review C1); it also sets `inPip` from it, as a recreated activity hears no mode change (M3). When the wish goes while in the window (the last episode ended, playback failed, the lock cover), `moveTaskToBack(false)` closes the window rather than show the page beneath in it (M1); not on a configuration change, and only when this instance held a wish: an activity recreated in the window withdraws one on its first frame (the lock cover is up until the lock state is read), which must not close it (re-review N1). A `false` from `moveTaskToBack` is logged. An `IllegalArgumentException` from the params (an aspect outside an OEM's narrower range) is logged like an `IllegalStateException`, not a crash (M4). Tests: `PictureInPictureTest`, `PipModeRenderTest`, `PipPrefsTest`; on a device, `PipSmokeTest`.
- **Sheets (`PlayerSheets`, `SubtitleStyleSheet`):** one at a time, each scrolling, every choice a radio row (role, selected state, 48dp): audio and subtitle tracks (with "Let the server draw these subtitles" while effects are not drawn), quality, speed, sleep timer, subtitle size, colour, background and edge, a "Use the file's own styling" switch, the delay ("Show subtitles earlier" / "later" in 0.1 s steps, only for a file subtitle; otherwise the reason), and About this video (`PlayerText.streamInfo`, the HDR line, the quality).
- **Errors and notices:** FAILED shows `AppError.of(kind).userMessage` with Try again (or Sign in, to `sign_in/{serverId}`, for `UNAUTHORISED` and `NOT_SIGNED_IN`) and Back. Unreadable subtitles, effects not drawn (with the action to let the server draw them) and the sleep timer pausing are snackbars, each dismissed once said.

Your server is repackaging it for this phone."; TRANSCODE "Your server is converting this video for this phone" with the first reason that has words (an unexplained `OTHER` listed first does not hide a real one; a fallback always says "because this phone couldn't play the original").
